HTTP Request Smuggling

HTTP Request Smuggling is a critical vulnerability where an attacker exploits disagreement between front-end and back-end servers about where one HTTP request ends and the next begins. By crafting a request with conflicting Content-Length and Transfer-Encoding headers, the attacker can "smuggle" a partial request into the queue, which gets prepended to the next legitimate user's request · leading to request hijacking, cache poisoning, or account takeover.

Real-World Analogy

📖 The Customs Officers

Two customs officers inspect luggage in sequence. Officer 1 reads a label saying "3 bags" and checks them through. Officer 2 reads the same label but interprets it as "2 bags" and only processes the first two. The third bag gets labeled as belonging to the next passenger and gets smuggled through. HTTP Request Smuggling is similar: the front-end server (CDN, load balancer) and back-end server (application) disagree on how many requests were submitted. By exploiting this disagreement, the attacker smuggles a partial request that gets attached to the next user's request.

🎯 Day 1 · Confirm Multi-Tier Architecture

Request Smuggling only applies if there's a front-end and back-end server (CDN + origin, load balancer + app, reverse proxy + backend). During reconnaissance, check for these indicators: X-Forwarded-For or X-Real-IP in responses (indicates proxy layer), multiple server headers, response timing variations that suggest different backends. If it's a single-server app, request smuggling is not applicable.

🎯 Day 4 · Request Smuggling Testing

On Day 4, only if you've confirmed a multi-tier architecture, test for request smuggling. Install the HTTP Request Smuggler Burp extension. Run the Smuggle Probe on target endpoints. If the probe confirms vulnerability (timing-based detection or observable smuggling), escalate to chained attacks like cache poisoning or session hijacking. This is complex and requires careful timing and validation.

How It Works

HTTP/1.1 allows two ways to specify the body length of a request:

  1. Content-Length (CL): Specifies the exact number of bytes in the body. Example: Content-Length: 13 means the body is exactly 13 bytes.
  2. Transfer-Encoding: chunked (TE): The body is divided into chunks. Each chunk is prefixed with its size in hex, followed by the chunk data. A zero-sized chunk signals the end of the body.

The vulnerability: If the front-end server prioritizes one header (e.g., CL) and the back-end prioritizes the other (e.g., TE), they disagree on where the request ends. The attacker crafts a request where the front-end thinks the body ends at byte X, but the back-end thinks it ends at byte Y. The difference is "smuggled" into the next request.

Example · CL.TE attack (front-end uses CL, back-end uses TE):

POST / HTTP/1.1
Host: example.com
Content-Length: 49
Transfer-Encoding: chunked

e
GET /admin HTTP/1.1
Host: example.com

0

[Next legitimate user's request comes here]

Front-end reads Content-Length: 49 and forwards the first 49 bytes. Back-end reads Transfer-Encoding: chunked and processes the "e" (hex 14, decimal 14 bytes), which is the GET /admin request. The GET /admin request gets smuggled and prepended to the next user's request, executing as if the next user made that request.

Where to Look

HTTP Request Smuggling is only relevant if:

  • Multi-tier architecture exists: CDN + origin server, load balancer + backend, reverse proxy + application. Single-server deployments are not vulnerable.
  • Keep-alive connections are enabled: The vulnerability requires persistent connections so the smuggled request gets prepended to the next user's request. If keep-alive is disabled, each request gets a fresh connection and smuggling is not possible.
  • HTTP/1.1 is used end-to-end: HTTP/2 doesn't support Transfer-Encoding: chunked, eliminating the attack class. If front-end uses HTTP/1.1 but back-end uses HTTP/2 (or vice versa), smuggling may still be possible but in different forms.
  • Front-end and back-end disagree on request boundary: This is the core requirement. If both enforce the same standard, there's no disagreement and no smuggling.

Indicators of vulnerability: Response headers include X-Forwarded-For, response timing is inconsistent (suggests different backend servers), server header changes between requests, application doesn't reject Transfer-Encoding header.

WAF Bypass Techniques

TE.CL Variant

WAF parses by Content-Length; backend parses by Transfer-Encoding. Send: Transfer-Encoding: chunked with a body that is a valid chunk sequence AND has a Content-Length that disagrees. The WAF sees one request; the backend sees two.

POST / HTTP/1.1
Host: example.com
Transfer-Encoding: chunked
Content-Length: 49

0

GET /admin HTTP/1.1
Host: example.com

Obfuscating Transfer-Encoding

Some servers accept malformed TE headers that WAFs normalise away:

Transfer-Encoding: xchunked
Transfer-Encoding : chunked  (space before colon)
Transfer-Encoding: chunked, identity
X: X\r\nTransfer-Encoding: chunked  (header injection)

HTTP/2 Downgrade (H2.CL / H2.TE)

WAF speaks HTTP/2 to the frontend (no request smuggling possible in H2). Frontend downgrades to HTTP/1.1 to the backend. Inject a Transfer-Encoding or Content-Length in an HTTP/2 header field · the downgrade carries it to HTTP/1.1 where smuggling applies.

Chunk Size Obfuscation

Valid hex chunk sizes accept leading zeros and uppercase: 0000000A is valid for a 10-byte chunk. WAFs matching \r\n0\r\n\r\n as the terminal chunk miss \r\n00\r\n\r\n.

0000000A
Request smuggling payload
00

Header Smuggling via CRLF

Inject \r\n in a header value: Foo: bar\r\nTransfer-Encoding: chunked. RFC-compliant parsers reject this; some real-world servers accept it, allowing you to inject a second TE header the WAF never saw.

Foo: bar\r\nTransfer-Encoding: chunked

Exploitation & Impact

Bypass Access Controls

Impact: Critical. Smuggle a request for /admin or other restricted endpoint. The back-end processes it as if the front-end (which bypasses auth) sent it.

  • Access admin panels.
  • Modify user permissions.
  • Escalate to full compromise.

Steal Other Users' Requests

Impact: Critical. Smuggle a request that causes the back-end to respond with the next legitimate user's request. This reveals the victim's request, including:

  • Session cookies / tokens.
  • Private data in request bodies (passwords, PII).
  • Internal endpoints the victim accessed.

Cache Poisoning via Request Smuggling

Impact: High. Smuggle a request that poisons the cache. All subsequent users receive poisoned content.

XSS via Request Smuggling

Impact: High. Smuggle a request containing XSS payload. If the response is cached, all users get XSS.

Partial Request Replay

Impact: Medium-High. Capture part of the next user's request (headers, body) and replay it independently, potentially modifying it to cause unintended actions.

Denial of Service

Impact: Medium. Continuously smuggle malformed requests that exhaust back-end resources or cause crashes.

Remediation

1. Disable HTTP/1.1 Keep-Alive on Front-End

Requires a fresh connection for each request, eliminating the ability to smuggle into the next user's request:

# Nginx
http {
  keepalive_timeout 0;
}

2. Ensure Both Servers Use Same Body Length Standard

Configure both front-end and back-end to prioritize the same header:

Front-end (Nginx):
proxy_pass http://backend;

Back-end (Apache):
LimitRequestFieldSize 8190  (enforce strict header parsing)

3. Upgrade to HTTP/2 End-to-End

HTTP/2 doesn't support Transfer-Encoding: chunked, eliminating the attack vector. If upgrading the entire stack isn't possible, at least upgrade the front-end to HTTP/2.

4. Don't Strip or Normalize TE Headers Between Servers

Some proxies try to "normalize" requests by removing conflicting headers. Don't do this · ensure servers communicate consistently:

// Bad: proxy removes TE header
if (request.headers['transfer-encoding']) {
  delete request.headers['transfer-encoding'];
}

// Good: pass headers as-is
proxy_pass http://backend;

5. Implement Request/Response Validation

Validate that Content-Length and Transfer-Encoding are never both present in a single request:

if (request.headers['content-length'] && request.headers['transfer-encoding']) {
  reject_request('Both Content-Length and Transfer-Encoding present');
}

6. Monitor for Smuggling Attempts

Alert on requests with unusual header combinations:

  • Both Content-Length and Transfer-Encoding headers.
  • Multiple Transfer-Encoding headers.
  • Conflicting body sizes between CL and TE.
  • Non-chunked Transfer-Encoding values.

7. Enforce Strict RFC 7230 Compliance

Both front-end and back-end must strictly follow RFC 7230 HTTP/1.1 specification for header parsing and request boundary detection.

Common Beginner Mistakes

Testing Single-Server Apps

Mistake: Attempting request smuggling on applications without a multi-tier architecture. Fix: Confirm multi-tier setup first by checking for X-Forwarded-For, Via, or other proxy headers. If the app is single-server, request smuggling doesn't apply.

Not Using HTTP Request Smuggler Extension

Mistake: Manually crafting CL.TE/TE.CL payloads without understanding the exact byte counts. This is error-prone. Fix: Always use the HTTP Request Smuggler extension · it automates the probe and handles byte calculations.

Forgetting to Disable Content-Length Update

Mistake: Manually crafting a smuggling payload, but Burp automatically recalculates Content-Length, breaking the attack. Fix: In Burp Repeater, go to Inspector tab and uncheck "Update Content-Length" before sending.

Not Understanding Timing-Based Detection

Mistake: Sending a probe and immediately assuming it's not vulnerable when there's no obvious error. Fix: CL.TE attacks often manifest as timeouts (server waiting for chunk end marker). Watch the response time · if it's significantly delayed (5-10 seconds), the server may be CL.TE vulnerable.

Missing the Exploitation Step

Mistake: Confirming request smuggling works but not escalating to actual exploitation. Fix: If smuggling is confirmed, escalate immediately: try to access /admin, capture the next user's request, or poison the cache. These are the high-impact exploitations.
