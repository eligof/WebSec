Web Cache Poisoning

Web Cache Poisoning is an advanced attack where an attacker manipulates an unkeyed input (a header or parameter that affects the response but isn't part of the cache key) to inject malicious content into the cache. All subsequent users requesting the same resource receive the poisoned version, making this a high-impact vulnerability affecting multiple victims simultaneously.

HIGH BSCP Advanced

Real-World Analogy

📖 The Library's Photocopy Machine

A library photocopies popular books to save time. They file the original and keep photocopies at the counter. An attacker sneaks in and replaces a page in the original book before the next photocopy is made. From that moment on, every patron who requests a copy receives the tampered version. The librarian never knows the original was corrupted · it's filed in the back. Web cache poisoning works the same way: the attacker injects a malicious input that modifies the response before it's cached, and then every user receives the poisoned version.

🎯 Day 4 · Identify Cached Responses

On Day 4, start by finding endpoints that are cached. Look for response headers like X-Cache: HIT, CF-Cache-Status: HIT, Age, or Cache-Control: public. These indicate a caching layer is in front of the origin server. Install the Param Miner Burp extension · it will help you discover unkeyed inputs automatically.

🎯 Day 5 · Deep Dive into Cache Poisoning

On Day 5, for every cached endpoint, use Param Miner to find unkeyed headers that affect the response. Once found, craft a request with a malicious payload (XSS, redirect, etc.) via the unkeyed header. First, confirm the injection in the response. Then, remove Cache-Control: no-cache and resend · if the response is cached with your payload, you've achieved cache poisoning. All future users get the poisoned version.

How It Works

Caches use a cache key to identify unique requests. Typically the cache key includes:

  • HTTP method (GET, POST)
  • Request path (/api/user, /product/123)
  • Query parameters (?page=1)

The vulnerability: If a header or parameter affects the response but is NOT in the cache key, an attacker can submit two requests that the cache treats as identical (same cache key) but that the origin server responds to differently (different header value). The second request can poison the cache.

Attack flow:

  1. Attacker sends request with unkeyed header containing XSS payload.
  2. Origin server reflects the payload in the response.
  3. Attacker confirms XSS appears in the response body.
  4. Attacker removes Cache-Control: no-cache (which prevents caching) and resends.
  5. Cache layer sees the request matches previous requests (same cache key) but the response is new, so it caches the poisoned version.
  6. All subsequent users receive the poisoned cached response with the XSS payload.

Why it works: Caches don't validate the origin server's response · they trust it. If the origin server includes user input in the response without sanitizing, the cache stores that user input. The attacker controls the user input via an unkeyed header.

Where to Look

Cache poisoning is only possible on cached endpoints. Look for these indicators:

  • Cache headers in response: X-Cache: HIT, CF-Cache-Status: HIT, Age, Cache-Control: public, max-age=X
  • Content Delivery Networks (CDNs): Cloudflare, Akamai, AWS CloudFront, Fastly. These aggressively cache static and dynamic content.
  • Reverse proxies: Nginx with caching enabled, Varnish, Squid.
  • Endpoints serving: JavaScript files, CSS, HTML pages, API responses that are marked cacheable.
  • Headers that reflect user input: X-Original-URL, X-Forwarded-Host, X-Rewrite-URL, Referer, User-Agent · any header that might be used to construct a response.

Difference from SSRF: SSRF requires the server to fetch a URL you control. Cache poisoning requires the cache to serve your poisoned response to other users.

Burp Suite Workflow

1
Install Param Miner extension. Go to Burp Extensions → BApp Store → search for "Param Miner" by albinowax. Install it. This extension automatically discovers unkeyed inputs that affect responses.
2
Identify a cached endpoint. Navigate to any resource (HTML page, JavaScript, API endpoint) and check the response headers. Look for X-Cache: HIT or Age or CF-Cache-Status. 
GET /index.html HTTP/1.1
...
Response Headers:
X-Cache: HIT
Age: 3600
Cache-Control: public, max-age=86400
3
Use Param Miner to find unkeyed inputs. Right-click the request → Extensions → Param Miner → Scan for cache unkeyed inputs. Param Miner will test dozens of headers automatically and report which ones affect the response but aren't in the cache key.
4
Inject XSS payload via unkeyed header. Once Param Miner finds an unkeyed header (e.g., X-Forwarded-Host), send the request to Repeater and inject an XSS payload: 
GET /index.html HTTP/1.1
Host: target.com
X-Forwarded-Host: attacker.com">
Cache-Control: no-cache

Response includes:
<a href="https://attacker.com">>...</a>
5
Confirm injection in response body. Check that your payload appears in the response. If it does, you have an injection point.
6
Remove Cache-Control and resend to poison the cache. Delete the Cache-Control: no-cache header from your request and resend: 
GET /index.html HTTP/1.1
Host: target.com
X-Forwarded-Host: attacker.com">
If the cache now returns the response (check X-Cache: HIT), the cache has been poisoned.
7
Verify poisoning from a different IP/user agent. Open a new tab, incognito mode, or use a different device to access the same endpoint. If you see your injected payload, cache poisoning is confirmed.

WAF Bypass Techniques

Cache Key Header Variation

Different capitalisations of headers that are unkeyed. Some caches normalise; some WAFs only inspect one form.

X-Forwarded-Host: attacker.com
x-forwarded-host: attacker.com
X-FORWARDED-HOST: attacker.com

Delimiter Injection in Keyed Parameters

Inject ?utm_content=x;injected=y. Some caches treat ; as a parameter delimiter and include only utm_content in the cache key, while the backend sees injected as a separate parameter.

GET /page?utm_content=x;injected=y HTTP/1.1

Fat GET Requests

Send a GET request with a body: GET /page HTTP/1.1\r\n...\r\n\r\ninjected=payload. Some caches key only on the URL; some backends process the body. WAFs often don't inspect GET request bodies.

GET /page HTTP/1.1
Host: example.com
Content-Length: 18

injected=payload

Cache Buster Bypass

WAFs may add cache-busting parameters to protected requests. Strip them using parameter pollution: ?cb=waf_added&cb= · some caches use the last value (empty), defeating the buster.

GET /page?cb=waf_added&cb= HTTP/1.1

Vary Header Exploitation

If the cache Varys on Accept-Encoding, send Accept-Encoding: gzip, evil-value. The poisoned cache entry is served to victims whose browsers send gzip.

Accept-Encoding: gzip, evil-value

Response Header Injection via Unkeyed Headers

X-Forwarded-Scheme: http forces a redirect stored in cache. WAFs that only inspect request paths miss header-based injection targeting cache-stored redirects.

X-Forwarded-Scheme: http

Exploitation & Impact

Stored XSS via Cache Poisoning

Impact: Critical. Inject XSS via an unkeyed header, poison the cache, and every user who visits the endpoint gets XSS.

  • Steal session cookies from all users.
  • Perform actions on behalf of all users.
  • Redirect all users to a phishing page.
  • Modify the page content for all users.

Redirect Poisoning

Impact: High. Poison the cache with a redirect to a phishing or malware site. Every user is redirected.

Attacker poisons cache with:
Location: https://phishing.com/fake-login

All users hit the poisoned cache and are redirected to phishing.com

Denial of Service

Impact: Medium. Cache a 404 or 500 error response for a critical endpoint. All users receive an error.

Response Header Injection (Cookie Poisoning)

Impact: High. Inject newlines to add a malicious Set-Cookie header. Every user receives the poisoned cookie.

X-Header: value
Set-Cookie: admin=true; Path=/

(Cached as part of response, affecting all users)

Content-Type Confusion (JS/CSS Injection)

Impact: High. If a cache doesn't validate Content-Type, serve JavaScript with CSS extension, or vice versa. Depending on how the client interprets it, you can achieve arbitrary code execution or script injection.

Remediation

1. Include All Response-Affecting Inputs in Cache Key

Use the HTTP Vary header to tell caches which inputs affect the response:

Vary: Host, X-Forwarded-Host, Accept-Encoding

// This tells the cache: "If Host or X-Forwarded-Host differs, treat it as a different request"

2. Don't Reflect Request Headers in Responses

Avoid reflecting headers directly into the response body:

// Bad: reflects request header
response.write("Cache for: " + request.headers['x-original-url']);

// Good: use a configured value
response.write("Cache for: " + config.primaryDomain);

3. Disable Caching for Dynamic Content

Use Cache-Control: no-store or Cache-Control: private for responses that contain user-specific or dynamic content:

if (responseContainsUserData || responseContainsUserInput) {
  response.setHeader('Cache-Control', 'no-store');
}

4. Validate and Sanitize Reflected Headers

If you must use headers in responses, validate and sanitize them:

const ALLOWED_HOSTS = ['example.com', 'www.example.com'];
const host = request.headers['x-forwarded-host'];
if (!ALLOWED_HOSTS.includes(host)) {
  return response.status(400).send('Invalid Host');
}

5. Use CSP to Prevent XSS

Even if cache poisoning succeeds with XSS, a strong CSP can block it:

Content-Security-Policy: default-src 'self'; script-src 'self';

6. Configure Cache Layer Properly

Educate your cache layer (CDN, reverse proxy) about what should and shouldn't be cached:

  • Don't cache responses with Set-Cookie headers.
  • Don't cache responses with Authorization headers.
  • Do cache only responses with explicit Cache-Control headers.

7. Monitor Cache Hit Ratio and Anomalies

Alert if cache hit ratio unexpectedly changes, or if unexpected content is being served from cache.

Common Beginner Mistakes

Not Using Param Miner Extension

Mistake: Manually testing headers without Param Miner. There are dozens of unkeyed headers to test; manual testing is tedious and you'll miss most of them. Fix: Always use Param Miner. It's fast and discovers unkeyed inputs automatically.

Not Checking Cache Headers

Mistake: Testing endpoints that aren't cached, or assuming an endpoint is cached without checking the response headers. Fix: Always check for X-Cache, Age, CF-Cache-Status, or Cache-Control headers. If they don't indicate caching, the endpoint isn't cached and can't be poisoned.

Forgetting to Remove Cache-Control: no-cache

Mistake: Testing injection with Cache-Control: no-cache, confirming the injection works, but then forgetting to remove it before trying to poison the cache. Fix: To poison the cache, you MUST remove Cache-Control: no-cache, no-store, and any other cache-busting headers.

Not Testing from Different Clients

Mistake: Injecting a payload but not verifying it's actually cached by visiting from a different IP/browser/incognito window. Fix: After poisoning, always verify by accessing the endpoint from a fresh client (different IP, different browser, incognito mode) to confirm the poisoned response is being served.

Missing Response Header Injection

Mistake: Only testing for body injection (XSS) and missing header injection opportunities. Fix: Test for newline injection (%0d%0a) in headers to inject Set-Cookie or Location headers. These are often even more dangerous than body injection.
